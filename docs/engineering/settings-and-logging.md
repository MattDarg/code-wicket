> The reasoning and measurements behind AGENTS.md's rules for settings, the Unified Settings
> manifest and logging.

> mode, not links — the rule each one tags is stated here in full, so nothing is missing if you
> cannot open them.

## ExtensionConfig and config.json

One model: **`ExtensionConfig`** over **`%APPDATA%\code-wicket\config.json`** (`CodeWicket.Shell`, STJ). Drives the VSIX + standalone hosts + header pickers. Fields incl. `DefaultProvider`/`DefaultModel`/`DefaultPermissionMode`/`AllowedCommands`/`AlwaysPromptCommands`/`AllowedPaths`/`KiroEnabled`/`ClaudeCodeEnabled`/`KiroCliPath`/`ClaudeAcpPath`/`CustomAcpAgents`/`TerminalMirrorEnabled`/`RunCommandEnabled`/`AgentWorkspaceScope`/`UseStubIde`/`LogAcpFrames` (**`UseStubIde` is config-only — deliberately NOT surfaced in Unified Settings.** It is developer plumbing: the stub swaps out the live VS services, a way to make a normal install behave oddly with no product benefit; hand-editing config.json is the escape hatch the test hosts use. **There is no `EngineExePath` field any more** — removed 2026-09-10, after the pre-release security review of September 2026: config.json is a file an agent can write under AcceptEdits, and a path in it was an executable the next window open would spawn as the user. The override is `CWKT_ENGINE_EXE` alone, an environment variable a tool call cannot set on devenv; an old file still carrying the key is ignored by the deserializer) (`TerminalMirrorEnabled` applies live via `Changed`; `RunCommandEnabled` gates the catalog at build, so next window open). A malformed/unreadable config falls back to defaults but is **logged** to `logs\config-error.log` (and a corrupt file is preserved as `config.json.bad`) rather than resetting silently.

**`KiroEnabled`/`ClaudeCodeEnabled`** (per-built-in enable checkboxes in settings, default on) switch a backend off entirely — a disabled backend is never registered by the engine (not in the picker, can't start), for installs where e.g. Kiro/Claude can never work.

**The UI is enable-checkboxes but the engine wire stays opt-out** (`CWKT_DISABLED_PROVIDERS`, a `;`-list the shell derives from the unchecked built-ins): absent = all on, so a new built-in lights up automatically for existing installs and custom agents stay enabled-by-presence (an allowlist would need every custom-agent add to also opt in). Custom agents toggle by presence in `CustomAcpAgents` (removing one disables it); the engine still honors a custom id in `CWKT_DISABLED_PROVIDERS` if hand-set in config.json.

**The fake provider is opt-in**: the engine registers it only when launched with `--fake` (= `DefaultProvider` explicitly `"fake"`), so end-user installs never see it; Desktop/Console test hosts pass it explicitly. `ChatToolWindow` honors `DefaultProvider` for the session request (was hardcoded fake-or-kiro); a configured default that isn't registered falls back to the picker's first available provider.

**`CustomAcpAgents`** adds any stdio-ACP CLI as a backend via config alone (per entry: `providerId`/`displayName`/`cliPath`/`args`/`env`/`capabilities`/`models`; capability names = `AgentCapabilities` flags). Surfaced in Unified Settings as a validated multiline JSON field; **saving probes each new/changed entry with a real ACP `initialize` handshake** (`Shell.AcpAgentProbe`, raw line-JSON so it works on net472) — bad path / non-ACP CLI rejects the save with the reason, and entries without hand-written `capabilities` get discovered ones persisted (spec baseline + `loadSession`→ResumeSession), marked `capabilitiesDiscovered: true`. Discovered/omitted capabilities also **refresh from `initialize` on every session start** (`AcpAgentConfig.DiscoverCapabilities` → provider updates ResumeSession in place, catching agent updates); hand-declared capabilities are authoritative and never touched. Hand-editing config.json directly skips the probe (the offline escape hatch). Applies on the next engine launch (reopen the chat window). Custom agents appear in the header picker via `engine/listProviders`, but the static `provider` enum in registration.json (default backend) can't list them. `ExtensionConfig.Changed` (static event) fires after every write so live consumers re-read (e.g. `ChatToolWindow.OnConfigChanged` re-applies command policy).

## Engine-consumed settings

Engine-consumed settings forward as **env** on the engine process (`EngineClient.Launch(env:)`): `CWKT_ACP_LOG`, `CWKT_KIRO_CLI`, `CWKT_KIRO_AGENT_ENGINE`, `CWKT_CLAUDE_ACP`, `CWKT_CUSTOM_AGENTS` (the serialized `CustomAcpAgents` array), `CWKT_MODEL_CACHE` (the serialized `DiscoveredModels` per-provider model cache, seeded onto providers at launch), `CWKT_WORKSPACE_SCOPE` (`RepositoryRoot` default / `SolutionOnly`, from `AgentWorkspaceScope` — how far above the solution a backend may look for its workspace marker; absent = the default, so an existing install gets issue #54's fix without touching config).

## EngineEnvironment

**`EngineEnvironment`** (config.json map) — extra env vars set on the engine process and inherited by every spawned agent CLI. The corporate-network escape hatch: `HTTPS_PROXY`/`HTTP_PROXY`/`NO_PROXY` (kiro-cli is Rust/reqwest, the Claude adapter is Node — both read these, neither reads Windows/WinINET proxy settings), plus TLS-interception CA bundles (`AWS_CA_BUNDLE` for kiro-cli, `NODE_EXTRA_CA_CERTS` for Node). Diagnosed on a proxied machine 2026-07-10: kiro-cli `dispatch failure (io error)` against `oidc.us-east-1.amazonaws.com` = blocked direct egress; the same failure mode also slows the provider dropdown (Kiro's model-catalog shell-outs time out). User entries are applied before the reserved `CWKT_*` keys, which win on collision. Surfaced in Unified Settings as a multiline **`KEY=value`-per-line** field (validated on save: malformed line or case-insensitive duplicate key rejects with the offending line quoted); stored in config.json as the `engineEnvironment` map.

## Log retention is ONE policy, owned by Core.DiagnosticLog

**Log retention is ONE policy, owned by `Core.DiagnosticLog`** — every diagnostic log goes through it (`engine.log`, the ACP/MCP/engine-channel byte tees, `config-error.log`, the `run_tests` tee). Before it, each writer picked its own mode ad hoc: the ACP tee truncated per connection (`FileMode.Create`), *everything else appended forever* and nothing was ever reclaimed — a 25-day-old `engine.log` had reached 11 MB (96% of it the `[rpc]` verbose StreamJsonRpc trace that `LogEngineChannel` switches on). Policy: **`StartRun` moves the primary aside to `<name>.yyyyMMdd-HHmmss`** so the primary holds THIS run — what the raw byte tees want — while prior runs survive a restart, which is what a field bug report needs; **a write past `MaxFileBytes` (5 MB) rolls mid-run**; **`Sweep`** drops anything older than `MaxAgeDays` (7) then evicts oldest-first until the dir is under `TotalBudgetBytes` (50 MB), rolled history before live primaries (a primary may be held open — that delete just fails and the next pass retries).

### Every line is stamped, and `DiagnosticLog` owns the stamp

**`AppendLine` prefixes `[yyyy-MM-dd HH:mm:ss.fff]` to every line it writes** (issue #82). It belongs here for the same reason the lock, the roll and the retention do: this type owns the log's shape. Left to callers it drifted into three formats (`ErrorTableLog` and `TestRunDebugLog` bracketed with milliseconds, `ExtensionConfig` unbracketed without) — while **the highest-volume writer of all, the agent CLI's stderr relayed through `engine.log`, carried no time at all.** That is the one stream that has to be read against a hang, a startup phase line or the frames in `acp.log`, and none of those comparisons were possible. Those three callers no longer stamp their own; a fourth that starts doing so will double up.

Two properties worth keeping:

- **Stamped INSIDE the write lock.** Computing it at the call site lets two concurrent writers — engine stderr arrives on pool callbacks while the UI thread logs — land in the opposite order to their stamps, so the log lies about sequence, the one thing it exists to establish. Pinned by `AppendLine_StampsAreOrderedWithTheWrites`, verified load-bearing by hoisting the call out of the lock (fails 3/3 runs).
- **It is write time at the SINK, not origin time.** Anything that crossed a pipe to get here — the agent's stderr → the engine → the shell — is stamped on receipt, so the value is an upper bound on when it was said. Fine for correlating, worth knowing before reading milliseconds off two processes.

The byte tees (`OpenTee`) are deliberately untouched: they shadow a raw protocol stream and injecting text would corrupt it.

**Age and total size are the ONLY things that delete a log — there is deliberately no cap on the number of rolled generations.** A count is an arbitrary proxy for "don't accumulate" that evicts unconditionally: a fixed depth of 3 would drop a run from ten minutes ago just because the window was reopened four times, with the directory sitting at 2 MB. The two sweep limits measure what actually matters (staleness, disk), so they alone decide; `MaxFileBytes` is **not** a retention limit, it bounds a single *file* so it stays openable, and rolling it is what hands the bytes to the sweep.

**That's why `Sweep` runs after every roll**, not just at host startup: rolling is the only thing that creates files, so pairing them keeps the budget binding at all times — otherwise a long debug session rolling every 5 MB accumulates all day with nothing reclaiming until the next window open. The startup call additionally reclaims **orphans** (logs whose feature was retired — no writer will ever open them again, so no roll can reach them). `OpenTee(path, exclusive:)` keeps the ACP tee's `FileShare.Read`: a concurrent `engine/summarize` session's open fails and it runs without teeing, rather than braiding two raw frame streams into one unreadable file. Every method is best-effort/never-throws, and a null sink degrades to not-teeing.

**Every sweep is SCHEDULED, never run inline — `SweepInBackground`, coalesced per directory** (issue #100). `ChatToolWindow.InitializeCoreAsync` is one straight-line synchronous block on the main thread: `OnToolWindowCreated` starts it on the caller's UI context, `VsIdeServices.CreateAsync` switches *to* the main thread and stays there, and from the sweep down to `EngineClient.Launch` there is not a single `await` (`RestartAsync` switches to the main thread before calling it as well). And it isn't one sweep — on that same block: the explicit `Sweep(LogDirectory)`, then `StartRun(stderrLog)` → `Roll` → `Sweep`, then `EngineClient.Launch` → `OpenTee` ×2, each rolling when non-empty → `Sweep` again, twice. **Four full enumerate-and-stat passes plus three `File.Move`s, per window open**, over a directory measured at **365 files / 42.2 MB** on one machine — two orders of magnitude more bytes than the 24-file diff dir that prompted #88, on the same thread, already shipping. `Sweep` early-returns before the eviction sort when under budget, but the enumeration and per-file `FileInfo` stat happen regardless. The reasoning is #88's, unchanged: the cost of touching that directory is not ours to predict (AV/EDR hooks, LocalAppData redirected onto a network share, VDI — issue #86), so a local timing establishes a floor and says nothing about the ceiling.

**The fix is not symmetrical with the diff sweep.** That one backgrounds whole; here only *half* of each trigger can move. `StartRun` and `OpenTee` hand back a sink the caller writes to immediately, so the roll's `File.Move` is ordered against the caller's own next act and stays inline — it is the `Sweep` *inside* `Roll` that defers. **Pairing roll-with-sweep is preserved, not dropped**: it exists because rolling is the only thing that creates files, so it's what keeps the budget binding at all times (see above), and the queue entry clears when a pass **starts** rather than when it finishes — so for any roll there is always a pass whose enumeration begins after it. A roll landing while an entry is queued is covered by that pass; one landing after it started queues a fresh entry. Coalescing is **per directory** (a host sweeping two scratch dirs would otherwise silently lose one). What deferral does cost: a process that exits immediately after a roll may never run its pass — a Console proof, not a host anyone's logs depend on — and the next host start sweeps what it left.

**Coalescing barely fires in practice, and the telemetry is what showed it.** The first run in Visual Studio with logging on recorded **six** passes for one window open — the startup sweep, then one per roll, each carrying `+1 roll inline` — not one pass. `Task.Run` picks work up in microseconds, so by the time the next roll lands a few ms later the previous pass has already started and cleared its entry; clear-at-start is doing exactly what it says, and merging a burst is simply not what a window open looks like. It still fires when the pool is saturated, which is the case it protects against. **What actually fixed the issue is the deferral, not the dedupe** — six 4 ms passes off the UI thread is not the problem the four inline ones were. A debounce would collapse them for real, and is deliberately NOT built: nothing has measured a machine where six background passes cost anything, and building for an unmeasured cost is restructuring on a theory.

**A second win, free: the pass is no longer under the global write lock.** `Roll` is called with `Gate` held, so a slow sweep used to block every `AppendLine` in the process for its whole duration — every host's engine log, ACP tee and permission-decision line.

**Sweeps and rolls are now concurrent, so `RetentionSweep` skips a file whose stat says it's gone.** A `FileInfo` for a path that no longer exists reports `LastWriteTimeUtc` as 1601, which is older than *any* cutoff — so without the check a file a roll renamed between our enumeration and our stat takes the age branch and we delete that **name**, by then possibly the fresh primary the roll just created. Defensive rather than pinned: the race is between two lines inside `RetentionSweep.Run`, with nothing a unit test can wedge between them.

`Sweep` stays public and synchronous for callers that must observe the result (the tests; any future teardown). `DiagnosticLogTests` pins the rest through `OverrideSweepScheduler`, a test-only seam standing in for the thread pool — the assertion that matters is a **negative** ("the directory has NOT been swept when the call returns"), and against a real pool that is a race, not a check. Four injections verified load-bearing: sweeping inline, no coalescing, coalescing globally instead of per-directory, and never clearing the entry (which latches retention off for the process lifetime).

**Every pass reports itself, duration first — `[retention] logs: 4 ms, 304 files, 0 deleted, 0.0 MB reclaimed (+3 rolls inline, 1 ms)`.** The sink is `DiagnosticLog.RetentionLog`, wired by **both** the VSIX (to `engine.log`) and the engine process (to its stderr, which the shell drains into the same file) — both, because the ACP and MCP tees roll inside the engine, and `acp.log` is the log that actually reaches the 5 MB cap mid-session. The diff scratch sweep reports on the same shape via `ReportRetention("diff", …)`, so one grep covers every scratch dir we reap. **Wired before the first sweep is scheduled**, or the startup pass — the expensive one, and the one a slow-machine report is about — writes nothing.

**The inline half is attributed separately (`+N rolls inline, X ms`), and a coalesced pass counts every roll it stood in for.** That parenthetical is the only part still on the caller's thread, so it is what a hang report is actually about; if it counted only the roll that happened to schedule the pass it would read as a quarter of the truth on a window open. `Scanned` counts every file the enumeration yielded, survivors included — that's the cost that is paid even when nothing is deleted, and `Sweep` early-returns before the eviction sort when under budget, so "0 deleted" must not read as "did nothing".

**Why log it at all, when we already measured it: because our measurement is a floor and only a floor.** 3–4 ms over 304 real files, warm, local SSD — consistent with #88's shape (1 ms at 24 files, 488 ms at 10k, 2.8 s at 40k). The ceiling belongs to the machine (AV/EDR interception, LocalAppData redirected onto a share, VDI), which is the entire argument for going off-thread in the first place, and it's the same reason a local number can never close a field report. The line is what makes one attributable: it separates "retention is slow here" from "something else is".

**`PruneOldTestResults` is recursive directory deletes under the same rule**: it runs inside `run_tests`' `Task.Run`, beside project classification, and is awaited there rather than forgotten because the run's own results directories are created afterwards and the prune deletes every subfolder it finds.

**A tee's owner MUST dispose it at teardown, or the NEXT run's roll silently fails and the two runs braid into one file.** `Roll`'s `File.Move` can't move a file the *same* process still holds open, and it swallows that (by design — a second devenv mid-write is expected), so the only symptom is a primary with several `=== session` headers in it and a missing generation. Latent until a host tears down in-process: `EngineClient.Launch`'s two `TeeStream`s were never disposed (only `_rpc` and the process were), which didn't matter while the sole teardown was devenv exiting — the in-place Restart made every restart lose `engine-channel.log`'s roll (measured 2026-07-28: `engine-channel.log` did not roll while `engine.log` and `acp.log` did).

**`ChatToolWindow.WriteStartupError` is the one deliberate holdout** — it must stay callable when Shell/Core won't load, so it keeps its self-contained `File.AppendAllText` and is bounded only by the sweep. Pinned by `DiagnosticLogTests`.

## Startup times itself, and a phase that never returns is reported from another thread

**A wedged UI thread writes nothing, so `engine.log` simply stops and its silence names no phase.** That is the gap this closes: a hang is the one failure that erases its own evidence, and none of the things that could cause one — a cold MEF composition cache after a VS update, a first directory walk over network- or sync-backed storage, endpoint security inspecting either — says anything about itself.

**It does not cover failures after `window ready`.** A crash on a dispatcher tick — the #103 shape, an unhandled `FileNotFoundException` from the Markdig assembly-name capture, which leaves a dump rather than silence — is reported by `MarkdownRenderFirewall`, not by this timeline: the render runs long after the last phase here closes.

**It exists because a UI-thread hang otherwise leaves no attributable evidence** (#86, a VDI sluggishness report whose only honest next step is field measurement). The reorder below is a plain correctness fix regardless.

**`Core.StartupTimeline` — phase lines into `engine.log`, plus a watchdog.** Two properties, and they are the whole design:

1. **A phase is written when it ENDS, not summarised at the finish.** A single "startup took N ms" line needs startup to have finished, which in the case being diagnosed is exactly what doesn't happen. Per-phase lines mean the log's last entry is always the last thing that completed, so the failure is bracketed even with the watchdog off.
2. **The stall report comes off a pool `Timer`, never from the caller.** The phase that hangs is by definition the one that cannot report itself — whatever the blocked thread was going to write is written after it unblocks, i.e. never. `Begin` arms a timer; a phase still open after 5 s is reported repeatedly for as long as it stays open. An indefinite hang therefore produces an indefinite series of lines *naming it*, which is the artifact the report needed.

**Repetition is deliberate, not a one-shot warning.** It separates "slow, then finished" from "never came back", and it puts an upper bound on the hang in the log even when the process is killed rather than recovering. One short line per 5 s cannot meaningfully grow a log — the 5 MB roll is years away at that rate.

**Durations are milliseconds everywhere, including the multi-minute ones.** These numbers exist to be *compared* — a fast machine's log against a slow one's — and a unit that switches at a threshold makes that a conversion exercise on the one line where it matters most.

**The log is opened FIRST, ahead of every phase it times.** `ChatToolWindow.InitializeCoreAsync` used to build the IDE services and *then* set up logging — sink opened after the most expensive phase and the prime suspect, which is the one ordering that guarantees the interesting case goes unrecorded. The block moved to the top of the method; it costs nothing, since the log paths are `ExtensionConfig` statics and nothing in it reads config. `StartRun`'s inline `File.Move` and the deferred `SweepInBackground` are unchanged (#100), and `config-error.log` is a separate file, so the config-load path is unaffected either way.

Phases, in order: **`first paint`** → **`config`** → **`engine spawn`** → **`ide services`** (the MEF suspect; composition is lazy now, so a number that is suddenly large here says the laziness stopped being enough — and note it is ~2.3–4.0 s on a window reopen but **~9.1 s when the window opens during VS's own launch**, which is the case a user actually meets) → **`engine attach`** → **`chat view`** → `window ready` total. Then a *second* timeline on the fire-and-forget tail, which runs on the UI thread after the window is already usable: **`provider catalog`** → **`picker`** → **`session restore`** → `session restored` total. Two timelines rather than one, because folding the restore into `window ready` would misreport when the user got a working pane.

**A log with phase lines and no `window ready` is a startup that never finished, and the last phase named is where it stopped.** That absence is the signal; the watchdog just makes it explicit sooner.

**The "Starting …" placeholder never painted, and the reason is a priority inversion in our own startup.** Reported as: open VS with the tab unfocused, switch to it, get a blank pane, then window *and* transcript appear together. The placeholder has been set in `ChatToolWindow`'s constructor all along — so "add a loading state" was the wrong fix. `OnToolWindowCreated` launches the init with `JoinableTaskFactory`, which runs it **inline on the UI thread**, and every continuation in that chain posts back at **`DispatcherPriority.Normal` (9), which outranks `Render` (7)**. Each await therefore handed the thread straight to the next step of our own startup and WPF got its first render pass only when the whole chain finished. One `Dispatcher.Yield(DispatcherPriority.Background)` — below `Render` and `Loaded` — before the expensive phases is the whole fix, and it is timed as **`first paint`** so the wait cannot hide in `window ready` as a gap belonging to no phase.

**There were TWO blank gaps, and closing the first exposed the second.** Once the placeholder painted, the pane still swapped to a real but *empty* chat at `window ready` and sat there while `provider catalog` + `picker` + `session restore` ran — 53–945 ms in the collected sessions, most of it the `provider catalog` await, during which the UI thread is free and WPF therefore has time to paint the emptiness. Nothing in that window was usable either: `ChatViewModel.InitializeAsync` holds the send gate shut across all of it, so the composer that appeared could not be typed into. The loading message now **overlays** the chat until `session restored`.

**Overlay, not a deferred swap** — and the difference is the whole point. Holding the placeholder and assigning the view at the end would leave the view outside the visual tree while the transcript is restored into it, so its first layout and render (item containers, markdown) would fall *after* the swap and the gap would move rather than close. Underneath an opaque overlay the view is sited at exactly the moment it was before, so the restore renders behind the message and lifting it reveals a finished pane. The overlay is captured as a **local**, not held in a field: `RestartAsync` re-enters init while the previous run's fire-and-forget restore may still be in flight, and a field would let that stale run uncover the *new* overlay. The reveal is in a **`finally`** — a failure must show the chat, not hide it, since the view-model reports its own errors into the transcript underneath.

**Deliberately not a spinner.** `ide services` holds the UI thread outright for 2.3–4 s, so any animation would freeze for exactly the interval it exists to cover — and a stalled spinner reads as a hang, which is strictly worse than static text. If the pane ever needs to look busier, the fix is getting that phase off the UI thread, not animating over it.

### What the first collected sessions actually said

**The watchdog, observed against a genuinely stopped UI thread.** Fourteen collected sessions (2026-08-08/09); it fired twice, both times naming `provider catalog` — and both were a breakpoint in the markdown render path, not the product. The shape is worth knowing because it is what a real hang will look like: **the `listProviders` *result* is already in the log above the stall line.** That is not the catalog having finished — the RPC completes on a pool thread and traces from there, while the `await`'s continuation cannot be dispatched onto a halted UI thread, so the phase is genuinely still open and "still running" is literally true. Everything that doesn't need the UI thread keeps writing straight through the stall (`shell/tools/list` served, the `[acp]` working-directory line, two retention sweeps), which is the signature: **a stalled phase surrounded by healthy non-UI logging is a wedged UI thread, not a slow backend.** Read the other way round it inverts: "but the result already arrived" makes the watchdog look as if it named the wrong phase.

**`ide services` is the number `window ready` is made of, and it is bimodal.** 2299–3954 ms in eight sessions against 74–122 ms in three, i.e. 70–80% of the total either way, and it tracks a cold devenv rather than the workspace (both extremes occur on the default workspace; the fastest are re-opens inside a live devenv). So the lazy accessors cut this without ending it — something in the eager path still costs seconds cold, on the UI thread. **It never trips the 5 s watchdog**, so it will never appear in a field report, and it is nonetheless what a "slow to open" complaint is about.

**`listProviders` is not a lookup — it is two live `kiro-cli` spawns, and that is nearly all of it.** Measured on one connection: `listProviders` 2044 ms, then `shell/tools/list` 11 ms on the same connection. The tempting read is a cold net10 closure loading lazily behind the first RPC — **and it is wrong**. `KiroAgentProvider.Models` shells out on first access and **first access is `engine/listProviders`**: `kiro-cli chat --no-interactive --list-models --format json` at 967–1484 ms, plus `kiro-cli settings chat.defaultModel --format json` at ~500 ms (both timed directly, 2026-08-09), which accounts for the 2044 ms on its own. So the cost is a network-backed CLI round-trip on the path to opening the chat window, and `EngineService.ListProviders` being a one-line projection says nothing about it — **the work is behind a property getter the projection touches.**

It is still right to ask early — the clock starts with the *request* (the engine had logged `started` 830 ms before that request went out), so `ChatToolWindow` issues the call right after `EngineClient.Launch` and hands the in-flight task to `ChatViewModel.InitializeAsync`, overlapping it with the chat view instead of queueing behind it. **`provider catalog` therefore measures what is LEFT of that call, not the call** — a large number there now means the overlap wasn't enough, which is a different question from before and the reason `picker` was split off it.

**So the seed answers and the probe runs behind it.** Last run's list is already persisted to `DiscoveredModels`, forwarded as `CWKT_MODEL_CACHE` and applied by `SeedModels`; `Models` now returns it immediately and starts the live probe in the background, where it overlaps `ide services` + `chat view` (2.8–4.9 s of UI-thread work) instead of sitting inside the call the picker is waiting on. Measured against the real engine: **`listProviders` 112 ms**, down from 2044 ms. Dropping the prefetch
is a **silent** regression — pickers still fill and every other test still passes — so it is pinned by
`StartupPrefetchTests`.

**The probe is eager-in-background, NOT lazy-on-first-dropdown, and the session start WAITS for it.** `KiroLoginState.IsSignedOut` runs the very same `--list-models` command and is short-circuited by `_knownLoggedIn`, which `KiroModelCatalog.TryList` sets on success — so the startup shell-out has always doubled as the login probe. Deferring it until something asks would not remove a spawn, it would **move one onto the session-start path**.

**Running the probe eagerly keeps the short-circuit only if the probe completes before a session starts, and here it does not.** Measured in Visual Studio: the session starts **243–1243 ms** in against a **~1.5 s** probe, so an unguarded gate finds the flag unset and spawns a **second identical CLI process alongside the first** — across eight sessions the session's own spawn went from ~500 ms to **1479–1802 ms**, and Kiro's readiness **did not move at all**. Nothing fails; the win cancels itself out. The fix is `KiroAgentProvider.Preflight`, which waits (bounded, 15 s, falling through on timeout) for the probe already in flight instead of duplicating it. **A correct diagnosis in a comment is not a mitigation**, and only timings from a real run in Visual Studio show this one; offline it is green.

**The refreshed list reaches the picker as a push, because it has no other way in.** `AcpAgentProvider.BeginModelRefresh` is offered to every registered provider and answered only by the ones with something to discover, so the engine needs no "if kiro". When the answer differs from the seed it goes back as `shell/providers/models` (`ProviderModelsDto`) — the existing `ApplyDiscoveredModels` route is fed from `StartSessionResponse.Models`, and **Kiro's `session/new` carries no models at all** (verified on the wire: `conversationId`, `workingDirectory`, `workspaceRootReason`, nothing else). `ChatViewModel.ApplyRefreshedProviderModels` is a *separate* method from `ApplyDiscoveredModels` for the same reason it exists: that one realigns `_activeModelId` because a running session resolved a model, and this one carries no session, so borrowing it would claim a session had switched model when none had. Both run under `_settingSelection` — an unsuppressed `SelectedModel` move reads as the user changing model, which drops or live-switches a session the user never touched.

**A refresh identical to the seed is not pushed** (`SameModels`), because the steady state is a cache that was right and a redundant push would rebuild the list under a user who may have the dropdown open. Order counts as a difference: the catalog puts the configured default first and the picker selects `Models[0]`. Proven end-to-end against the real engine with a deliberately short seed — result at 112 ms carrying the seed, push at 1464 ms carrying the live 9-model list.

**`picker` is not free, and it gates the warm start.** ~500 ms between the catalog arriving and `engine/startSession` going out, on the UI thread: building the picker view-models persists each backend's model list, and `ExtensionConfig.Update` is a full config.json read + serialize + write + `Changed` fanout **per provider**. Setting the selection is also what releases `WarmStartSession`, so time spent here delays the backend coming up — issue #19's whole purpose — while looking like nothing more than a slow picker.

**The Kiro v3 warm start is already off the critical path; what it isn't is early.** Its `startSession` returned 1350 ms after it was sent (node spin-up included), 1.3 s *after* `session restored` had already been written — so it costs the window nothing. But it cannot fire until the catalog has arrived and the picker is set, which put it 7.5 s into a cold window open, of which only 1.35 s was Kiro. **The engine PROCESS is spawned before `ide services`, not after it** (`EngineClient.Spawn` / `Attach`, split because only the attach needs `IIdeServices`). Not for the engine's own boot — for what it does the moment it is up: it builds its registry and starts every backend's model probe immediately, and that probe is the ~1.5 s the first session otherwise waits on. Spawning ahead of `ide services` buys the whole of that phase as probe time — 2.3–4.0 s on a reopen, ~9.1 s during VS's own launch. Measured evidence that this is the lever, confirmed after the hoist: **Kiro's session opens in 1170–1221 ms when the probe has finished, and 2444–3055 ms when it has not** — and Claude Code, which has no pre-session shell-out at all, opens in **1110 ms**. So Kiro's session start is not slow; everything above ~1.2 s is the probe.

**The session waits for LOGIN to be known, not for the probe to end.** `KiroModelCatalog.TryList` makes two calls and establishes login on the first (`--list-models`); the second (`settings chat.defaultModel`, ~500 ms) exists only to order the picker and tells the gate nothing. `KiroLoginState.SignedIn` signals at the first, and `WaitForPendingModelRefresh` takes whichever of that or the probe's end comes first — the probe stays a wait target because a probe that *fails* never signals, and that is exactly when the gate must run its own check. Losing the serialisation is the trade: the ACP session may now spawn while that settings read is still running, which is one lightweight call against a process launch, where the bug this all started from had two full `--list-models` probes racing.

**The hoist cannot fix the warm case; the login signal partly can.** With `window ready` at 362–641 ms, `startSession` goes out ~450–660 ms in and the probe cannot finish first however early the engine spawns — so the session still waits. What the signal removed is the part of that wait spent on a call the gate doesn't need. **Confirmed by isolating the gate wait** (`startSession` → the `[acp] 'kiro' agent version` line) from the ACP handshake, which is a near-constant ~1230 ms and was masking it end-to-end: warm gate wait **1085–1399 ms pre-hoist and 1188–1363 hoist-only, against 760–814 ms with the signal** — a 54 ms cluster across three sessions, matching the timed cost of `settings chat.defaultModel`. Warm Kiro readiness ~3.1–3.6 s → **~2.5 s**; when the probe has already finished the gate wait is 60–176 ms and Kiro opens in ~1.2–1.3 s, level with Claude's 1110 ms. **The remaining ~760 ms is `--list-models` itself**, and that is the floor: shortening it means trusting a stale login or skipping the gate, which trades a headless browser-launch hazard for time. The cost is a window in which the process is **unowned** — no `EngineClient` exists, so no `Dispose` reaches it — hence the kill-on-failure path in `ChatToolWindow`. (An unattached engine would in fact exit by itself: nothing writes to the stdin we redirected and its `host.Completion` ends when that closes, so the explicit kill is defence for a child that ignores EOF, not the only thing preventing a stray process.)

**Shortening `provider catalog` or `picker` moves the warm start earlier, but that only buys backend readiness if nothing else fills the gap** — the duplicate-spawn regression above is exactly what filling it looks like, and it cancelled the entire gain while every phase line got better. **A startup timeline can improve on every number it prints and leave the user waiting the same amount of time**, because it stops at `session restored` and the backend comes up after that. Measured warm, on the first run in Visual Studio after the change: `provider catalog` 1997–4541 ms → 0–900, `session restored` 2385–4638 → 53–945, `startSession` out at 1674 → 243–1243 — and Kiro ready 2813 → 2561–3617, i.e. nothing. The numbers that matter for readiness are `startSession → kiro-cli first log` and `→ session ready`, and neither is a phase.

**The index walk reports separately, and reports the walks it ABANDONS.** `FileReferenceResolver.IndexLog` (null by default — the VSIX wires it, Desktop deliberately doesn't) writes `[file-index] 812 ms, 3412 paths, 1204 names, root C:\src\repo`. Its cost belongs to the machine, not to us — repo size, storage redirected onto a share, on-access scanning of every enumeration — so "the blue links take a while" is unattributable without a number, and the number needs a size beside it to mean anything. Cancelled walks are logged too (`abandoned (root changed)`): the root genuinely flaps during startup, so a log carrying only the surviving walk would attribute the whole wait to it while hiding the full-tree enumerations that ran alongside.

**What it still cannot see**: the watchdog reaches the log through the caller's sink, and `DiagnosticLog.AppendLine` serialises every writer behind one lock — so a thread wedged *inside a write* takes the watchdog down with it. Fine for the failures this was built for (all of them slow work the UI thread was made to wait on, holding no log lock), and worth knowing before reading silence as "the phase completed".

**Pinned by `StartupTimelineTests`, and the two that matter hold while the calling thread is blocked** — `Thread.Sleep` on the test's own thread, so anything reaching the sink demonstrably came from elsewhere. Injections verified: removing the timer fails those two and only those two; removing *both* silence guards (dispose and clear-phase — each alone is sufficient, deliberately) fails `EndSilencesTheWatchdog`. `FileReferenceTests` covers the walk's own reporting the same way, including the abandoned case.

## The age-and-budget mechanic is shared; the diff scratch dir is its second caller

**The logs are not the only scratch dir we write, and the diff dir had no retention at all** (issue #88). `VsEditApplier` writes the diff viewer's before/after copies to `%LOCALAPPDATA%\code-wicket\diff` and nothing ever deleted them: 24 files spanning 15 Jul → 3 Aug when the issue was filed.

**The reason nobody added retention was a comment stating VS does it for us.** We pass `VSDIFFOPT_LeftFileIsTemporary`/`RightFileIsTemporary`, which asks VS to delete the files when the comparison window closes, and the code asserted that as fact. The folder disagrees. Eight of those 24 were written *after* diffs moved to preview tabs (27 Jul), and the 3 Aug trio settles it: three diffs at 19:19, 19:20 and 19:22, under preview tabs where **each new diff takes over the single preview slot** — so the first two windows were closed *while devenv was still running*, exactly the event the flag reaps on, and all six files were still there three days later. (What that evidence can't rule out is a session that was killed rather than exited; hence the sweep is a **backstop to** the reap, not a replacement, and nothing depends on which way it goes.)

**The growth shape is why it stayed small enough to miss.** Files are named `<stem>.before<ext>`/`.after`, so a repeat diff *overwrites* — the file count is bounded by the set of distinct file stems ever diffed, not by the number of diffs. That set is unbounded over time (the union across every solution, forever) and each file holds a **whole** side: the one `ChatViewModel` pair is 266 KB on its own. And disk is the lesser half — these are verbatim source snapshots sitting in LocalAppData indefinitely, the same content sensitivity that kept them out of temp to begin with.

**Policy: age (7 days) + total budget (20 MB), kicked off once per chat window from the `VsEditApplier` constructor.** Tighter budget than the logs' 50 MB because a log is read by a human debugging a field report, whereas a before/after pair is dead the moment its window closes. The age limit has a second job: it must clear the longest a diff window can plausibly stay open, since a **promoted (permanent) tab** survives until the user closes it and deleting a live window's backing file is the one way this pass could be user-visible. The constructor is the right hook because nothing *we* opened is alive at that point (`_openDiffs` is empty) — the age cutoff is what keeps a *second* devenv's live windows out of range, and a file it still holds simply fails to delete and is retried next pass.

**It runs OFF the UI thread (`Task.Run(...).Forget()`), and that is a rule rather than a measurement result.** `VsIdeServices.Create` runs on the UI thread, and bulk file enumeration + deletion must never happen there, because the cost of touching this directory is not ours to predict: on-access AV/EDR scanning hooks both enumerate and delete (this project already treats corporate EDR as a live constraint — it's why these files aren't in temp to begin with), LocalAppData can be caught by folder redirection onto a network share, and our users are not all on local SSDs (issue #86 is a VDI sluggishness report). **A local timing establishes a floor and says nothing about the ceiling** — a floor that looks free is exactly what puts work like this on the UI thread. For what the floor is worth: 1 ms over the 24 files issue #88 was filed on, but O(files) with a fat tail (488 ms at 10k, 2.8 s at 40k), and the **first** sweep on a machine is the bad one — it lands on however much accumulated while nothing reclaimed at all. Racing a diff the user opens meanwhile is benign: the file list is snapshotted at enumeration, a just-written file is never past the age cutoff, and budget eviction is oldest-first so it sorts last.

**A fault on that background thread would be SILENT, so it is caught and logged at the call site.** `TplExtensions.Forget()` is documented as *"consumes a task and doesn't do anything with it"* — a genuine no-op that expresses intent to the threading analyzer and does **not** observe the fault. An exception escaping the delegate would fault the task, go unobserved, and surface only at finalization via `TaskScheduler.UnobservedTaskException`, which since .NET 4.5 doesn't tear the process down: no crash, no log line, retention just stops and the only symptom is the folder growing again. `RetentionSweep.Run` never throws (blanket catch, pinned by `RetentionSweepTests`), so the `try`/`catch` around `SweepDiffScratch()` writing to `ToolErrorLog` is belt-and-braces for the day that contract changes — the point being that it must not be `Forget()`'s no-op standing between a broken sweep and anyone finding out. Not unit-testable (a lambda in a VSSDK-dependent constructor); the never-throws contract underneath it is.

**Owned by the applier that WRITES the files, not moved to the engine.** Out-of-process would take the cost off devenv entirely, but the engine has no other knowledge of this directory and also runs in hosts that never write a VS diff (Desktop/`--fake`, the Console host, stub-IDE mode) — it would be reaping a directory it doesn't own, with the path duplicated across a process boundary and free to drift. Off-thread gets the same benefit without splitting the writer from the reaper.

**Not the `PruneOldTestResults` shape** (delete everything prior at the start of each run). A TRX has no life beyond its run; a diff does — both the promoted tab and the `_openDiffs` re-activate path need their backing files to survive later diffs *in the same session*.

**The mechanic now lives in `Core.RetentionSweep`, with the log-specific half left in `DiagnosticLog`** — the limits, and the rolled-history-before-primaries eviction order, passed in as a `Comparison<FileInfo>`. Extracted rather than re-hand-rolled: a third ad-hoc pruner is how the log directory got into trouble in the first place.

**A sweep may only ever be pointed at a directory we exclusively own.** `DiffScratchDir()` falls back to `%TEMP%` when LocalAppData is unavailable — fine for *writing* one file, catastrophic for an age-and-budget *delete* pass, which would reach the whole machine's temp files. So the sweep resolves through `DiffScratchRoot()`, which returns **null** instead of falling back and never creates the directory. `RetentionSweep.Run` is non-recursive for the same blast-radius reason: every caller's scratch files are flat, and recursing would turn one bad path argument into a very large delete.

Pinned by `RetentionSweepTests`; every check was verified load-bearing by injecting its bug. Two of those injections (age, custom eviction order) also fail `DiagnosticLogTests`, which is what proves the delegation is real rather than merely compiling.

## Unified Settings layout is ours to control, and it's declared not implied.

**Unified Settings layout is ours to control, and it's declared not implied.** Both `CategoryRegistration` and every `ExternalSettingRegistration_*` take an optional **`order`** integer (`registration.schema.json` in `<VS>\Common7\IDE\UnifiedSettings`), and an **external region declares its own `categories`** — its property keys are monikers nested under them.

**A setting whose values are WORDS has to be checked against the code that reads them** (issue #190, `messageRelease` on General). `PendingReleaseModes.Parse` answers Queue for anything it does not recognise — which is right for a config written before the setting existed, and wrong for a manifest offering a spelling the parser has never heard of. That failure is silent in the worst way: picking the other value saves, redisplays correctly, and opens the window on the default anyway. So `SettingsRegistrationTests` reads the manifest's `enum` and round-trips every value through the parser, **and asserts the two land on DIFFERENT rungs** — the round-trip alone holds over a parser that answers Queue for both, which is precisely the bug. Its declared default is checked against `ExtensionConfig`'s for the same reason the diagnostic tees' are: it is written down twice.

**The division of labour, confirmed against the live UI: a REGION is a node in the left tree (its own page); a CATEGORY is a heading within that page.** (One region makes the tree read "Code Wicket › Settings": `settings` is a path segment VS auto-titles into a node.) The settings are **four regions** = four pages — **General**, **Backends** (with Kiro / Claude Code / Custom-and-shared headings), **Permissions**, **Advanced** (with Tools / Storage / Diagnostics headings) — everything carrying an explicit `order`. Permissions earns its own page because three tall glob boxes otherwise push every later setting below the fold.

**The provider needed no change through either restructure**: `CodeWicketSettingsProvider.Leaf()` matches the last dotted segment, so a deeper moniker — or one in a different region — still resolves to the same key. That also makes **leaf names a cross-region invariant**: two regions sharing one would read and write the same config field while presenting as two settings, with nothing thrown and both pages simply lying. Pinned by `SettingsRegistrationTests` (unique leaves, every region on the provider's serviceId, every page has a category and vice versa). Explicit `order` on every setting is deliberate — relying on declaration order is what let `agentWorkspaceScope` land among the tool toggles.

**`CacheTag` is stamped automatically and must NOT be hand-written.** It is what tells VS the manifest *content* changed and must be re-parsed; the manifest GUID is fixed across versions, so a content edit with a stale tag can serve users the previous layout — and forgetting to bump it is invisible. So `CodeWicket.SettingsManifest.pkgdef` is a **template with no CacheTag line**, and the `StampSettingsManifestCacheTag` target appends one derived from a SHA-256 of `registration.json` (leading 16 hex chars = a qword) into `obj\`, which is the copy the VSIX packages. The input *is* the file being invalidated, so they cannot drift; any content change yields a new tag, which is the safe direction (a redundant re-parse costs nothing, a missed one is silent).

**`IncludeEngineInVsix` takes it via `DependsOnTargets`, not a second `BeforeTargets="GetVsixSourceItems"`** — two targets hooked to the same one have no guaranteed order between them, and the consumer running first packages an *empty* Include with no error at all (observed). `/updateConfiguration` remains the manual fallback for a hive that still won't re-read.

## The Diagnostics page names the log to read FIRST, and it says it once (issue #82)

**Three log files, two toggles — and the toggles were named so the wrong one was the obvious pick.** (A fourth file and a third toggle have since joined them, below; the naming trap is what this section is about.) Told "turn on engine logging", a user reaches for **Log engine channel**, which is wrong twice over: it tees the shell↔engine hop, so it carries our already-terse `SessionError` DTO and none of the agent CLI's stderr. They reproduce, look, find the same useless word and conclude there is nothing more to see. Meanwhile `acp.log` — the file holding the failing frame — sat behind a name that means something only to someone who already knows the protocol. `engine.log`, the one that was always being written and held the answer, had no entry at all because it has nothing to toggle.

| file | toggle | contents |
|---|---|---|
| `engine.log` | **none — always on** | engine stderr incl. the agent CLI's own, prefixed `[<cli>]`; `[startup]` phase lines; retention lines; permission decisions |
| `acp.log` | `diagnostics.logAcpFrames` — *Log agent protocol frames (acp.log)* | raw ACP JSON, engine ↔ agent CLI |
| `engine-channel.log` | `diagnostics.logEngineChannel` — *Log engine channel bytes (engine-channel.log)* | raw JSON-RPC bytes, shell ↔ engine |
| `render.log` | `diagnostics.logRendering` — *Log chat rendering cost (render.log)* | `[md-cost]` one line per streamed message + one `[render-env]` header (#86); also the env-gated `[md-render]` layout trace |

**The render log is named for RENDERING, not for markdown — and that is the second name it has had.** Markdown streaming is the first render cost worth measuring (#86) and the first, but a chat pane can be slow for reasons that are not markdown's, and a log named after one feature is a log the next investigation quietly writes a second copy of, leaving the user two checkboxes for one question. So the file is `render.log`, the setting is `logRendering`, the environment header is `[render-env]`, and per-feature traces are distinguished by their line PREFIX (`[md-cost]`, `[md-render]`). Free to do here because nothing had shipped: the old name existed for one afternoon and no config anywhere had persisted `logRenderCost`.

**The append is QUEUED, never written inline on the UI thread.** `DiagnosticLog.AppendLine` opens, writes and closes per call under a process-wide lock, so the cost belongs to the machine rather than to us — AV/EDR interception, LocalAppData redirected onto a share, VDI. Those are the same three conditions this file already names as the reason bulk log IO must never run on the UI thread (#100, #88), and they are *the environment #86 is a report from*: an inline write would put machine-priced IO on the slow machine's UI thread, and could additionally block on another process's write to the same lock. It is a handful of appends per turn rather than per render, so the number is small — but "small" is a dev-box estimate of a quantity this file declares not ours to estimate.

`RenderDiagnosticsLog.Post` chains each write behind the last on `TaskScheduler.Default`. **Serial rather than fire-and-forget**, because a cost trace is only readable as a sequence and a `Task.Run` per line races them into the file in an order that is not the order they happened. The scheduler is named explicitly rather than inherited, or a continuation scheduled from inside a task on a UI scheduler comes straight back to the thread this exists to keep off. Two consequences worth knowing when reading the file: `DiagnosticLog` stamps at WRITE time, so a line is stamped slightly after the message it describes finished (ordering is preserved, so the lag can compress a gap but never invert one); and the last line dies with the process unless someone drains the queue, hence `Flush`, called from `ChatToolWindow.Dispose` and the Desktop host's `OnExit`.

**It defaults OFF, like the other two.** The queue makes the enabled case honest; it does not make an always-on default free — the probes, the timer and the writes still exist, and a trace nobody reads should not be running on every install. The price accepted is one round trip before any numbers exist. (It was built default-on and turned over, on the argument that a reporter on a locked-down VDI cannot be talked through enabling anything — a real cost, and the one being paid here deliberately.)

**The setting deliberately does NOT enable `CWKT_MARKDOWN_RENDER_LOG`'s per-render `[md-render]` trace.** That one appends on every rebuild — ~10/second/message, +62% on the careful drag — so with both on, most of what the `[md-cost]` aggregate reports is the other trace's file IO. A user asked to turn on render logging must not silently receive the instrument that falsifies the measurement, which is why one is a setting and the other stays a developer-only variable.

**The sink is installed by the HOST, and nothing is written until it is** (`RenderDiagnosticsLog.Sink`, same shape as `DiagnosticLog.RetentionLog`). Not a style choice: `ExtensionConfig.LogDirectory` is **not** covered by `ExtensionConfig.RedirectTo` — the redirect moves config and attachments, not logs — so a writer that switched itself on from inside the UI library would also fire from the unit tests, which construct real viewers and render real markdown, straight into the developer's own log directory. A host is the only place where the decision can be made with the redirects already applied. The Desktop host enables it for **interactive** runs only, for the same reason.

**The "read engine.log first" pointer lives on the CATEGORY, not on each setting.** Repeating it in both descriptions was the first draft and it read as boilerplate — the eye skips a sentence it has already seen, which is the opposite of the goal. `CategoryRegistration` accepts `description` (verified against `Common7\IDE\UnifiedSettings\registration.schema.json`), so the Diagnostics page carries it once, above both checkboxes.

**A category description (`CategoryRegistration.description`) renders, and that is worth writing down
because nothing else told us.** Zero of the ~20 VS-shipped manifests set one, so the schema was the only evidence it was legal and there was no evidence at all that the UI drew it — a fallback was kept ready (a single pointer on `logAcpFrames`, `order: 10`, never both). **Verified in Visual Studio 18.7, 2026-08-08**: it renders as a paragraph under the category heading and above the first setting, on its own, un-truncated, with `→` and the `%LOCALAPPDATA%\…` path intact. The Tools category on the same page has none and draws just its heading, so the two shapes sit side by side in one screenshot. Reusable: **a Unified Settings category is a place to put a sentence**, which is the right home for anything true of a whole group rather than of one checkbox.

The one sentence kept on a setting is `logEngineChannel`'s *"Does not contain the agent CLI's output."* That is not a repeat of the category text — it is the correction for the specific trap, on the specific setting that causes it.

**A rename must stop at the title.** The leaf (`logAcpFrames`, `logEngineChannel`) is the config binding — the provider dispatches on it and `ExtensionConfig` binds through it — so carrying a rename into the leaf would silently orphan the setting on every machine that had already set it: the checkbox reads default-off while the old value sits in config.json doing nothing. Nothing else in the manifest would complain, so `SettingsRegistrationTests` pins both leaves and the category description explicitly (each verified load-bearing by injecting its own bug). `CacheTag` needs no attention — the build stamps it from a hash of this file — **and that turns out to be sufficient for manifest content on its own**: adding `logRendering` (a new leaf, a new title and a new description) appeared on a plain rebuild-and-launch with no `/updateConfiguration` and no hive reset, observed 2026-08-11 on VS 18.7. **What the tag does NOT cover is the pkgdef**: it hashes `registration.json`, so a registration that lives in the pkgdef instead — a `ToolsOptionsPages` entry for a classic Options page — invalidates nothing, and the experimental hive needs `/updateConfiguration` before that page appears (measured 2026-09-16). Before the stamp existed (July 2026) the manual step was needed for content changes too. It remains the fallback for a hive that will not re-read.

## Attachment storage: a size limit and no clock (issue #118)

`AttachmentStorageLimitMb` — Unified Settings → **Advanced → Storage**, default 100 MB, floor 10.

**Named for the class of thing rather than for images**, because that is what it is likely to grow to
cover: pasted files, whatever else a message comes to carry. The floor exists because a hand-edited `0`
would otherwise mean "keep nothing" and empty the directory on the next window open — a lot of damage
for a typo, so it clamps UP, and it clamps on the way out too, so the Settings UI shows the value
actually in force rather than one it will not honour.

**There is deliberately no age rule.** It launched with 7 days, copied from the log and diff-scratch
policy, and that was wrong for a reason worth keeping: those directories hold *scratch* — a log or a
before/after copy is dead the moment its purpose passes, so a timer is exactly right — while this one
holds conversation CONTENT. Conversations are kept indefinitely, so attachments were the only piece of
conversation content we deleted on a clock. The only real reason to reclaim them is disk, which the
budget already states, and a size bound degrades gracefully where a timer simply deletes: a conversation
loses its pictures when the disk fills, not on a birthday.

`RetentionSweep.Run` therefore takes a **nullable** `maxAge`, null meaning no age rule at all —
implemented as a `DateTime.MinValue` cutoff, so the age branch becomes unreachable rather than needing a
second flag kept in step with it. The log and diff-scratch callers pass a value and are unaffected,
which is pinned.

**Not verifiable offline**: the Unified Settings half (an `integer` property with `minimum`/`maximum`,
the first non-boolean/string in this manifest, and a new `storage` category) only exists in devenv. The
`CacheTag` is stamped by the build from a hash of `registration.json`, as always — never hand-written —
and a new property is picked up by the stamped `CacheTag` the next time the extension is launched (`/updateConfiguration` only as a fallback — see above).

## The Settings page is pushed, never re-queried (issue #271)

**The report.** An "always allow" answered on the permission banner is written to config.json and is in
force at once, but the Permissions page in Unified Settings did not show it — not on reopening the
dialog, not on its Refresh button — until devenv restarted. The provider's comment stated the belief the
report contradicted: *"We never raise these (realtimeNotifications = false): USX re-queries when the page
is shown."*

**What USX actually does, measured on VS 18.9.1** (the schema's one-line description, "whether the
callback provides real-time notifications", says nothing about any of this):

- **A setting row pulls its value once, when it first connects to the provider**, and subscribes to
  `SettingValuesChanged`. It pulls again only when that event names its moniker. There is no pull on
  show, on focus, or on reopening the dialog; the page's rows persist for the process and resume
  without re-reading. That is how the defect above was met in the first place.
- **`realtimeNotifications` decides exactly one thing: whether the region gets a Refresh button**, which
  appears when the flag is false. It does not gate whether rows listen for `SettingValuesChanged` — they
  always do — and it does not change how failures are treated.
- **Refresh calls `RefreshCacheAsync`, and only if the provider implements
  `ICachingExternalSettingsProvider`.** Ours did not, so the button did nothing — which is why the
  report's step 3 held.
- **A change notification is matched against the moniker the row pulled with**, case-insensitively and
  exactly — the same string the row passes to `GetValueAsync` — or matches every row when the provider
  says so.
- **For a caching provider, a push re-reads the setting before writing it.** If the store no longer holds
  what the row last saw while the row carries a user edit, USX enters a conflict state — *"This setting
  was changed to X in the backing store. Keep your change or keep the backing store change?"* — instead
  of writing.

**The stale-overwrite question, answered.** A push is per-setting: only the row whose value the user
changed is pushed. Editing another field on a stale page did NOT save the stale
list back. Editing the stale list itself did — a user removing one rule from a list missing the banner's
additions saved the list without them. That is the narrower data loss, and it is closed two ways below.

**The fix, in three parts, and why each.**

1. **`Shell.ServedSettings` — a record of what the page has been told.** `GetValueAsync` records each
   value it serves under the moniker USX asked with; `Reconcile` compares every served moniker against
   the store, re-records, and names the ones that moved. Only served monikers are named (nothing else
   holds a stale copy), a null current value leaves the record alone (it is "could not read", not a
   change, and naming it would re-pull a row into a failure), and the re-record is what makes a change
   announced ONCE rather than on every later zoom tick. Boxed values compare by `Equals`, or every serve's
   fresh box would name every setting on every write. The values it compares are `Read`'s — the same
   function `GetValueAsync` answers from — so the record and the page can never disagree about a value.
   Pure and TFM-neutral so it is testable; the provider itself lives in the net472 VSSDK project the
   test project cannot reference.
2. **The provider subscribes to `ExtensionConfig.Changed`**, reconciles on every write and raises
   `SettingValuesChanged` for what moved — on the main thread, always posted (`SwitchToMainThreadAsync
   (alwaysYield: true)`), because a row's handler clears an `ObservableCollection` and because an inline
   raise inside a caller's flow is the shape that misfires (next point). **It never announces its own
   save.** USX calls `SetValueAsync` and only THEN records the value as the provider's and re-marks the
   row's source; a notification landing between the two makes the row re-pull while its value is still
   marked as the user's edit, and wherever what we stored is not byte-identical to what was typed —
   `allowedTools` normalisation to `server/tool`, the `messageRelease` round-trip, the attachment clamp,
   custom-agent JSON re-serialised with discovered capabilities — USX reads that as a backing-store
   conflict over the user's own save. Ordering cannot be guaranteed (the custom-agents save lands on a
   pool thread after its probe, so its continuation and our post race for the dispatcher), so the rule is
   the simple one: a dialog save is never announced, marked by a `[ThreadStatic]` flag set around the
   `Save` alone — thread-static so a banner's save on another thread is not silenced by it. The cost: a
   normalised value shows as typed until the next change to that setting, which is what shipped before.
3. **`ICachingExternalSettingsProvider`, with `RefreshCacheAsync` = reconcile-and-raise.** This makes the
   Refresh button do something, and it is what USX's pre-push refresh needs: a config.json edited OUTSIDE
   the process (the documented offline escape hatch for custom agents) is invisible to
   `ExtensionConfig.Changed`, so Refresh is the only route by which it reaches an open page, and the
   pre-push reconcile is what turns the stale-list overwrite into USX's own conflict prompt.
   `CommitPendingChangesAsync` is a no-op: every `SetValueAsync` has written the file before it returns.

**`realtimeNotifications` stays `false`, deliberately, and is pinned** (`SettingsRegistrationTests.
Every_region_keeps_its_refresh_button`). The issue's likely-fix said flip it; what the flag decides is
whether the Refresh button exists, and flipping it would remove the one route for out-of-process edits
with no other symptom. The event is raised regardless of the flag.

**Not verifiable offline. To verify in a live instance:** answer a banner with "Always allow" while the
Permissions page is open → the list gains the rule without a restart; hand-edit config.json in an editor
→ Refresh brings it in; hand-edit `allowedCommands` while the page holds a pending edit to the same list
→ the conflict prompt, not a silent overwrite. The offline checks pin the record (7, `ServedSettingsTests`)
and the flag; three injections are LOAD-BEARING with the right identity each time: a reconcile that names a
moved value but never re-records it, one that names every served moniker on every write, and one region's
`realtimeNotifications` flipped to true.

**Loose end, not built:** after a dialog save that normalised the value, the page could be told the
stored spelling — but only by a notification that is guaranteed to land AFTER USX's post-push bookkeeping,
which the async custom-agents path cannot promise.
